## 🔴 Критические проблемы (Срочный приоритет)

### 1. I/O-шторм `saveRecoveryDraft` и синхронный перечит каталога в Rust

- **Файлы:**
  - `src/components/workspace/file-actions/use-markdown-autosave.ts` (строки 202–210)
  - `src/lib/recovery-drafts.ts` (строки 29–48)
  - `src-tauri/src/recovery.rs` (строки 125–163, 282–308)

#### Механизм возникновения бага:

1. В `use-markdown-autosave.ts` обработчик изменения контента:
   ```typescript
   const handleContentChange = React.useCallback(
     (fileId: string, content: string) => {
       ...
       useDocStore.getState().patchDoc(fileId, { content })
       useDocStore.getState().markUnsaved(fileId)
       if (document.path) void saveRecoveryDraft(fileId, content, "markdown", document.path)
       ...
     }
   )
   ```
2. `saveRecoveryDraft` вызывается **без какого-либо дебаунса**.
3. В Tauri-окружении отправляется IPC-команда `commands.saveRecovery(id, kind, hint, content)`.
4. В Rust функция `save_recovery`:
   - Вызывает `frontmatter::atomic_write_bytes` (запись во временный файл + fsync + замена целевого файла).
   - Сразу после этого вызывает `prune_quotas(&root)`.
   - Внутри `prune_quotas` вызывается `read_all_entries(root)`, которая:
     - Сканирует директорию `.amby/recovery/`.
     - **Читает с диска каждый найденный `.json` файл**.
     - **Парсит каждый файл через `serde_json`**.
     - **Считает FNV-1a хэш от содержимого каждого файла** для валидации целостности.
5. В результате: при наборе текста пользователем со скоростью 5–8 символов в секунду генерируются десятки параллельных IPC-запросов и дисковых транзакций. Диск перегружен I/O-операциями, очередь IPC переполняется, поток ввода начинает зависать.

#### Решение:

- **На фронтенде:** обернуть вызов `saveRecoveryDraft` в строгий дебаунс (1000–1500 мс) либо запускать его синхронно с таймером автосохранения.
- **В Rust:** убрать полный перечит и парсинг всех файлов recovery при каждом вызове `save_recovery`. Ограничение квот (`prune_quotas`) выполнять либо по таймеру (sweep), либо проверять размер и mtime файлов без их полного чтения и валидации хэшей.

### 2. Синхронный обход и парсинг всего документа на каждое движение курсора

- **Файлы:**
  - `src/components/workspace/tiptap/TiptapEditor.tsx` (строки 181–184)
  - `src/components/workspace/tiptap/markdown-selection.ts` (строки 85–118)
  - `src/components/workspace/editor/document-editor.tsx` (строки 278–280, 290–296)

#### Механизм возникновения бага:

1. В `TiptapEditor.tsx` хук `onSelectionUpdate` срабатывает на любое изменение выделения:
   ```typescript
   onSelectionUpdate: ({ editor }) => {
     onSelectionChangeRef.current?.(
       docSelectionToMarkdownSelection(editor.state.doc, valueRef.current, editor.state.selection),
     )
     ...
   }
   ```
2. Функция `docSelectionToMarkdownSelection` обращается к `docPositionToSourceOffset`:
   ```typescript
   const before = precedingWord(doc.textBetween(0, safePosition, "\n"), Number.MAX_SAFE_INTEGER)
   const after = followingWord(doc.textBetween(safePosition, doc.content.size, "\n"), 0)
   ```
3. Вызовы `doc.textBetween(0, safePosition)` и `doc.textBetween(safePosition, doc.content.size)` **синхронно рекурсивно обходят всё дерево ProseMirror от начала до самого конца документа** и аллоцируют полный текст документа в строки, после чего ищут слова регулярными выражениями.
4. Это происходит **на каждое нажатие стрелки клавиатуры, клик мыши или ввод символа**.
5. При этом в `document-editor.tsx` полученный результат `editorSelectionRef.current` используется **только в одном месте**:
   ```typescript
   const handleEditorViewModeChange = React.useCallback((mode: DocumentViewMode) => {
     setEditorSelection(editorSelectionRef.current)
     onViewModeChange?.(mode)
   }, [...])
   ```
   То есть 100% времени ресурсы CPU расходуются вхолостую на случай, если пользователь решит нажать кнопку переключения в Source mode.

#### Решение:

- Убрать вызов `docSelectionToMarkdownSelection` из `onSelectionUpdate`.
- Рассчитывать маппинг позиции курсора **лениво — только в момент клика по переключателю режимов** (`handleEditorViewModeChange`).

### 3. Непрерывная сериализация и запись Canvas при перетаскивании карточек

- **Файлы:**
  - `src/components/workspace/canvas/use-canvas-document.ts` (строки 56–63)
  - `src/components/workspace/orchestration/use-canvas-workspace.ts` (строки 88–102)

#### Механизм возникновения бага:

1. В `useCanvasDocument`:
   ```typescript
   React.useEffect(() => {
     if (!mounted.current) {
       mounted.current = true
       return
     }
     onChange(serializeCanvas(fromReactFlow(nodes, edges)))
   }, [nodes, edges])
   ```
2. Во время перетаскивания (drag) любого узла в `@xyflow/react` массив `nodes` обновляется **на каждый пиксель перемещения курсора мыши** (60–120 раз в секунду).
3. На каждый кадр:
   - Выполняется `serializeCanvas(fromReactFlow(nodes, edges))`.
   - Вызывается `handleCanvasSave(path, json)`.
   - Внутри `handleCanvasSave` вызывается `setOpenCanvases(...)`, что вызывает **полный перерендер компонента `WorkspaceOrchestration`** (всего рабочего стола).
   - Вызывается `saveRecoveryDraft` (дисковый I/O в Tauri Rust бэкенд на каждый пиксель перемещения!).

#### Решение:

- Сохранять состояние холста не в `useEffect([nodes, edges])`, а по событию завершения жеста перетаскивания: `onNodeDragStop` и `onSelectionDragStop`.
- Для текстовых изменений внутри карточек использовать дебаунс (например, 500–1000 мс).

### 4. Race Condition и утечка слушателей событий Tauri IPC

- **Файлы:**
  - `src/components/workspace/use-vault-data.ts` (строки 593–610, 623–665)
  - `src/components/workspace/settings-dialog.tsx` (строки 391–402)
  - `src/components/workspace/use-settings-store.ts` (строки 131–146)

#### Механизм возникновения бага:

1. Подписка оформлена через цепочку Promise:
   ```typescript
   let unlisten: (() => void) | undefined
   listen("event-name", handler).then((fn) => {
     unlisten = fn
   })
   return () => unlisten?.()
   ```
2. Если компонент размонтируется до того, как Promise от `listen()` разрешится (например, быстрое переключение между хранилищами, закрытие диалога настроек, remount вкладки), функция очистки эффекта вызывается тогда, когда `unlisten` ещё `undefined`.
3. Когда Promise позже разрешается, `unlisten = fn` выполняется, но отписка уже никогда не произойдёт.
4. В ядре Tauri остаётся висеть активный listener. При следующем открытии создаётся ещё один. Это приводит к дублированию событий (например, многократные параллельные запуски `refreshTree()` при одном изменении файла) и утечке памяти.

#### Решение:

Ввести безопасный шаблон с флагом отмены:

```typescript
let cancelled = false
let unlisten: (() => void) | undefined
listen("event-name", handler).then((dispose) => {
  if (cancelled) dispose()
  else unlisten = dispose
})
return () => {
  cancelled = true
  unlisten?.()
}
```

### 5. Отсутствие задержки на скрытие открепленных боковых панелей (Flickering)

- **Файлы:**
  - `src/components/workspace/workspace-orchestration.tsx` (строки 1620–1635, 1755–1770)
  - `src/components/workspace/use-sidebar-layout.ts` (строки 292–295, 355–357)

#### Механизм возникновения бага:

1. Когда панель откреплена (`!leftDockPinned`), она раскрывается как плавающий оверлей при наведении мыши на левый край экрана (полоска шириной 4px).
2. На контейнере оверлея установлены обработчики:
   ```tsx
   onMouseEnter={() => setSidebarHover("left", true)}
   onMouseLeave={() => setSidebarHover("left", false)}
   ```
3. При малейшем выходе курсора за пределы оверлея (например, пользователь вел курсор к кнопке или тексту заметки и случайно сдвинул мышь на 1 пиксель) `onMouseLeave` моментально выставляет `isLeftSidebarHover(false)`.
4. Панель мгновенно начинает схлопываться. Пользователь инстинктивно возвращает мышь назад — панель снова раскрывается.
5. Это вызывает сильное визуальное мерцание ("дёргание" интерфейса), спам анимаций Framer Motion и повторные ререндеры `WorkspaceOrchestration`.

#### Решение:

Добавить таймер задержки на закрытие (`hideDelay` 250–350 мс) с отменой при повторном `onMouseEnter`.

## 🟡 Архитектурные проблемы и оптимизации рендеринга

### 6. Монолитный рендеринг `WorkspaceOrchestration` при правке документа

- **Файлы:** `src/components/workspace/workspace-orchestration.tsx` (строки 249–257, 1027–1145)
- **Проблема:**
  Корневой компонент `WorkspaceOrchestration` (1828 строк) подписан на `openDocs`:
  ```typescript
  const openDocs = useDocStore((s) => s.openDocs)
  const unsavedFileIds = useDocStore((s) => s.unsavedFileIds)
  ```
  При любом наборе текста (через дебаунс Tiptap или каждый keystroke в SourceEditor) объект `openDocs` обновляется. Это триггерит полный ререндер всего рабочего пространства: пересоздаются вкладки `headerTabs`, опции пресетов, пересчитывается кэш `CachedDocumentEditor` и создаются десятки анонимных функций в `paneEditorProps`.
- **Оптимизация:**
  - Использовать точечные селекторы Zustand (например, подписать редактор только на `openDocs[activeFileId]`).
  - Вынести редактор и заголовок в изолированные подкомпоненты, чтобы ввод текста не вызывал ререндер родительского макета.

### 7. Неработающая мемоизация `TreeNode` в дереве файлов

- **Файлы:**
  - `src/components/workspace/tree/sidebar-tree.tsx` (строки 208–240)
  - `src/components/workspace/tree/tree-row.tsx` (строки 43–73)
- **Проблема:**
  Компонент `TreeNode` обёрнут в `React.memo`, однако `SidebarTree` при каждом своем рендере передаёт в каждую строку свежесозданные инлайн-функции:
  ```tsx
  onToggleOpen={() => toggleOpen(row.item.id)}
  onStartEdit={() => setEditingId(row.item.id)}
  onFinishEdit={(newName) => { ... }}
  ```
  Поверхностное сравнение пропсов (`shallow compare`) всегда возвращает `false`. В итоге при любом действии (например, вызове `setPtrDrag` на каждый тик движения мыши при drag-and-drop) перерисовываются абсолютно все видимые строки дерева. Кроме того, в каждой строке дерева прямо в DOM монтируются `ContextMenuContent` с субменю и диалоги прикрепления слоев.
- **Оптимизация:**
  - Передавать стабильные функции верхнего уровня, принимающие `id` аргументом (например, `onToggleOpen={handleToggleOpen}`).
  - Монтировать содержимое `ContextMenu` и диалогов лениво по факту открытия.

### 8. Отсутствие дебаунса ввода текста в `SourceEditor` (CodeMirror)

- **Файл:** `src/components/workspace/source-editor.tsx` (строки 207–212)
- **Проблема:**
  В `SourceEditor` вызов `onChangeRef.current(next)` происходит синхронно в `EditorView.updateListener` на каждое изменение документа без задержки. Это сразу же запускает цепочку: `patchDoc` -> обновление стора -> ререндер `WorkspaceOrchestration` -> `saveRecoveryDraft` (IPC) -> пересчёт счетчика слов.
- **Оптимизация:**
  Ввести дебаунс 150–200 мс на вызов `onChange` со сбросом (`flush`) по `blur` и `unmount` (по аналогии с тем, как это реализовано в `TiptapEditor`).

### 9. Layout Thrashing в `BlockHandles` (ручки блоков в Tiptap)

- **Файл:** `src/components/workspace/tiptap/BlockHandles.tsx` (строки 389–445)
- **Проблема:**
  При движении мыши по редактору в обработчике `pointermove` вызываются:
  ```typescript
  editorDom.querySelectorAll(".amby-column")
  // и внутри цикла для дочерних блоков:
  child.getBoundingClientRect()
  ```
  Вызовы `getBoundingClientRect()` во время движения мыши заставляют браузер принудительно выполнять синхронный перерасчёт стилей и геометрии DOM (Forced Synchronous Layout / Layout Thrashing), что приводит к дерганию прокрутки и микрозадержкам отклика курсора.
- **Оптимизация:**
  Кэшировать габариты колонок при скролле/ресайзе либо опираться на относительные координаты событий курсора.

### 10. Блокировка SQLite-мьютекса во время файловых операций на диске

- **Файл:** `src-tauri/src/commands/mutations.rs` (строки 388–435)
- **Проблема:**
  В команде `move_item` блокировка `let conn_guard = db.conn.lock().unwrap();` захватывается до:
  - перемещения файлов и каталогов на физическом диске (`move_item_impl`),
  - чтения и перезаписи wiki-ссылок по файлам хранилища (`apply_planned_wiki_rewrites`).
    Пока диск выполняет синхронный ввод-вывод, мьютекс базы данных удерживается. Если в этот момент пользователь печатает в строке поиска Quick Open или открывает заметку, чтение из SQLite зависает в ожидании разблокировки мьютекса.
- **Оптимизация:**
  Разделить логику: планирование под блокировкой -> дисковые операции без блокировки -> применение результатов в SQLite под короткой финальной блокировкой.

### 11. Повторное чтение файла с диска сразу после записи в `write_note`

### 12. Невиртуализированный `QuickOpenModal` при больших объемах заметок

- **Файл:** `src/components/workspace/quick-open-modal.tsx` (строки 44, 91–103)
- **Проблема:**
  В `QuickOpenModal` компонент `CommandList` рендерит весь массив `files` плоским списком. В хранилищах с 2000–5000 заметок создается несколько тысяч DOM-элементов `CommandItem`. Это приводит к заметной паузе (1–2 секунды) при нажатии `Cmd+O` и задержкам фильтрации при вводе названия заметки. Кроме того, в результатах отображается только `file.name`, из-за чего одноимённые заметки в разных папках невозможно различить.
- **Оптимизация:**
  - Ограничить отображаемый список первыми 50–100 результатами.
  - Добавить отображение относительного пути к файлу.

### 13. Рендеринг таблицы баз данных на каждый пиксель прокрутки

### 14. Перерисовка графа связей через React SVG

- **Файл:** `src/components/workspace/graph-tab-view.tsx` (строки 114–122)
- **Проблема:**

- **Оптимизация:**
  Использовать прямой рендеринг в HTML5 Canvas или напрямую мутировать SVG-атрибуты через refs в обход React VDOM.
