# План исправлений производительности и багов для Codex Luna

Дата: 9 сентября 2026 года. Основание: [AUDIT_PERFORMANCE_AND_BUGS.md](AUDIT_PERFORMANCE_AND_BUGS.md), сверенный с текущим рабочим деревом ветки `dev`.

Это план реализации, а не отчёт об исправленных ошибках. Все 14 пунктов аудита включены. Задания ниже рассчитаны на последовательное выполнение: одна завершённая задача, её проверки и запись результата — затем следующая. Исправления приложения при подготовке плана не выполнялись.

## Что уточнено после чтения кода

- **№ 1:** recovery вызывается на каждую публикацию текста из редактора, а Rust перечитывает записи при проверке квот. Это подтверждённый дорогой путь; переполнение IPC, конкретные задержки и степень влияния на ввод ещё нужно измерить. У Tiptap уже есть собственная задержка публикации текста.
- **№ 2:** полный текст документа действительно извлекается при преобразовании выделения. Перенос вычисления на смену режима должен учитывать ещё не опубликованную правку редактора.
- **№ 3:** основной Canvas-файл уже сохраняется через `AutosaveCoordinator` с задержкой 500 мс. На изменениях `nodes`/`edges` остаются сериализация, повторная валидация JSON, обновление состояния рабочего пространства и recovery IPC.
- **№ 4–5:** встречаются небезопасные асинхронные подписки и мгновенное снятие hover с откреплённой панели. Исправлять нужно конкретные оставшиеся места, сохраняя уже добавленные защиты и поведение панелей.
- **№ 6:** подписка `WorkspaceOrchestration` на весь `openDocs` осталась, однако `headerTabs`, props панелей и скрытые редакторы уже частично мемоизированы. Их нельзя считать заново отрисовываемыми без проверки профайлером.
- **№ 7:** дерево уже виртуализировано. У `TreeNode` есть собственный comparator, который не сравнивает перечисленные в аудите inline callbacks. Они сами по себе не объясняют каждый ререндер. Общие drag/selection props и неполный учёт изменившихся обработчиков требуют отдельной проверки.
- **№ 8–9:** синхронная публикация SourceEditor и измерения геометрии блоков требуют работы, но сама по себе операция `getBoundingClientRect()` ещё не доказывает forced reflow. Сначала проверить имеющееся ограничение частоты и реальные layout-события.
- **№ 10–11:** длительная блокировка вокруг перемещения и повторное чтение Markdown после записи подтверждаются. `db.conn` защищает также активное хранилище и его поколение; просто удалить блокировку небезопасно.
- **№ 12–13:** Quick Open монтирует все файлы, таблица обновляет React state на каждом scroll event. Таблица уже использует виртуальный диапазон строк.
- **№ 14:** граф уже ограничивает обновления через `requestAnimationFrame`, но внутри вызывает `setTick`. Первое исправление — обновлять координаты SVG через refs; перенос всего графа на Canvas не обязателен.

Числа FPS и задержек из аудита не считать измеренной исходной линией. Повторить измерения на одном тестовом хранилище и одном компьютере.

## Общие правила для Luna

1. Прочитай `AGENTS.md`, `docs/engineering.md`, `docs/vault-format.md` и `docs/markdown-compatibility.md`. Перед каждой задачей сверяй фактический код: номера строк аудита могут устареть.
2. Рабочее дерево уже содержит накопленные правки в Rust, панелях, дереве, настройках и watcher. Изучи `git status --short` и diff затрагиваемых файлов. Сохрани существующие изменения; не выполняй `reset`, `clean`, автоматический stash или массовое форматирование. Начинай работу от `dev`; если понадобится новая ветка, используй префикс `codex/`.
3. Не меняй версию, не делай commit/push, tag или release без отдельного запроса. В каждой завершённой задаче добавляй только подтверждённый результат в `updates.md` под `## Следующая версия`; сохраняй накопленные записи.
4. Все операции с данными проходят через существующую границу storage/IPC. Не добавляй прямой доступ frontend к файловой системе, вторую очередь автосохранения или второй источник состояния документа.
5. Сохрани atomic writes, проверку revision, snapshot перед заменой, восстановление из trash, неизвестный Markdown/YAML/Canvas, BOM и окончания строк. SQLite остаётся восстанавливаемым индексом. Этот план не требует миграции файлов пользователя.
6. Любая отложенная операция имеет владельца: хранилище, generation, тип и ID документа, текущую версию буфера. Старый save, таймер или cleanup не может очистить/записать более новый буфер либо новое хранилище.
7. Новые видимые строки добавляй во все языки `src/locales/resources.ts`, статические стили — в `src/themes/`. Форматируй только затронутые файлы.
8. Используй существующие Vitest-тесты и `tests/component/` с локальным `happy-dom`, где это подходит. Тесты DOM без настоящего layout не заменяют ручную проверку браузера и Tauri.
9. После каждой задачи запускай целевые тесты и `npm run build`. Перед передачей реализации на ревью запускай `npm run verify`. После Rust-изменений обязателен `npm run rust:test`; для backend-задач — строгий Clippy. При изменении IPC регенерируй bindings тестом Rust, никогда вручную.
10. Если обязательная проверка падает, укажи точную команду и причину, отдели исходную проблему от внесённой регрессии. Не объявляй задачу проверенной и не исправляй несвязанные файлы ради зелёного статуса.

## 01. Устранить гонки подписок Tauri

**Файлы:** `src/components/workspace/use-vault-data.ts`, `settings-dialog.tsx`, `use-settings-store.ts`, `header-tabs.tsx`, `vault/empty-state-header.tsx`; остальные места, найденные через `rg` по `listen`, `onCloseRequested`, `onResized`, `unlisten` и `dispose`.

**Действия:**

1. Разделить подписки React effect и подписки с временем жизни всего приложения. Для каждой установить одного владельца cleanup.
2. В оставшихся небезопасных эффектах установить флаг завершения; если регистрация разрешилась после cleanup, немедленно вызвать возвращённую отписку. Cleanup сделать идемпотентным.
3. Не выполнять обработчик после завершения эффекта или смены generation. Сохранить существующие проверки хранилища и отмену асинхронной загрузки после `await`.
4. Обработать rejection регистрации, чтобы не оставались необработанные Promise. При повторении одного шаблона выделить небольшой общий helper, не создавая отдельную событийную систему.

**Проверки:** управляемый Promise регистрации: resolve до cleanup, после cleanup, reject; повторный mount/cleanup в StrictMode; событие во время отмены. В Tauri многократно открыть/закрыть настройки и сменить хранилище, затем изменить один файл.

**Готово, когда:** одна подписка получает одно событие, поздно зарегистрированный listener снимается, устаревшая обработка не обновляет новое хранилище. `refreshTree` может вызываться из разных законных источников; проверять именно отсутствие дубликатов одной подписки.

## 02. Ограничить recovery-записи с сохранением последних правок

**Файлы:** `src/lib/recovery-drafts.ts`, `src/lib/recovery-drafts.test.ts`, `file-actions/use-markdown-autosave.ts`, `orchestration/use-canvas-workspace.ts`, `autosave/autosave-lifecycle.ts`, при необходимости `src-tauri/src/commands/history.rs` и граница IPC.

**Действия:**

1. Разделить постановку свежего снимка в память и завершённую durable-запись. Не менять незаметно смысл `await saveRecoveryDraft`: восстановление/перенос, которым нужна завершённая запись, должны использовать явный немедленный save/flush.
2. Ввести общий для recovery механизм объединения снимков по `(vault, generation, kind, id)`. На ключ допускается одна запись в работе и только последний ожидающий снимок. Не заводить таймер отдельно в каждом редакторе.
3. Стартовая политика для проверки: первая правка нового dirty-периода записывается сразу; дальнейшие объединяются с задержкой 500 мс и `maxWait` 1 000 мс. `maxWait` ограничивает ожидание запуска, а не длительность диска. Непрерывный ввод не должен откладывать recovery бесконечно. Финальные значения подтвердить замерами и описать окно возможной потери последних правок при аварии.
4. Согласовать успешный autosave, recovery save/delete и версии буфера. Поздний таймер не воссоздаёт уже ненужный черновик; завершение старого save/delete не удаляет новый. Ошибка основной записи сохраняет recovery и dirty-state. Ошибку recovery нельзя считать доказательством сохранения данных.
5. Flush при штатном закрытии, смене хранилища, освобождении буфера и переносе выполнять до потери контекста документа. При конфликте основной autosave остаётся на паузе, но локальный recovery продолжает обновляться. Не полагаться на асинхронный cleanup React или `beforeunload` как гарантию завершения IPC.
6. Охватить queued и in-flight операции при remap/delete. Проверить совпадающий note ID в разных vault и несколько окон. Сейчас recovery-команды используют активное хранилище, а `save_recovery` отдельно получает root и generation: обеспечить атомарный снимок контекста и отказ для устаревшего запроса на границе Rust. Если нужны новые IPC-параметры, обновить типы и регенерировать bindings.
7. Распространить поведение на browser fallback, не ломая восстановление старых localStorage-черновиков. Обновить контракт recovery в `docs/vault-format.md` фактической политикой периодичности и flush.

**Проверки:** расширить `recovery-drafts.test.ts`, `autosave-coordinator.test.ts`, `autosave-lifecycle.test.ts`, `autosave-integration-harness.test.ts`. Fake timers и отложенные Promise: длительный непрерывный ввод, два документа, медленная запись, ошибка, новый ввод во время save/delete, flush без blur, remap, конфликт, смена generation, два окна. Проверить восстановление после аварийного завершения на временном vault в Tauri.

**Готово, когда:** recovery IPC не следует за каждым символом/кадром, очередь ограничена, последняя версия восстанавливается в пределах описанного окна, черновик не исчезает до успешного файлового save. После изменения IPC — native build и проверки bindings.

## 03. Убрать полный перечит recovery при проверке квот

**Файлы:** `src-tauri/src/recovery.rs`, состояние recovery в backend, `src-tauri/src/vault_context.rs`, `src-tauri/src/commands/history.rs`, `docs/vault-format.md`.

**Действия:**

1. Сохранить существующие лимиты: 5 МБ содержимого записи, 50 МБ совокупного содержимого, 100 записей, TTL 14 дней. Сейчас квота считает `content.len()`, а порядок удаления опирается на `saved_at_ms`: замена на размер JSON и mtime изменит семантику.
2. Предпочтительный вариант: после startup/activation sweep построить восстанавливаемый каталог метаданных в памяти — ключ, путь, время записи, размер содержимого. Обновлять его после успешных save/delete/remap; не перечитывать и не хешировать все тела на каждом save.
3. Согласовать каталог и pruning отдельной синхронизацией recovery на хранилище. Параллельный sweep не должен удалить свежую версию на основании старых метаданных. Не удерживать глобальный SQLite lock ради квот.
4. Сохранить полную валидацию версии, JSON, хеша и TTL при чтении/восстановлении и при startup sweep. При потере каталога безопасно восстановить его; не отключать квоты и не переносить их на неопределённое «потом».
5. Оставить atomic writer и обработку ошибок файловой системы. Не вводить новый долговечный формат каталога ради этой оптимизации.

**Проверки:** реальные граничные значения либо инъекция лимитов в существующий алгоритм: превышение количества/объёма, рост и уменьшение одного черновика, TTL, повреждение JSON/хеша, ошибка удаления/записи, параллельные сохранения и восстановление каталога. Замерить число прочитанных тел после прогрева.

**Готово, когда:** обычное сохранение одного черновика не читает тела остальных, квоты и восстановление сохраняют контракт. Выполнены Rust tests, Clippy и build.

## 04. Вычислять выделение только при смене режима

**Файлы:** `tiptap/TiptapEditor.tsx`, `tiptap/constants.ts`, `tiptap/markdown-selection.ts`, `tiptap/editor-serialization-lifecycle.ts`, `editor/document-editor.tsx`, `source-editor.tsx`.

**Действия:**

1. Установить все места вызова `docSelectionToMarkdownSelection` и все потребители выделения. На событиях движения курсора хранить только дешёвую позицию редактора; убрать преобразование всего документа из горячих обработчиков, включая update, если оно там дублируется.
2. Расширить существующий `EditorHandle` в `tiptap/constants.ts` методом вроде `getMarkdownSelection()`: Tiptap сначала делает `flushSerialize(editor)`, затем возвращает выделение по актуальному `valueRef`; Source возвращает текущий CodeMirror range. При необходимости вернуть snapshot текста вместе с выделением. Не создавать глобальный ref «текущего редактора» — вкладки и split имеют отдельных владельцев.
3. При разрешённой смене режима сначала синхронно опубликовать незавершённую сериализацию, затем вычислить выделение по тому же состоянию и передать его новому режиму. Не вычислять offsets нового ProseMirror-документа по устаревшему `value`.
4. Сохранить Source-only guard, текстовые anchors, scroll и историю. Переход Source → Live также получает актуальные текст/позицию.

**Проверки:** счётчик mapper: движения курсора не запускают полный mapping, переход режима запускает. Большая заметка, выделение диапазона, повторяющиеся слова, кириллица/emoji, начало/конец, CRLF, таблицы, колонки и opaque-блоки; быстрый ввод с немедленным переходом режима. Запустить `tiptap/markdown.test.ts` и существующие compatibility/columns-тесты.

**Готово, когда:** переход не теряет последнюю правку и не меняет Markdown-байты, а курсорная навигация больше не вызывает этот обход документа.

## 05. Сохранять Canvas по содержательным изменениям

**Файлы:** `canvas/use-canvas-document.ts`, `canvas/canvas-editor.tsx`, `canvas/canvas-nodes.tsx`, `canvas/canvas-edges.tsx`, `orchestration/use-canvas-workspace.ts`, `src/lib/canvas-format.ts` и его тесты.

**Действия:**

1. Разделить визуальные обновления React Flow и публикацию сохраняемого документа. Выделение, фокус, измерение DOM и перемещение viewport сами по себе не должны сохранять JSON.

**Готово, когда:** тик симуляции не вызывает React commit, координаты и управление корректны, измеренные длительности кадров улучшились. Если после этого узкое место — сама d3-симуляция или число SVG-элементов, зафиксировать профиль и выделить перенос на Canvas в отдельную последующую задачу; не объявлять его необходимым заранее.

## 17. Выполнить общую проверку и передать результат

1. Повторить сценарии задачи 00 на тех же данных и окружении. В `docs/performance-verification.md` показать фактические значения до/после по всем 14 пунктам, включая закрытые без изменения кода с доказательством отсутствия проблемы. Не приписывать одной оптимизации весь общий выигрыш.
2. Пройти общий сценарий: печать → быстрый переход режима → split/смена вкладки → Canvas drag/resize/text → move/rename → внешний конфликт → штатное закрытие/смена vault → восстановление. Отдельно аварийно завершить только тестовый экземпляр и проверить recovery. Проверить Linux/Windows/macOS-специфику в доступных окружениях; отсутствующие платформы явно отметить.
3. Запустить `npm run verify` и `npm run build` на окончательном diff. По текущему `package.json` verify запускает `verify:full`: version check, TypeScript, ESLint, Vitest, format check, knip, Rustfmt, strict Clippy, Rust tests и bindings check. Не подменять его `verify:fast`; описания команд в старых документах могут отставать.
4. Для накопленных desktop/IPC/backend-изменений выполнить `npm run tauri build` либо явно записать конкретную причину невозможности native build. Использовать существующие `test:storage:live`/`test:native:ui`, если их сценарии покрывают изменённые контракты. Browser fallback отдельно проверить через `npm run dev`.
5. Проверить итоговый diff: нет ручных изменений bindings, generated bundles, временных хранилищ, секретов, потери накопленных правок и незапрошенного повышения версии. Обновить `updates.md` только фактически достигнутыми результатами.
6. Передать краткий отчёт: закрытые пункты, измерения, файлы, выполненные команды, непрошедшие проверки и оставшиеся ограничения. Не помечать весь аудит закрытым, пока есть непроверенные сценарии сохранности данных.
