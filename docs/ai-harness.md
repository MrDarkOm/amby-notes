## 1. Что представляет собой harness

Harness — среда исполнения вокруг модели: каталог возможностей, сбор разрешённого
контекста, выполнение операций, права, журнал, проверка результата, восстановление,
память и навыки. Модель предлагает последовательность действий. Приложение
проверяет и выполняет каждое из них, затем возвращает фактический результат.

Агент понимает приложение через четыре источника:

1. Версионированные описания сущностей, форматов и связей между ними.
2. Каталог действительно доступных команд с ограничениями текущего модуля.
3. Состояние разрешённой части пространства, полученное через read/query API.
4. Результаты собственных действий и проверенные навыки решения задач.

Чтение всего исходного кода приложения при каждом запросе не требуется. Документация
API поставляется с приложением; изменения API обновляют catalog version и проверки
совместимости навыков. Доступ к произвольным внутренним функциям не предоставляется.

### 1.1 Владельцы ответственности

| Компонент                | Ответственность                                                                                    |
| ------------------------ | -------------------------------------------------------------------------------------------------- |
| UI и существующие stores | Запрос пользователя, выбор области, dirty buffers, preview, история и разрешение конфликтов        |
| Runtime в Rust           | Задания, budgets, provider transport, последовательность model/tool calls, остановка и checkpoints |
| Registry и policy в Rust | Схемы, доступность модулей, действие actor, права на все затронутые ресурсы                        |
| Executor в Rust          | Preconditions, сериализация, journal intent, вызов общей domain operation, receipt                 |
| Domain services          | Lossless изменения заметок, баз, досок, настроек; одинаковые правила для UI и агента               |
| Journal/recovery         | Долговечная история, before/after evidence, повторное распознавание результата, undo               |
| Skill/learning services  | Выбор закреплённых версий, предложения уроков, испытания, управление версиями                      |
| Plugin host              | Изоляция кода и SDK; каждое обращение к данным через проверенный broker                            |

Legacy UI IPC может существовать во время перехода, но не доступен модели и
недоверенному плагину как обход executor. Привилегированность вызова определяется
host-сессией/каналом, а не полем `actor` из JSON. H-70 проверяет обходы через raw
Tauri invoke, asset protocol, Worker globals и прямой доступ к сети.

## 2. Режимы пользователя

| Режим       | Данные пространства                                  | Изменения                                                              |
| ----------- | ---------------------------------------------------- | ---------------------------------------------------------------------- |
| Обсудить    | Только предоставленный контекст и разрешённые чтения | Запрещены; журнал и checkpoint беседы записывает host                  |
| Подготовить | Чтения для составления точного плана                 | Служебный preview; заметки, настройки и активные плагины не изменяются |
| Выполнить   | По выданной grant                                    | Разрешённые действия с журналом и предусмотренным undo                 |

Пользователь выбирает область и режим один раз для задания. Обычные операции
внутри этого разрешения не требуют повторного подтверждения на каждом шаге.
Дополнительный выбор нужен при расширении области, новом внешнем эффекте,
изменении разрешений плагина или обнаружении конфликта. Модель может предложить
расширение, но не нажать подтверждение и не выдать себе grant.

`Подготовить` сохраняет описание операций, значения, ссылки и ревизии. Для связки
«создать заметку → добавить её на доску» используются типизированные ссылки на
результат предшествующего шага; ID резервирует host. Детерминированные defaults
фиксируются до preview. Если результат шага требует нового творческого решения
модели, это следующая версия плана, а не незаметная часть уже подтверждённой.

Разрешение на точный план связано с digest плана, исходными ревизиями,
эффектами, grant revision и сроком действия. Существенное изменение любого из
них делает подтверждение устаревшим. Режим непосредственного выполнения
использует действующую grant; наличие preview не обязательно для каждого шага.

## 3. Сущности и идентификаторы

| Сущность                | Идентификатор и назначение                                                                    |
| ----------------------- | --------------------------------------------------------------------------------------------- |
| Workspace               | Opaque `workspaceId` из host registry; canonical root и binding revision хранятся отдельно    |
| Grant                   | `grantId` + монотонная revision; immutable история решений пользователя                       |
| Submission              | Выданный host `submissionId`; transport retry повторяет его, новая просьба получает новый     |
| Run                     | `runId`; один workspace либо только global settings                                           |
| Step                    | `stepId`; логический шаг плана, может иметь несколько попыток                                 |
| Operation               | `operationId`; единственное намерение применить конкретные аргументы к конкретным ресурсам    |
| Attempt                 | `attemptId`; повтор transport/исполнения той же operation без нового намерения                |
| Resource                | Тип + namespace + stable object ID/проверенный locator; строка пути сама по себе не authority |
| Receipt                 | `receiptId`; проверенный результат operation с revisions и outcome                            |
| Skill/proposal/artifact | Stable ID + immutable content digest; новая редакция получает новую revision                  |

Нельзя использовать provider tool-call ID как единственный operation ID:
провайдер может повторить ответ с новым ID. Runtime хранит соответствие tool call
конкретному step/operation. Повтор семантически похожего действия моделью
дополнительно обнаруживает loop detector; это не доказательство idempotency.

## 4. Контракт Action

### 4.1 Дескриптор

| Поле                            | Требование                                                                           |
| ------------------------------- | ------------------------------------------------------------------------------------ |
| `actionId`, `schemaVersion`     | Стабильное имя и версия схемы; неизвестная версия не исполняется                     |
| `capabilityVersion`, `moduleId` | Реальная версия domain adapter и условие доступности                                 |
| `inputSchema`, `outputSchema`   | Закрытые типы, пределы размера/глубины; неизвестные аргументы отклоняются            |
| `effectKind`                    | `read`, `durableMutation`, `transient`, `external`; смешанные эффекты перечисляются  |
| `resourceResolver`              | Host определяет read/write/effect closure, включая побочные изменения                |
| `preconditions`                 | Revisions, ожидаемое отсутствие, schema/module generation, editor checkpoint         |
| `preview`, `verify`             | Проверяемый preview и постусловия; не произвольный текст модели                      |
| `undoClass`                     | `snapshot`, `fieldPatch`, `inverseDomain`, `none`, `manualExternal`                  |
| `limits`                        | Размер входа/ответа, число объектов, срок действия, затратность и допустимые retries |

Дескриптор не содержит произвольный обработчик от навыка. Плагин объявляет
расширение каталога через SDK, но host связывает его с sandbox и правами плагина;
оно не становится привилегированной командой ядра.

### 4.2 Запрос

Runtime добавляет к валидированным аргументам `runId`, `stepId`, `operationId`,
`attemptId`, `grantId/revision`, `workspaceBindingRevision`, `generation`,
`catalogVersion`, expected revisions и approved plan reference, если требуется.
Эти поля не могут быть переопределены моделью.

Digest операции включает action/schema version, нормализованные типизированные
аргументы, ссылки на input blobs, preconditions, workspace и grant revision.
Нормализация не меняет значимые байты содержимого, окончания строк, порядок
списков или числа. Алгоритм канонического представления версионируется в H-01.
Тот же operation ID с другим digest возвращает `idempotencyConflict`.

### 4.3 Receipt

Receipt содержит фактические созданные IDs, resource references, before/after
revisions, время, domain journal reference, verification results, undo manifest
reference, cache/index status и безопасные диагностические коды.

| `outcome`             | Значение                                                                           |
| --------------------- | ---------------------------------------------------------------------------------- |
| `succeeded`           | Durable постусловия проверены; состояние cache отдельно `ready`/`pending`/`failed` |
| `noChange`            | Preconditions совпали, изменений не требовалось; новые версии данных не созданы    |
| `rejected`            | Policy/schema/preconditions остановили действие до публикации                      |
| `failedBeforePublish` | Операционная ошибка, подтверждено отсутствие опубликованных эффектов               |
| `partial`             | Известны применённые и неприменённые части; есть recovery plan                     |
| `outcomeUnknown`      | Нельзя доказать, какие эффекты произошли; повтор запрещён до reconciliation        |

Обновлённый React state или текст «готово» от модели не считается receipt.
Ошибка SQLite после успешной записи не запускает повтор записи исходного файла.
Run не сообщает о выполненном пользовательском результате, пока нужные ему
постусловия не проверены. Ожидающая индексация обозначается отдельно.

### 4.4 Ошибки и дальнейшее действие

| Код                                          | Реакция runtime                                                                 |
| -------------------------------------------- | ------------------------------------------------------------------------------- |
| `permissionDenied`, `scopeChanged`           | Остановить зависимые шаги; получить пользовательское решение или сократить план |
| `moduleUnavailable`, `unsupportedCapability` | Обновить каталог; не подменять действие raw write                               |
| `validationFailed`                           | Безопасная диагностика; ограниченная корректировка аргументов                   |
| `revisionConflict`, `dirtyBufferConflict`    | Новый preview либо пользовательское разрешение конфликта                        |
| `journalUnavailable`, `quotaExceeded`        | Приостановить доступ агента к новым эффектам/данным до восстановления журнала   |
| `idempotencyConflict`                        | Ошибка runtime/protocol; автоматическая замена operation ID запрещена           |
| `outcomeUnknown`                             | Перейти в recovery; не повторять operation вслепую                              |
| `cancelled`                                  | Не запускать следующие действия; сверить уже начатую публикацию                 |

## 5. Grant и область доступа

Grant связывает доверенное решение пользователя со следующими ограничениями:

- workspace identity, binding revision, текущая generation;
- отдельные read/write roots и object capabilities;
- allowlist действий и settings keys с указанием global/workspace;
- доступ к журналу, skill/memory namespaces и конкретным plugin projects;
- provider profile, допустимые категории отправляемых данных;
- срок действия, budgets, approval rules, режим задания.

### 5.1 Проверка области

Policy вызывается перед чтением, перед раскрытием результата, перед каждым
provider request и непосредственно перед публикацией. Работа проверяется и
при resume, replay UI events, undo и plugin callback. UI фильтр не заменяет
backend проверку. Cache key включает scope revision и resource revision.

В первом контракте write-доступ к существующему объекту требует read-доступа:
preview, verification и undo должны видеть его исходное состояние. Capability
создания нового объекта задаётся на родителя, включает проверку отсутствия и
не даёт читать соседние файлы. Scope membership определяется по canonical
identity; путь после rename/move проверяется заново.

Поиск фильтрует объекты до snippets, ranking, totals, pagination и aggregation.
Relation/rollup/transclusion, full-text index и embedding retrieval подчиняются
той же области. Неизвестный или недоступный объект имеет одинаковый внешний
ответ `notAccessible`; diagnostic log не раскрывается агенту без прав.

### 5.2 Логические права и физические файлы

Пользователь разрешает изменить свойство заметки, а backend может обновить
общий `.amby/properties.json`. Разрешение на заметку даёт domain adapter право
точечно изменить её раздел sidecar; чтение/запись соседних записей агентом
запрещены. Полный файл участвует во внутреннем CAS/backup, но не выдаётся модели.
Undo такого действия применяет inverse к разрешённым полям и сохраняет
последующие изменения соседних записей.

Аналогично settings patch меняет конкретный ключ, а не даёт доступ ко всему
`settings.json`. Право менять строку базы не разрешает менять schema/manifest
базы. Для изменения shared schema требуется отдельная capability на всю схему.
Физические lock sets могут быть шире логических grant; domain adapter не
использует это как право на другие семантические изменения.

### 5.3 Полный набор эффектов

Rename, move, database type change, удаление bundle и refactor рассчитывают
closure до записи: источники, назначения, вложения, связанные metadata и
изменяемые ссылки. Если closure выходит за grant, операция не начинается.
Ответ не показывает имён недоступных объектов. Host UI может запросить более
широкую область у пользователя, не передавая её содержимое модели заранее.

Прочитанная заметка, web-страница, текст ошибки, skill или сгенерированный plugin
не могут задавать новые права. Результаты инструментов помечаются как данные.
Длинные выдержки из заметок не вставляются в system instruction.

## 6. Исполнение и координация редактора

### 6.1 Последовательность mutation

1. Проверить schema, grant, module, limits; вычислить effect closure.
2. Получить editor barriers без удержания filesystem/settings locks.
3. Завершить согласованные autosaves; dirty-конфликт требует решения пользователя.
4. Взять locks в стабильном порядке, повторно проверить scope/revisions/барьеры.
5. Сохранить snapshots, inverse manifest и durable prepared intent.
6. Применить общую domain operation с атомарной публикацией отдельных файлов.
7. Перечитать durable состояние, записать receipt и verification.
8. Освободить locks/barriers, обновить stores/index и доставить события UI.

Чистые буферы согласуются автоматически. При dirty-состоянии безопасный вариант
по умолчанию — пауза с выбором «сохранить мои правки и пересчитать», «показать
разницу» или «пропустить действие». Отбрасывание правок не подразумевается.
Если пользователь заранее выбрал автоматическое сохранение перед агентом,
оно использует обычный coordinator и явно отражается в timeline.

Snapshot для undo агентного шага снимается после сохранения пользовательских
правок. Undo возвращает именно это состояние. Несохранённые recovery drafts
не подменяются snapshot агента и не удаляются по его успешному ответу.

### 6.2 Барьер между окнами

Host знает зарегистрированные окна и открытые ими документы. Lease содержит
window/session ID, document identity, vault generation и checkpoint. Подтверждение
барьера от одного окна не покрывает остальные. Во время короткой publication
редактор блокирует запись соответствующего документа и отменяет stale saves;
новый пользовательский ввод не теряется и не публикуется поверх результата.

Закрытие/зависание окна или истечение lease не трактуется как согласие потерять
buffer. Сначала сверяются recovery drafts и состояние окна. Невозможность
доказать безопасную координацию даёт `dirtyBufferConflict`/`needsRecovery`.
При полностью закрытом документе domain action работает без монтирования UI.

### 6.3 Locks и границы гарантий

Порядок всех domain locks: global settings/module namespace, workspace ID,
канонический resource key. Общий lock покрывает файл, даже если два действия
меняют разные логические ключи. Existing mutation gate в Rust включается в эту
иерархию; переход не создаёт независимую очередь, обходящую старую.

Блокировка append журнала кратковременна; recovery reader не держит её, ожидая
domain lock. Ожидание пользователя/модели и получение editor barrier никогда
не происходят под lock записи. Несколько процессов Amby должны использовать
подтверждённую межпроцессную координацию либо отклонять второго writer.

Внешние программы не обязаны соблюдать locks Amby. Повторная проверка revisions
у публикации снижает риск гонки, но не обещает filesystem compare-and-swap
против произвольного внешнего writer. История и явные конфликты обязательны.

## 7. Runtime и контекст

Основные состояния run: `queued`, `running`, `waitingForUser`, `pausedConflict`,
`needsRecovery`, `succeeded`, `failed`, `cancelled`. Undo имеет отдельное состояние.
После перезапуска восстановленные незавершённые задания ожидают продолжения
пользователем; replay не запускает новые model calls автоматически.

Каждый provider request фиксирует profile/model, версии capabilities, references
контекста, budgets и request ID. Credentials доступны только transport. Tool call
исполняется после получения и валидации полного JSON; streaming fragments не
запускают частичные mutations. Несколько tool calls в ответе — не разрешение
исполнять зависимые записи параллельно.

Context item имеет источник, resource revision, scope provenance, видимость,
диапазон/chunk и признак truncation. Обобщение диалога сохраняет требования
пользователя, открытые вопросы, operation/receipt references, pending conflicts
и границы прав. Сам summary не является источником права или доказательством
успеха. Источники и их revisions перепроверяются при следующем действии.

При сужении grant runtime прекращает запросы и пересобирает контекст без
запрещённых источников, включая summaries, memory и screenshots. Уже отправленные
провайдеру данные нельзя отозвать этим механизмом; UI не обещает их удаление.
Старый provider conversation/cache handle не переиспользуется. Fallback на другой
provider разрешён лишь действующим правилом пользователя о передаче данных.

Budget defaults из плана — стартовые продуктовые ограничения, не benchmark.
Считаются отдельно model calls, tokens, tools, активное время, retries и learning.
Provider usage `unknown` не равен нулю; при неизвестной стоимости жёсткими остаются
лимиты вызовов/токенов/времени. Повтор одной ошибки ограничен; ожидание пользователя
не расходует лимит активного времени, но grant может истечь.

## 8. Undo, остановка и внешние эффекты

Undo запускается как новая operation с текущими правами, inverse manifest и
проверкой after revisions. Task undo — граф обратных зависимостей, а не только
обратный порядок времени. Новая пользовательская ссылка или строка, зависящая
от созданного объекта, блокирует опасное удаление этого объекта.

Для file snapshot требуется совпадение послеоперационных bytes. Для field patch
проверяется presence/value изменённых ключей, версия схемы и семантические
зависимости; соседние ключи сохраняются. Несогласованный набор полей не
откатывается частями под видом полного успеха. Повтор undo распознаётся по ID.

Возврат отдельных шагов без остальных разрешён только после проверки dependency
closure. UI показывает `available`, `conflict`, `partial`, `unavailable` и причину.
Redo — новое выполнение исходного намерения с новым preview/preconditions,
а не повтор старого сообщения модели или слепая публикация after snapshot.

В текущем baseline `deleteItem` использует системную корзину, `archiveItem` —
`.amby/trash/`. В обычный автономный набор входит `item.archive` с проверяемым
restore. `item.systemTrash` имеет `manualExternal` и по умолчанию
`requiresUserInteraction`; его нельзя выдавать за гарантированно обратимую
операцию агента. Просьба именно о системной корзине не подменяется архивированием.
Постоянный purge истории/архива не входит в обычную grant.

Удаление созданных агентом объектов при undo также использует внутренний архив
с manifest восстановления. Архивирование слоя должно иметь собственную domain
операцию: текущий `deleteLayer` нельзя переименовать в безопасный archive adapter.

Stop запрещает следующие шаги. Если atomic publication уже началась, runtime
сначала классифицирует её результат и записывает receipt. Stop не означает undo.
Отзыв grant запрещает новые содержательные записи, включая компенсацию; host
может закончить аудит и read-only reconciliation начатой операции. Для применения
recovery к данным после отзыва нужно текущее разрешение пользователя.

## 9. Навыки, память и обучение

### 9.1 Контракт навыка

| Поле revision                        | Смысл                                                                       |
| ------------------------------------ | --------------------------------------------------------------------------- |
| ID, revision digest, parent digest   | Неизменяемая версия и lineage                                               |
| title, description, trigger examples | Когда навык полезен; не глобальная инструкция                               |
| owner, origin, namespace             | Пользовательский, встроенный или agent-owned; область происхождения         |
| required actions/schema versions     | Проверка совместимости с текущим каталогом                                  |
| applicability/preconditions          | Когда процедура применима и когда следует отказаться                        |
| procedure/resources                  | Текстовая процедура, примеры, scoped references; executable assets отдельно |
| expected outcomes/verification       | Проверки результата; критерии приёмки контролирует host                     |
| evidence/evaluation refs             | Задания, из которых получен урок, и отчёты испытаний                        |
| status                               | `draft`, `proposed`, `verified`, `active`, `disabled`, `archived`           |

При поиске сначала доступны краткие карточки разрешённых навыков; полное
содержимое загружается по необходимости. Задание закрепляет конкретный digest.
Активация новой версии не меняет уже выполняющееся задание. Security revoke
может остановить его независимо от закрепления.

Навык описывает способ работы, но не выдаёт grant и не увеличивает budget.
Раздел «как запускать скрипт» в импортированном SKILL-файле не делает script
исполняемым. Исполняемые расширения проходят plugin lifecycle и sandbox.
Пользовательский/pinned навык не переписывается автоматически.

### 9.2 Цикл обучения

1. После завершения задания собрать scoped evidence: исход, исправления
   пользователя, повторяющиеся ошибки, расход и проверенные receipts.
2. Решить, есть ли переносимый урок; отсутствие полезного урока — штатный исход.
3. Создать proposal: целевая base revision, текстовый diff, причина, provenance,
   необходимые capabilities, тестовые задачи и риски.
4. Проверить формат, scope, секреты, конфликт с исходным навыком и права владельца.
5. Прогнать baseline/candidate на свежих изолированных fixtures; holdout и
   критерии не доступны candidate для изменения. Не переигрывать реальные actions.
6. Сохранить report, связывающий точные digests candidate, corpus, harness и
   model configuration. Результат не переносится на изменившиеся bytes.
7. В режиме `propose` показать diff и доказательства пользователю. В явно
   включённом `autoVerified` активировать только agent-owned text-only версию
   без новых полномочий, внешних эффектов и расширения области.
8. Записать activation event и previous active reference для rollback.

Если base skill изменился после испытания, proposal становится `stale`; новая
revision требует повторной проверки. Негативный результат реального задания
создаёт evidence/proposal, но не даёт модели право молча переписать свою policy.
Качество оценивается по успешному результату и регрессиям, а не по частоте выбора
навыка. Curator архивирует версии с сохранением ссылок; не удаляет pinned,
user-owned и используемые незавершёнными заданиями данные.

### 9.3 Память

Предпочтение пользователя, факт о проекте, процедура и audit event — отдельные
типы данных. Запись памяти содержит source references/revisions, namespace,
время, срок актуальности и статус подтверждения. Вывод модели помечается как
вывод, а не как пользовательское правило. Явное исправление пользователя
замещает прежний факт с сохранением истории; неизменившийся summary не оживляет
удалённую память.

Урок из приватного раздела наследует его ограничения даже после удаления имён.
Перенос в global library требует отдельного preview и пользовательского решения
о публикации/обобщении. Scope обучения не шире пересечения текущей grant и
provenance источников. После отзыва источника зависимые summaries/embeddings
не выдаются модели до безопасной пересборки.

## 10. Мастерская плагинов

Пользовательская просьба «сделай плагин» создаёт plugin project с отдельным
namespace. Цикл: описание → файлы проекта → проверка → сборка → изолированный
preview → diff версии/прав → активация → наблюдение → следующая revision.

Права authoring ограничены файлами данного проекта. Build runner использует
фиксированные зависимости и команды host; запрещены произвольные shell команды,
package lifecycle scripts и сетевой install. Неподдерживаемая зависимость
возвращает диагностику. Создание arbitrary native Rust/Node extension не входит
в первую версию мастерской.

Preview получает synthetic workspace и отдельный профиль; доступ к реальному
разделу включается отдельной пользовательской grant. Права коду плагина равны
пересечению manifest permissions, разрешений установки, текущего workspace и
вызывающей agent grant. Фоновый plugin task имеет собственный principal/grant;
он не наследует завершённый run без явного разрешения.

Активация связана с digest исходников, dependency lock, compiler configuration,
артефакта и permission diff. Изменение любого входа сбрасывает результаты
проверки. Локальное происхождение не обозначается официальной подписью Amby.
Runtime isolation должна быть доказана в production build; Worker без DOM
недостаточен. Если безопасный runtime не готов, authoring остаётся доступным
для подготовки проекта, а live activation блокируется.

Installer сохраняет предыдущую версию и согласует backend publication journal
с frontend registry. Их нынешнее раздельное состояние нельзя считать общей
транзакцией. Rollback кода и rollback пользовательских данных различаются:
миграция плагина имеет отдельный versioned preflight/backup/recovery contract.
Удаление плагина не удаляет его пользовательские данные без отдельного решения.

## 11. Сквозной пример

Запрос: «В разделе проекта создай заметку с планом, базу задач с таблицей и
доской, набросок в Excalidraw со ссылками на заметки; включи крупный шрифт».

1. Grant охватывает раздел проекта, его database/board objects и конкретный
   global key `prefs.fontScale`. Пользователь видит, что шрифт изменится глобально.
2. Агент читает доступный каталог. Если запрошенного database layout ещё нет,
   сообщает ограничение; не сохраняет неизвестный discriminant.
3. Preview фиксирует schema базы, свойства, два view, тексты и элементы сцены;
   ссылки используют результаты создания объектов, а не угаданные IDs.
4. Notes, database/views, Excalidraw и setting исполняются зависимыми шагами с
   общими domain adapters. Каждый шаг имеет собственный receipt.
5. Проверки повторно читают данные, выполняют scoped query базы, проверяют
   связи сцены; visual preview используется только из разрешённых источников.
6. Если Excalidraw-шаг не удался, UI показывает созданные объекты и остаток плана.
   Пользователь выбирает продолжить, оставить или откатить; «всё готово» не выдаётся.
7. Task undo восстанавливает setting по ключу и отменяет зависимые объекты.
   Если пользователь добавил задачу в новую базу, её удаление приостанавливается.
