# Творческая мастерская Amby: задание для Claude Code

Дата: 30 сентября 2026 года.

Статус: архитектурное предложение и план реализации. Модуль по этому заданию ещё не реализован. Имена новых типов, файлов и API ниже являются предложениями, а не описанием существующих интерфейсов.

## 1. Цель и запрос пользователя

Пользователю нужен модуль для создания персонажей, отношений между ними, сюжетных арок, историй, книг, вселенных, локаций и объектов. Нужны собственные категории и автоматическая пробковая доска, которая на основании данных показывает, что с чем связано.

Реализовать официальный отключаемый модуль `amby.creative` с пользовательским названием «Творческая мастерская». Он объединяет каталог мира, структуру рукописи, арки и доски поверх обычных заметок и существующего механизма баз данных Amby.

Главный пользовательский результат: автор создаёт сцену, выбирает персонажей, место и арку; эти связи сразу доступны в карточках участников и на доске. Из любой карточки можно открыть ту же заметку и продолжить работу без копирования текста между инструментами.

### Обязательный объём

- Персонажи, их характеристики и отношения друг с другом.
- Вселенные, истории, книги, главы, необязательные сцены, арки, локации и объекты.
- Создание собственных типов сущностей, полей, шаблонов и типов отношений.
- Написание текста существующим редактором с автосохранением и восстановлением.
- Автоматическое построение доски по явным данным и сохранение ручной расстановки.
- Связи по стабильным ID, сохранность при переименовании, перезапуске и перестроении индекса.
- Локальная работа без обязательной сети и AI.

### За пределами первой законченной версии

AI-извлечение фактов, совместное редактирование, полноценная издательская вёрстка, EPUB/DOCX-пайплайн, произвольные календари вымышленных миров, альтернативные каноны, ветвящиеся интерактивные произведения и размещение одной сцены в нескольких рукописях. Эти возможности не должны задерживать основной сценарий. Их расширения описаны отдельно ниже.

## 4. Архитектурное решение

### 4.1. Проект и общий каталог

Творческий проект — переносимый набор связанных данных. В нём могут быть несколько вселенных, историй и книг. Активный проект задаёт область запросов и досок; хранилище может содержать несколько проектов.

Рекомендуемая исходная модель: одна база «Сущности» на проект и одна база «Связи». Все пользовательские объекты, включая главы и сцены, являются обычными Markdown-строками базы «Сущности». Отношения с собственным описанием являются Markdown-строками базы «Связи».

Обоснование: действующая Relation указывает одну целевую базу через `targetDatabaseId`. Общий каталог позволяет связать персонажа с локацией, религией или пользовательским типом без полиморфных Relation и создания множества полей на каждую пару категорий.

Разделы «Персонажи», «Локации», «Книги» в интерфейсе — специализированные представления общего каталога. Пользователь не должен вручную собирать технические базы для начала работы.

Компромисс: физическая схема содержит объединение полей разных типов. Добавить конфигурацию применимости и отображения полей по типам. Не показывать персонажу все свойства локаций. Если масштаб реального проекта выявит ограничение общей схемы, следующую архитектуру обосновать измерениями и оформить отдельно; не создавать второй источник свойств в модуле.

### 4.2. Три разных вида структуры

Разделить:

1. Файловую иерархию и принадлежность к базе. Сейчас владельцем записи является ближайший database container.
2. Структуру произведения: история/книга → главы → сцены и авторский порядок среди соседей.
3. Произвольные смысловые связи между объектами и их визуальное расположение.

Порядок сцен не должен зависеть от имени файла, алфавитной сортировки или координаты карточки. Арка может проходить через несколько глав и книг. Локация или персонаж могут участвовать в нескольких историях без копирования заметки.

### 4.3. Один канонический источник каждого факта

- Простые структурные отношения, например «глава входит в книгу», могут храниться в обычных Relation-полях сущности.
- Содержательные отношения с пояснением, контекстом или историей изменений хранятся отдельными записями связей.
- Привязки сцены к участникам, месту и аркам хранятся в определённых полях сцены. Граф строит по ним рёбра, не создавая дублирующие записи в базе «Связи».
- Обратное отображение «в каких сценах участвует персонаж» вычисляется запросом к тем же фактам.
- Упоминания из `[[wikilinks]]` остаются самостоятельным слоем.
- Координаты, фильтры и скрытые карточки принадлежат представлению доски.

Нельзя одновременно хранить одно отношение в YAML персонажа, отдельном JSON графа и Canvas с независимым редактированием каждого списка.

## 5. Предметная модель

### 5.1. Встроенные типы

| Тип       | Назначение и первоначальные поля                                                                       |
| --------- | ------------------------------------------------------------------------------------------------------ |
| Вселенная | Описание, правила мира, связанные истории; вложенные области через отдельные отношения.                |
| История   | Замысел, синопсис, статус; самостоятельное произведение или объединение книг.                          |
| Книга     | Синопсис, статус, структура рукописи; принадлежность истории необязательна.                            |
| Глава     | Родитель в рукописи, порядок, синопсис, статус, режим содержания.                                      |
| Сцена     | Родитель и порядок, синопсис, участники, место, точка зрения, арки, цель, конфликт, результат, статус. |
| Арка      | Цель или конфликт, исходное состояние, этапы, итог; связи с персонажами, историями и сценами.          |
| Персонаж  | Описание, мотивация, цели, внутренний/внешний конфликт, необязательный портрет.                        |
| Локация   | Описание, тип места, родительская локация; связанные сцены и объекты.                                  |
| Объект    | Описание, свойства и происхождение; владение и перемещения могут быть отношениями с контекстом.        |
| Событие   | Опорный факт хронологии; может существовать без сцены, описывающей его в тексте.                       |

Не делать большие анкеты обязательными. Создание персонажа требует названия и типа, остальные поля можно заполнить позднее. Шаблоны помогают начать работу, но не ограничивают свободный Markdown.

### 5.2. Общие свойства и идентичность

- Идентичность заметки — существующий `amby-id`, сохраняемый при rename/move.
- Тип — стабильный ID определения типа, связанный со стабильным option ID/schema binding; название и язык интерфейса не являются ключом.
- Заголовок, иконка, описание, статус и принадлежность мирам доступны по назначению типа.
- Принадлежность проекту определяется согласованным manifest/database membership. Не хранить противоречащий этому независимый список в React.
- Пустое значение, неизвестное значение, ошибочная ссылка и незагруженное значение различаются.
- Пользовательские generic `id` и `title` остаются пользовательскими. Модуль не присваивает себе произвольные `amby-*` поля в обход контракта ядра.

Дублирующиеся или некорректные ID обрабатываются действующими правилами read-only/диагностики. Не создавать постоянные творческие связи на временные path-scoped conflict keys.

### 5.3. Собственные категории и поля

Определение типа хранит стабильный ID, пользовательское название, иконку, шаблон Markdown, порядок/группы полей и ссылки на существующие `propertyId`. Переименование типа или поля изменяет отображение, а не идентичность и storage key.

Пример: пользователь создаёт «Фракцию», добавляет «Идеологию», «Лидера» и «Территории», задаёт шаблон описания. Новый тип появляется в каталоге, выборе целей отношений и на доске без добавления TSX-компонента и Tiptap-узла.

Применимость полей и допустимые типы целей проверяются в backend, а не только скрытием элементов интерфейса. При смене типа сущности сохранять ранее заполненные значения; объяснять, какие поля перестали отображаться. Удаление используемого типа не должно удалять заметки или молча менять их категорию: сначала архивирование определения либо явно выбранное переназначение с восстановлением.

Пресеты, их обновления и пользовательские изменения различать. Повторное включение модуля не должно создавать второй набор типов и полей или перезаписывать отредактированные шаблоны.

### 5.4. Содержательные отношения

Логическая запись отношения:

| Поле                   | Смысл                                                                               |
| ---------------------- | ----------------------------------------------------------------------------------- |
| `relationId`           | `amby-id` заметки отношения.                                                        |
| `sourceId`, `targetId` | Одиночные Relation к базе сущностей этого проекта.                                  |
| `relationTypeId`       | Стабильный тип: наставник, союзник, противник, владеет, принадлежит и т. п.         |
| `contextIds`           | История/книга/арка/сцена, в рамках которой утверждение применимо.                   |
| `evidenceIds`          | Необязательные сцены или события, подтверждающие отношение.                         |
| Markdown body          | Пояснение автора и развитие отношения.                                              |
| Временной контекст     | Расширение после определения хронологии; не выводить автоматически из номера главы. |

Тип отношения определяет направленность, прямую/обратную подпись, допустимые типы концов и ограничения. Симметричная связь «союзник» имеет один канонический факт. Направленная «наставник» отображается обратно как «ученик» без второй независимой записи.

Несколько отношений между одной парой допустимы: Марк может быть братом и противником Алисы. Проверка дубликатов учитывает тип и контекст, а не только пару ID. Для симметричных связей нормализовать пару при проверке дубликатов, не теряя исходное пользовательское описание.

Личные отношения могут образовывать циклы. Циклы в структуре «книга → глава → сцена» или во вложенности локаций должны отклоняться. Ограничения не смешивать.

Удалённая, вынесенная из базы, недоступная и ещё не загруженная цель — разные состояния. Сохранять ID незавершённой связи для восстановления. Не удалять отношения каскадно из-за временного отсутствия цели в индексе.

### 5.5. Арки

Арка — самостоятельная сущность. В минимальном варианте содержит описание исходного состояния, цели/конфликта, этапов и предполагаемого итога; сцены связываются с ней через Relation.

В представлении арки видны связанные персонажи и сцены. Поддержать отдельный порядок этапов арки: он не обязан совпадать с порядком чтения. По сценам можно перейти в текст. «Арка без сцен» и «этап без привязки» допустимы как состояние планирования.

Не вычислять художественную завершённость только по числу сцен. Статус завершения задаёт автор; подсчёты являются вспомогательными показателями.

## 6. Рукопись и время

### 6.1. Структура и текст

Хранить явную связь с родителем рукописи и устойчивый порядок среди соседей. Выбрать один алгоритм порядка и документировать вставку, перенос, равные позиции и восстановление. Это авторские данные, а не только `manualOrder` случайного табличного представления.

В первой версии глава или сцена имеет одно место в структуре рукописи. Для повторного использования одной сцены в нескольких книгах позднее потребуется отдельная сущность размещения; не подделывать это дубликатами `amby-id`.

Сцены необязательны. Определить явные режимы главы:

- `body`: текст главы находится в её Markdown-body.
- `scenes`: текст главы собирается из дочерних сцен в заданном порядке; Markdown самой главы остаётся доступным как авторский материал и не включается автоматически второй раз.

Переключение режима не удаляет и не переписывает существующий текст. Интерфейс ясно показывает, что входит в рукопись. Синопсис и черновые заметки не должны незаметно попадать в экспорт.

Использовать существующие `DocumentEditor`, document store, очередь автосохранения, editor-surface lease, историю и recovery drafts. Не создавать второй store текстов книги и независимый autosave внутри модуля.

Первая сборка рукописи — последовательное чтение и экспорт в Markdown. Не начинать с единого редактируемого документа, который незаметно разбивает правки обратно по множеству файлов. Для цельного редактирования потребуется отдельный контракт границ и транзакций.

### 6.2. Две последовательности

Порядок чтения и хронология мира независимы. Сцена-флешбэк может быть последней в книге и описывать самое раннее событие.

Для начального планирования доступны порядок рукописи, порядок этапов арки и явные связи событий «до/после». Полноценный просмотр состояния мира на момент времени — следующий этап после введения валидируемого временного контракта.

Не сохранять «третий день Эры Пепла» как фиктивную ISO-дату. Для будущей хронологии предусмотреть отдельные календарь/эру, относительный порядок, неизвестную дату, приблизительность и интервалы. Номер главы не является датой; порядок публикации не является длительностью отношения.

При реализации изменения отношений прошлое сохраняется. Пример: «союзники до предательства» и «противники после предательства» — разные интервалы одного развития, а не перезапись прежнего факта. Отдельно определить знание читателя и истинное состояние мира, прежде чем обещать режим скрытия спойлеров.

## 7. Пользовательские поверхности

### 7.1. Вход в модуль

Команда/панель «Творческая мастерская», выбор проекта, создание нового проекта с минимальным набором пресетов. В существующем хранилище не перемещать и не классифицировать заметки автоматически.

Новый проект создаётся безопасно с проверкой столкновений путей и повторяемостью операции. Подключение существующих заметок вне проектной базы — отдельная явная операция с preview последствий для membership/свойств. До её реализации не имитировать поддержку универсальных межпроектных Relation.

### 7.2. Каталог мира

Разделы по типам, поиск и фильтры по мирам/историям/статусам. Карточки показывают название, иконку или локальное изображение и несколько выбранных полей. Создание доступно без заполнения длинной анкеты.

Страница сущности: заголовок, значимые поля, свободный Markdown, отношения и связанные сцены/арки. Для персонажа виден список его появлений; для локации — сцены в ней; для предмета — связанные владельцы и события.

Один и тот же объект открывается из каталога, графа и рукописи с общим состоянием сохранения. Поддержать side peek и переход в полноценную вкладку, используя существующие механизмы владения редактором.

### 7.3. Режим рукописи

Слева дерево произведения, в центре текст выбранной главы/сцены, справа контекст: участники, место, арки и справочные карточки. Должна быть возможность свернуть вспомогательные панели и писать без отвлекающих элементов.

Перенос главы/сцены меняет структуру произведения через доменную операцию; обычная сортировка представления не меняет авторский порядок. Прогресс текста считает только участвующие в сборке источники без двойного подсчёта глав и сцен.

### 7.4. Арки

Карточки/список этапов с привязанными сценами, персонажами и итогами. Предусмотреть показ сцены в структуре книги и открытие её текста. Подробный timeline не требуется для первого полезного сценария.

## 8. Автоматическая пробковая доска

### 8.1. Источники и объяснимость

Источники рёбер:

1. Структурные поля сущностей: часть книги, участник сцены, место действия, арка.
2. Записи содержательных отношений.
3. Опционально включаемые упоминания из текста.

Каждое ребро несёт provenance: тип источника, ID записи/свойства/ссылки и путь к её редактированию. Пользователь может понять, почему линия существует. Ребро из Relation и ребро из wikilink не должны становиться неразличимыми.

Совместное участие в сцене можно показать как вывод «участвуют в одной сцене». Оно не означает дружбу, знакомство или вражду. Производные связи явно обозначать; их пересчёт не записывает новые авторские факты.

### 8.2. Режимы доски

| Режим      | Область и назначение                                                             |
| ---------- | -------------------------------------------------------------------------------- |
| Окружение  | Выбранная сущность и ближайшие связи с управляемым раскрытием соседей.           |
| История    | Персонажи, места, объекты и арки выбранной истории/книги.                        |
| План книги | Карточки глав/сцен в порядке рукописи; отдельное действие для изменения порядка. |
| Арка       | Этапы и связанные сцены, с возможностью открыть текст.                           |

Для каждой доски сохраняются стабильный ID, название, область, фильтры типов и отношений, включённые слои, раскладка, закреплённые позиции, вручную скрытые элементы и параметры отображения. Определить, какие настройки переносимы, а какие относятся только к текущему окну.

### 8.3. Поведение

- Создание и редактирование фактов обновляет доску без повторного открытия.
- Новая карточка располагается рядом с относящимися к ней объектами; существующие закреплённые карточки не прыгают.
- Автораскладка запускается явно либо ограниченно для новых узлов. Полная перестройка — отдельное действие с восстановлением прежнего расположения.
- Перемещение карточки на свободной доске меняет только layout. Перенос между главами в плане книги — отдельная доменная операция с ясным результатом.
- «Связать» требует выбора смысла отношения и сохраняет соответствующий факт. Нельзя ограничиваться нарисованной линией, которую остальные представления не видят.
- «Скрыть с доски» сохраняет заметку и отношения. «Удалить отношение» редактирует источник отношения через его обычную операцию. Удаление линии-упоминания не переписывает Markdown неявно.
- Пользовательская заметка-стикер, если она добавлена, является сохраняемым объектом доски; автоматический пересчёт её не удаляет.
- Поддержать подписи, направление, несколько отношений одной пары, миникарту и открытие карточек. Цвет дополняется текстом/формой.
- Основные действия доступны с клавиатуры и без hover. Уважать reduced motion, масштабы текста и существующие темы.

Семантическое undo и undo расположения различаются. Выбрать понятное владение историей: отмена перемещения не должна неожиданно удалять отношение; отмена связи не должна терять несохранённый текст её заметки.

### 8.4. Технология и масштаб

Использовать React Flow. Не копировать весь `CanvasEditor` с его независимым сохранением `.canvas`: выделить необходимые карточки, навигацию или общие примитивы, а творческую топологию получать из предметных данных.

Текущий `canvas-layout.ts` — отправная точка, не доказательство качественной раскладки произвольного графа. Проверить циклы, несвязанные компоненты, разный размер карточек, несколько рёбер одной пары и ручные закрепления. Для сложных раскладок рассмотреть ELK после измерений; его ещё нет в зависимостях. Расчёты большого графа переносить из основного UI-потока.

Граф запрашивается по проекту, области, корневым ID, типам рёбер и глубине. Backend возвращает ограниченный результат, признаки усечения/продолжения, диагностику и версию проекции. Первоначальный продуктовый ориентир — до 200 видимых карточек с раскрытием; это предлагаемое ограничение представления, а не установленная производительность приложения.

Не читать тела всех заметок в браузере при каждом движении карточки. Загружать summaries и видимый участок, миниатюры по необходимости. Кэш запроса включает vault generation и scope; устаревший ответ после переключения проекта не должен заменять новую доску.

### 8.5. JSON Canvas

Добавить экспорт текущего ракурса как обычного `.canvas` со ссылками на существующие заметки и подписями линий. Это переносимый снимок, а не второй источник творческих отношений. Определить поведение недоступных целей и относительных путей.

Изменение экспортированного `.canvas` не обязано редактировать данные проекта. Двусторонняя синхронизация требует отдельного контракта и не входит в первую версию. Обычные и сторонние Canvas-файлы сохраняют текущую совместимость и неизвестные поля.

Уточнить существующее противоречие документации о frontmatter и record shards до внедрения. Не вводить ради модуля ещё один слой значений или молчаливую массовую миграцию. Legacy shards не удалять без документированного перехода и восстановления.

### 9.2. Предложение структуры проекта

Ниже кандидат для согласования на этапе C0, а не уже поддерживаемый формат:

```text
Творческие проекты/Пепельный берег/
├── creative-project.json             # новый versioned manifest проекта
├── Сущности/
│   ├── Сущности.json                  # обычный manifest базы
│   ├── .ambd/
│   │   ├── views/
│   │   ├── templates/
│   │   └── creative/
│   │       ├── types/<type-id>.json
│   │       ├── relation-types/<type-id>.json
│   │       └── boards/<board-id>.json
│   ├── Персонажи/Алиса.md
│   ├── Локации/Старый порт.md
│   ├── Книги/Пепельный берег.md
│   ├── Главы/Глава 04.md
│   └── Сцены/Сделка в порту.md
└── Связи/
    ├── Связи.json                     # обычный manifest базы
    ├── .ambd/
    └── Алиса подозревает Марка.md
```

Manifest проекта содержит format/version, project ID, ссылки на обе базы по стабильным ID и роли системных полей по `propertyId`. Имена каталогов и русские названия не являются идентификаторами.

Проверить discovery, перенос/копирование, bundle export, индексирование, watcher и существующую legacy-миграцию баз. Новый project manifest не должен ошибочно определяться как database manifest. Не создавать служебную `.ambd/` в произвольной папке, если legacy discovery может принять её за отдельную базу. Финальные пути и правила оформить в контракте до записи пользовательских данных.

Весь проект переносится вместе с обеими базами и durable-метаданными. `.ambd/creative/` не является кэшем и не удаляется при rebuild или отключении модуля. Не хранить единственную копию определений типов и досок в глобальных настройках приложения/localStorage.

При копировании проекта отличать backup/перенос с сохранением идентичности от дублирования внутри того же vault. Дублирование требует нового набора ID и согласованного remapping внутренних ссылок либо явного неподдерживаемого действия; нельзя создавать конфликтующие ID молча.

### 9.3. Запись и конфликты

Все новые мутации идут через `src/lib/storage.ts` и Rust. Продолжать действующие CAS/revision и vault-generation соглашения, проверять типы и пути на стороне backend.

До замены файла создавать требуемый snapshot. Для многофайловых действий нужны preflight всех целей, durable backup/journal, записи прогресса, повторяемое завершение/восстановление и явный результат ошибки. Атомарная запись отдельного файла не является транзакцией всей книги. Ошибка rollback сохраняет recovery-данные и не выдаётся за успешное восстановление.

Не допускать lost update между редактированием текста и изменением свойств той же заметки из доски. Операции координируются с document store/очередью сохранения; stale body save не должен затереть обновлённый YAML. Внешние изменения при локальном dirty-состоянии становятся конфликтом.

Сохранять BOM, CRLF/LF, неизвестные YAML/Markdown/JSON и текущие правила Source-only. В творческой карточке действуют те же guards редактора. Не сериализовать неподдерживаемый Markdown ради формирования preview.

Все пути проверяются существующими vault guards; не добавлять широкие static FS scopes. Вложения локальные и проходят текущие asset-механизмы. Удаление использует установленный restorable-trash контракт; не менять глобальное поведение корзины в рамках модуля.

## 10. Интеграция в код

Предлагаемые новые области, которые следует уточнить после C0:

- `src/components/workspace/creative/`: регистрация модуля, проектная страница, формы сущностей, рукопись, арки и доска.
- `src/components/workspace/creative/creative-store.ts`: состояние запросов и представлений без копий document bodies.
- `src/lib/storage/creative-port.ts` и repository/adapter по действующему паттерну: типизированный доступ к проектам, графу и мутациям.
- `src-tauri/src/creative/`: формат проектных метаданных, discovery, validation, query и операции, использующие общий database/note domain.
- `src-tauri/src/commands/creative.rs`: тонкая IPC-граница; `lib.rs` остаётся регистрацией.
- `src/themes/`: оформление карточек, доски и состояний; `src/locales/resources.ts`: все интерфейсные строки и поддерживаемые переводы.

Предлагаемые операции: создать/открыть проект, создать сущность по типу, изменить тип, создать/изменить отношение, получить scoped graph, сохранить настройки доски, изменить структуру рукописи, собрать/экспортировать рукопись. Это названия ответственности, не готовые API. Не дублировать существующие команды для свойств и заметок, если они обеспечивают нужные гарантии.

Новые IPC-типы имеют typed errors для conflict, invalid target, missing/out-of-scope data, read-only future format и recoverable failure. Добавлять `#[specta::specta]`; bindings генерировать тестом, не редактировать вручную.

`amby.creative` использует базы как runtime-зависимость. Проверить включение, отключение зависимости, safe mode и переключение vault. Одной записи в `dependencies` недостаточно. При остановке завершить безопасные pending saves, сохранить recovery и снять подписки; не оставлять фоновые записи старого проекта.

Canvas и Graph можно использовать через общие библиотеки/примитивы. Не требовать включения пользовательского модуля `amby.canvas` только ради отображения React Flow. Не открывать общий SDK привилегированному community-коду ради удобства официального модуля.

При выключенном модуле тексты и файлы остаются доступны; творческие команды и фоновые задачи прекращаются. При повторном включении данные открываются без дублирования пресетов. Unknown future metadata открывается read-only с диагностикой, а не сбрасывается в defaults.

## 11. Зависимости надёжности, которые проверить первыми

На момент анализа обнаружены следующие места. Подтвердить их актуальность и исправлять с regression cases:

1. `database-workspace.tsx` загружает relation options с `page: { limit: 100 }`, а `relation-picker-popover.tsx` фильтрует переданные варианты. Нужны поиск по всей базе, pagination и разрешение названий выбранных ID вне первой страницы.
2. `UpdateDatabaseRelationValueRequest` не содержит ожидаемой ревизии заметки. `update_database_relation_value` имеет отдельный многофайловый путь. Требуются защита от stale writes, согласованное восстановление и актуализация затронутых целей, в том числе удалённых из связи.
3. `apply_value_batch` игнорирует некоторые ошибки backup/recovery/finalization. Сбой обязательного backup обязан остановить изменение исходника. Неудачную финализацию нельзя завершать удалением единственных recovery-данных.
4. Документация Relation обещает вычисляемую inverse-проекцию, а текущая реализация также пишет обратные YAML-значения. До переиспользования выбрать один контракт и явно определить совместимость; новая база связей не должна добавлять ещё один несогласованный список.
5. Контракты frontmatter и record shards в документах расходятся. Согласовать source of truth с реальным чтением, записью, rebuild и импортом.
6. Проверить безопасное переименование свойства и незакрытые проблемы computed projection из прежнего handoff. Не использовать устаревший Rollup как достоверный показатель готовности книги.

Не нужно ждать всех Calendar/Timeline/Formula-возможностей из другого roadmap. После закрытия необходимых границ переходить к первому творческому сценарию.

## 12. Этапы и критерии завершения

### C0. Контракт и проверка основы

Результат: актуализированная карта хранения/владения, согласованные форматы проекта, типов, досок, структурных полей и отношений; список подтверждённых prerequisite-блокеров. Закрыты необходимые failure-boundary проблемы из раздела 11.

Проверить конфликты, backup failure, restart recovery, inverse consistency и поиск записи за пределами первых 100 целей. Не переходить к пользовательским записям нового формата, пока не определены versioning, read-only unknown versions и восстановление.

### C1. Проект, типы и каталог

Результат: модуль включается, создаёт проект с двумя базами и минимальными пресетами; пользователь создаёт персонажа, локацию, объект и собственный тип, редактирует их через обычные заметки.

Готово, когда создание не требует ручной настройки баз, rename сохраняет identity, перезапуск сохраняет данные, повторное включение не размножает поля, чужие заметки остаются нетронутыми. Пресеты содержат книги, главы, сцены и арки даже до появления специализированных представлений.

### C2. Связи и первая автоматическая доска

Результат: сцена связывается с участниками, местом и аркой; между персонажами создаётся типизированное отношение; доска показывает эти факты, их источник и переход в заметку.

Готово, когда оба направления отображения согласованы, новая связь появляется без reopen, pinned layout переживает обновление и restart, hidden не удаляет факт, stale запрос не переключает проект назад. Работают циклы отношений, неизвестные цели и собственные типы.

Это первая законченная вертикаль продукта. Не откладывать её до сложной хронологии или AI.

### C3. Рукопись и арки

Результат: дерево книг/глав/сцен, устойчивое изменение порядка, режимы текста главы, контекстная панель, этапы арок, последовательное чтение и Markdown-экспорт произведения.

Готово, когда перестановка сцен не переименовывает файлы и не меняет хронологию мира, экспорт имеет точный ожидаемый порядок без дубликатов, dirty text сохраняется при переходах, одна сцена может участвовать в нескольких арках без копирования.

### C4. Завершение первой версии

Результат: сохранённые ракурсы досок, экспорт `.canvas`, нормальная работа на большом synthetic project, отключение/включение, copy/move/recovery-сценарии в заявленных пределах, темы, переводы, клавиатура и нативная проверка.

Готово после приёмочной матрицы, обязательного verify/build, подходящей native packaging-проверки и честного отчёта об ограничениях. Состояние «работает на фикстуре в браузере» не закрывает этап.

### C5. Развитие после первой версии

Отдельные итерации: хронология мира и интервалы отношений, вымышленные календари, контекст читательского знания, альтернативные версии событий, повторные размещения сцен, продвинутые layouts, дополнительные форматы экспорта.

AI — необязательное расширение: предлагает сущности/отношения с указанием исходного фрагмента и позволяет автору принять их. Не превращает гипотезу в канон автоматически. Рукопись не отправляется внешнему сервису без соответствующего действия пользователя и настроек AI.

## 14. Автоматические и ручные проверки

### Focused tests

- Чистая graph projection: стабильные node/edge IDs, происхождение, фильтры, inverse labels, дубликаты, пропавшие цели и ограничения глубины.
- Типы и constraints: собственные типы, rename стабильного ID, архивирование используемого определения, допустимость концов связи.
- Структура рукописи: cycle rejection, перенос между родителями, стабильный порядок, экспорт body/scenes.
- Store/query lifecycle: generation, cancellation, invalidation обеих сторон, восстановление view state.
- Rust I/O: неуспех до записи, неполная публикация, recovery, rollback conflict, rebuild, lossless YAML, collisions и path confinement.

Не ограничиваться тестами чистых helpers: проверять production command/repository path, который действительно пишет данные. Новые failure-injection механизмы не доступны в production build.

### Нагрузочные фикстуры

Начать с проекта на 1 000 сущностей и 5 000 отношений, затем проверить 10 000 сущностей. Это предлагаемые размеры приёмки, не уже измеренные показатели. Включить циклы, hubs, несколько книг, собственные типы, длинные подписи, большие заметки и missing targets.

Измерять время первого scoped graph, раскрытия соседей, память, сохранение карточки и реакцию на внешнее изменение. Зафиксировать устройство, runtime, размер видимого графа и численные результаты; по ним установить допустимые бюджеты. Не рисовать все 10 000 карточек сразу ради прохождения «теста масштаба».

### Обязательные команды

- После каждого завершённого batch: `npm run build`, включая изменения документации; записать результат.
- Перед передачей реализации на review: `npm run verify` по актуальному `package.json`.
- При Rust/IPC-изменениях: `npm run rust:test` и regenerated bindings; полный verify уже включает этот запуск, повторять на неизменных исходниках без причины не требуется.
- Для backend-heavy изменений: strict Clippy и Rustfmt; они также входят в текущий полный gate.
- Форматировать затронутые файлы Prettier/Rustfmt, не форматировать весь незавершённый пользовательский diff без необходимости.
- Для desktop behavior/IPC/permissions/modules: подходящая нативная сборка и реальные сценарии `npm run tauri dev`. Указать точную команду и ограничения окружения; debug/ad-hoc bundle не является подписанным релизом.
- Browser smoke через `npm run dev`: UI, fixture adapter, disabled/unsupported states. Он не заменяет native storage smoke.

Не запускать конкурирующие Cargo builds с разными feature sets в общем target: в прежнем handoff уже зафиксирован такой конфликт. Использовать последовательные сборки или действительно независимые target directories.
