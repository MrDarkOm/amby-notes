Дата: 20 октября 2026 года. Ветка `sync/e2-tests` (от локальной `dev`, eb40fcf: Э1 влит). План: [sync-plan.md](../sync-plan.md), раздел 6, шаги 0–3 и 5; протокол — приложение Б.
Сервера нет: каждый запрос отвечает `501 not_implemented`. Opus проверил протокол и тесты 20.10 (см. «Правки после проверки Opus»); сервер пишет другая сессия.

Двоичные данные в JSON — строчный hex (П2): правило то же, что в приложении А; цена — заголовки вдвое длиннее своих байт.

Исполняемый файл `amby-sync-server` понимает `serve`, `user add|list|remove`, `maintenance`, `backup`.
  - Зависимости: `axum 0.8`, `tokio`, `rusqlite 0.32` (bundled, как в приложении). `cargo deny check`: advisories, bans, licenses, sources — ok.
- **Шаг 2. Тесты.**
  - [sync/conformance](../../sync/conformance/src/lib.rs): библиотека (HTTP-клиент, трейт `UserAdmin` с реализациями «в процессе» и «командой», запуск сервера в процессе с подменными часами, клиент с настоящей криптографией `sync/core`) и 14 файлов тестов в `tests/`.
  - [sync/server/tests/config.rs](../../sync/server/tests/config.rs): 8 тестов настроек (П40, П41).
  - `Dockerfile` ([sync/server/Dockerfile](../../sync/server/Dockerfile)): минимальный, многоступенчатый, не от root, том `/data`, проверка здоровья.
  - Скрипт [run-docker.sh](../../sync/conformance/run-docker.sh) (`npm run sync:conformance:docker`): собрать образ, запустить, прогнать набор против контейнера.

## Красная проверка

`npm run sync:conformance:red` (то же, что `cargo test -p amby-sync-conformance -p amby-sync-server --no-fail-fast`, разобранное по причинам):

```text
tests: 178; passed: 0; failed: 178; ignored: 0
failed because of the stub (not_implemented): 178
failed on an assertion of the test:          0
failed for another reason:                    0
```

- Падают **все 178**, проходит 0. Причина у каждого одна: ответ `501 not_implemented` («expected HTTP 200, got HTTP 501 (not_implemented)»), команда `user add` с `not_implemented`, либо `Err(NotImplemented)` из разбора настроек. Ни ошибок сборки, ни «соединение отклонено», ни таймаутов. Скрипт `classify_red.py` возвращает код 1 при любой другой причине и при любом прошедшем тесте.
- Тот же набор против **отдельно запущенного** заглушечного сервера (`AMBY_SYNC_URL`, `AMBY_SYNC_ADMIN_CMD`, то есть путь «чужой адрес + команда»): 170 из 170 падает по `not_implemented`. Это проверка того, что способ работы против контейнера (кроме самого Docker) устроен верно.
- Красный прогон сразу поймал ошибку теста (`user_add_accepts_the_edge_names`: самое длинное имя оказалось из 68 символов вместо 64). Исправлено до коммита.

**Честная оговорка.** Подавляющее большинство тестов на заглушке доходит только до первого шага (`user add` или первый запрос) и дальше не выполняется. Поэтому логика второй половины тестов ни разу не запускалась ни на какой реализации. Проверено вручную: хелперы кодирования и поиска в `server_is_blind.rs`, форма запросов проверена сборкой и ручным чтением по приложению Б. Ошибки в тестах ожидаемо всплывут при написании сервера; по правилу раздела 6 они исправляются отдельным коммитом после проверки Opus.

## Правки после проверки Opus (20.10)

Протокол принят, внесено (одним отдельным коммитом, затем красная проверка заново):

- **Лента сжатая (П31, П32):** у записи в ленте только последняя версия, на её `seq`; прежние — в `versions`. Разрыв (`gap`) бывает только после уборки целой удалённой записи. Тест «лента показывает все версии» переделан, добавлены: запись переезжает на новый `seq`, изменённая во время перелистывания не теряется, остаток коммита не разрывается.
- **Ограничение попыток (П16):** два счётчика — строгий по паре «имя + адрес» и мягкий по имени (`AMBY_SYNC_LOGIN_MAX_FAILURES_PER_USER`, `AMBY_SYNC_LOGIN_WINDOW_PER_USER_SECS`, `AMBY_SYNC_TRUST_PROXY`). Тесты в процессе: нападающий не закрывает владельцу вход, мягкий счёт срабатывает с разных адресов, без `TRUST_PROXY` заголовок игнорируется, берётся последний адрес, блокировка не трогает устройства с токеном.
- **Пределы (Б.9):** 10 000 записей в коммите, 64 МиБ JSON; граничный тест — на собственном сервере с заниженным лимитом (40). В Р2 записано, что до 10 000 файлов переименование папки атомарно.
- **Квота (П42):** `507 quota_exceeded`, `quota.rs` (6 тестов).
- **Ф34 в приложении А:** ключ имён `HKDF(AK, "amby-sync/name-key/1")`, конверт 105 байт; помощник набора шифрует имена так; тесты на длину 105 байт для устройства и пространства.
- **Закрытие потока SSE** при отзыве токена и **`user remove`** (токены → `401 unauthorized`, имя можно создать заново): по тесту на каждое.
- В Э5 добавлено «удаление пространства с сервера из приложения». `cargo-deny`: ISC убран из разрешённых (никому не нужен), предупреждение исчезло. Пометки «на проверку Opus» заменены на «проверено Opus, 20.10».

## Открытые вопросы (были до проверки)

После проверки Opus все закрыты, ответы — в Б.10 плана. Ниже прежний список для истории.

Полный список — приложение Б.10 плана (12 пунктов). Главные:

1. **hex вместо base64url (П2).** Тысяча заголовков в одном запросе вдвое длиннее своих байт.
2. **Блокировка по имени (П16).** Чужой может закрыть владельцу вход на 15 минут пятью неверными паролями; верный пароль тоже получит `429`. Альтернатива — счёт по IP.
3. **Поддельная соль (П13)** не меняется при смене пароля, настоящая меняется: долгий наблюдатель заметит.
4. **Тело и запись не связаны на сервере (П30):** сервер не мешает сослаться на чужое тело своего пространства, подмену ловит устройство.
5. **Разрыв ленты (П32, П36):** устройство, отсутствовавшее больше 30 дней, получает `gap: true` и сверяется заново.
6. **Имя устройства (П12):** формат шифрования под AK не описан в приложении А; набор использует `XChaCha20-Poly1305` с AAD `amby-sync/device-name/1`, ядру Э3 нужна функция и запись `Ф…`.
7. **Лента отдаёт все живые версии (П31),** а не только последнюю.
8. Решения, принятые мной при написании тестов и записанные в приложении после первого коммита: `already_enrolled` убран (повтор кода — `invalid_enroll_code`), `since` и `limit` проверяются (`400`), в `/v1/info` добавлен `sse_keepalive_secs`, проверки с часами и уборкой идут только на собственном сервере набора. Запуски набора занижают два параметра: JSON-лимит 2 МиБ и интервал `: ping` 1 секунда (так же в скрипте для контейнера), чтобы тесты лимитов и SSE были дешёвыми.

