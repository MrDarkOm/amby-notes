## Красная проверка

`npm run sync:conformance:red` (то же, что `cargo test -p amby-sync-conformance -p amby-sync-server --no-fail-fast`, разобранное по причинам):

```text

failed because of the stub (not_implemented): 178
failed on an assertion of the test:          0
failed for another reason:                    0
```

- Падают **все 178**, проходит 0. Причина у каждого одна: ответ `501 not_implemented` («expected HTTP 200, got HTTP 501 (not_implemented)»), команда `user add` с `not_implemented`, либо `Err(NotImplemented)` из разбора настроек. Ни ошибок сборки, ни «соединение отклонено», ни таймаутов. Скрипт `classify_red.py` возвращает код 1 при любой другой причине и при любом прошедшем тесте.
- Тот же набор против **отдельно запущенного** заглушечного сервера (`AMBY_SYNC_URL`, `AMBY_SYNC_ADMIN_CMD`, то есть путь «чужой адрес + команда»): 170 из 170 падает по `not_implemented`. Это проверка того, что способ работы против контейнера (кроме самого Docker) устроен верно.
- Красный прогон сразу поймал ошибку теста (`user_add_accepts_the_edge_names`: самое длинное имя оказалось из 68 символов вместо 64). Исправлено до коммита.

**Честная оговорка.** Подавляющее большинство тестов на заглушке доходит только до первого шага (`user add` или первый запрос) и дальше не выполняется. Поэтому логика второй половины тестов ни разу не запускалась ни на какой реализации. Проверено вручную: хелперы кодирования и поиска в `server_is_blind.rs`, форма запросов проверена сборкой и ручным чтением по приложению Б. Ошибки в тестах ожидаемо всплывут при написании сервера; по правилу раздела 6 они исправляются отдельным коммитом после проверки Opus.

## Правки после проверки Opus (20.10)

Протокол принят, внесено (одним отдельным коммитом, затем красная проверка заново):

- **Лента сжатая (П31, П32):** у записи в ленте только последняя версия, на её `seq`; прежние — в `versions`. Разрыв (`gap`) бывает только после уборки целой удалённой записи. Тест «лента показывает все версии» переделан, добавлены: запись переезжает на новый `seq`, изменённая во время перелистывания не теряется, остаток коммита не разрывается.
- **Ограничение попыток (П16):** два счётчика — строгий по паре «имя + адрес» и мягкий по имени (`AMBY_SYNC_LOGIN_MAX_FAILURES_PER_USER`, `AMBY_SYNC_LOGIN_WINDOW_PER_USER_SECS`, `AMBY_SYNC_TRUST_PROXY`). Тесты в процессе: нападающий не закрывает владельцу вход, мягкий счёт срабатывает с разных адресов, без `TRUST_PROXY` заголовок игнорируется, берётся последний адрес, блокировка не трогает устройства с токеном.
- **Пределы (Б.9):** 10 000 записей в коммите, 64 МиБ JSON; граничный тест — на собственном сервере с заниженным лимитом (40). В Р2 записано, что до 10 000 файлов переименование папки атомарно.
- **Квота (П42):** `507 quota_exceeded`, `quota.rs` (6 тестов).
- **Ф34 в приложении А:** ключ имён `HKDF(AK, "amby-sync/name-key/1")`, конверт 105 байт; помощник набора шифрует имена так; тесты на длину 105 байт для устройства и пространства.
- **Закрытие потока SSE** при отзыве токена и **`user remove`** (токены → `401 unauthorized`, имя можно создать заново): по тесту на каждое.
- В Э5 добавлено «удаление пространства с сервера из приложения». `cargo-deny`: ISC убран из разрешённых (никому не нужен), предупреждение исчезло. Пометки «на проверку Opus» заменены на «проверено Opus, 20.10».

6. **Имя устройства (П12):** формат шифрования под AK не описан в приложении А; набор использует `XChaCha20-Poly1305` с AAD `amby-sync/device-name/1`, ядру Э3 нужна функция и запись `Ф…`.
7. **Лента отдаёт все живые версии (П31),** а не только последнюю.
8. Решения, принятые мной при написании тестов и записанные в приложении после первого коммита: `already_enrolled` убран (повтор кода — `invalid_enroll_code`), `since` и `limit` проверяются (`400`), в `/v1/info` добавлен `sse_keepalive_secs`, проверки с часами и уборкой идут только на собственном сервере набора. ### Дефект в 47 тестах (нужно решение Opus; я их не трогал)

В `blobs.rs` (14 тестов), `commits.rs` (17) и `feed.rs` (16) стоит `let space = fresh_space(&Target::from_env());`. Временный `Target` уничтожается в конце этой строки, а `Drop for InProcess` останавливает сервер ([inprocess.rs](../../sync/conformance/src/inprocess.rs)). Следующий же запрос теста получает `Connection refused`. В красной проверке этого не было видно: заглушка падала раньше, внутри `fresh_space`.

- Приложение Б тут ни при чём: это ошибка в тестовом коде, а не расхождение с протоколом. Против отдельного сервера (там `Target` не владеет процессом) и против контейнера те же 47 тестов зелёные.
- Исправление механическое: `let target = Target::from_env(); let space = fresh_space(&target);`. В копии вне репозитория я заменил так все 47 мест через `Box::leak`, и `cargo test` дал 178 из 178. Эту копию я использовал и для `cargo mutants`, потому что мутанты требуют зелёного базового прогона.
- Пока тесты не исправлены, задача `rust` в CI (`cargo test --workspace`) будет красной на всех трёх системах; задача `container` зелёная.

### Что сделано

Коммиты по частям (каждый можно читать отдельно; по одному они не собираются, пока не собрана вся цепочка модулей):

1. база и миграции, настройки: [db.rs](../../sync/server/src/db.rs), [config.rs](../../sync/server/src/config.rs);
2. хранилище тел файлами, учёт пользователей в базе, общее состояние: [store.rs](../../sync/server/src/store.rs), [state.rs](../../sync/server/src/state.rs);
3. вход и ключи: подключение, `prelogin`, `login`, `recover`, `GET/PUT /v1/keys`, устройства (П5, П11–П19);
4. пространства и тела: части, докачка, Range, квота (П20–П25, П42);
5. коммит и лента: атомарный пакет, сжатая лента, история (П26–П33);
6. уведомления SSE (П34);
7. уборка, команды администратора, роутер, командная строка (П35–П39);
8. Docker, пример `docker-compose.yml` с Caddy, [README](../../sync/server/README.md) на английском, задача `container` в CI.

Данные и сбои:

- SQLite (`rusqlite` bundled) в режиме WAL, `synchronous=FULL`; версия схемы в `user_version`, миграции по одной в транзакции, `quick_check` до и после, `foreign_key_check` после; база, записанная более новым сервером, не открывается.
- Коммит: одна транзакция `BEGIN IMMEDIATE`; сначала тела (П30), потом все базовые версии, и ничего не записывается, если хоть одна проверка не прошла. Гонки тест выдерживает (1 победитель из 8, 7 отказов).
- Тело: часть пишется во временный файл, `fsync`, переименование; `complete` склеивает во временный файл, `fsync`, переименование, затем база помечает тело завершённым, затем части удаляются. Строка в базе появляется раньше файлов, удаляется раньше файлов: после сбоя остаётся лишний файл, а не ссылка на отсутствующее тело. Лишние каталоги подметает уборка (сначала читает каталоги, потом строки, чтобы не принять начатую загрузку за мусор).
- `user remove`: строки в одной транзакции, файлы после.
- Резервная копия: сначала тела, потом снимок базы (`VACUUM INTO`), потом проверка, что для каждого завершённого тела снимка в копии есть файл; иначе копирование повторяется (до трёх раз). Проверено вручную: копия открывается, `instance_id` тот же, `integrity_check` — ok.

Безопасность:

- Хэши токенов и ключей сравниваются `subtle::ConstantTimeEq`; для неизвестного имени и неиспользованного кода идёт тот же путь с нулевым хэшем.
- Поддельная соль: `HMAC-SHA256(prelogin_secret, "amby-sync/prelogin/1" ‖ имя)`, первые 16 байт; секрет создаётся один раз и хранится в базе.
- В журнал пишутся только причины внутренних ошибок и предупреждение про `http://`; токены, `auth_key`, коды, обёртки и тела запросов — никогда. Код подключения выводится только в стандартный вывод `user add`; в базе его SHA-256.
- Сервер ничего не расшифровывает; в базе и на диске нет ни одного ключа, пароля или токена (тест «сервер слеп» зелёный).
- Нет `unsafe`, нет `unwrap` (линт workspace).
- Новые зависимости: `hmac`, `subtle`, `futures-util` (только `alloc`), `getrandom` в сервере и признаки `fs`, `io-util` у `tokio`. Все уже были в `Cargo.lock` через ядро и `axum`; `cargo deny check` — ok.

### Решения, которые приложение Б не описывает (прошу проверить)

1. **В записях `versions` повторяется `item_id`** (П33 перечисляет его только сверху). Помощник набора (`open_change`) читает `item_id` из каждой записи; лишнее поле допустимо по П7. Предлагаю внести его в П33.
2. **Ключ `blob_id` в записи коммита обязателен** (значение `null` или hex16); пропущенный ключ — `400`. Так же `deleted`.
3. **Повторный `POST /blobs` не продлевает 24 часа** (тест `a_body_without_a_commit_is_removed_after_24_hours` этого требует; в П25 так и сказано: создание, часть, `complete`).
4. **Квота (П42)** — сумма размеров всех строк `blobs` пользователя: завершённые (на что-то ссылающиеся или нет) и начатые по заявленному размеру. Это совпадает с П42 и с тестом «что уже сохранено».
5. **Память о `commit_id`** хранится `retain_version_days` дней, потом уборка её стирает (повтор спустя месяц был бы новым коммитом и получил бы `version_conflict`).
6. **Просроченные коды подключения** стираются уборкой через 7 дней после срока, чтобы «верный, но поздно» оставалось отдельным ответом.
7. **`prelogin` с именем длиннее 256 символов** — `400` (П13 говорит «до 256»).
8. **Ограничение попыток:** `Retry-After` = секунды до того, как самая старая неудача из числа удерживающих блокировку выйдет из окна (при двух счётчиках — большее). Успешный вход, подключение и смена ключей не трогают мягкий счётчик; строгий обнуляется, помечая неудачи пары (`strict_cleared`), а не удаляя их.
9. **Адрес клиента.** `build_app` отдаёт роутер как есть (интерфейс не менять), а адрес сокета доступен только при `into_make_service_with_connect_info`. `main.rs` так и запускает сервер. Запуск набора в процессе его не использует: все клиенты там с одного адреса, что для тестов (без `TRUST_PROXY`) эквивалентно.
10. **Закрытие потока при отзыве** — сразу, через канал, и дополнительно проверкой токена перед каждым событием и `: ping`.
11. **Публичный интерфейс.** Остались `Config`, `Clock`, `ManualClock`, `SystemClock`, `AppState::open`, `build_app`, `ROUTES`, `error_response`, трейты `BlobStore`/`UserStore`, функции `admin::*` и `maintenance::run`. Убраны заглушки: варианты `NotImplemented` в `ConfigError`, `StoreError`, `AdminError`, `MaintenanceError`, а также `StubBlobStore` и `StubUserStore` (набор их не использует). Добавлены: `AppState::try_open`, `DbError`, `FsBlobStore`, `DbUserStore`, `StoreError::HasPassword`.
12. **`serve`**: уборка раз в 10 минут и перед остановкой, остановка по `SIGTERM`/Ctrl-C с 10 секундами на закрытие запросов и потоков; команда `healthcheck` (в образе нет `curl`). `user remove` без `--yes` — отказ с кодом 2.

- **Гонка уборки (проверка Opus).** Файлы удалённых тел удалялись после транзакции без замка базы, и заново начатое тело с тем же `blob_id` могло потерять новые файлы. Теперь файлы удаляются во второй транзакции `BEGIN IMMEDIATE` (`Db::write_then`), пока замок держится, и только если строки тела в базе нет. Так же сделаны `user remove` и подметание остатков; `remove_parts` после `complete` трогает только части завершённого тела и безопасен. Детерминированного теста без внедрения сбоя не написать, поэтому правка идёт без нового теста.

### Сила тестов (шаг 7): cargo mutants

Прогнан весь код сервера, кроме `main.rs` (командная строка, её видит только прогон против контейнера), `clock.rs`, `state.rs` и `app.rs` (по 2–7 мутантов, это сборка). Всего **589 мутантов**: **274 пойманы**, **48 выжили**, 267 не компилируются (cargo-mutants считает их негодными). Из тех, что можно проверить, поймано 85 %.

Как запускал (без правки репозитория). `cargo mutants --package amby-sync-server` гоняет тесты только того пакета, который мутирует, а набор лежит в другом пакете, и ключи `--test-package` и `--test-workspace` на версии 27.1 этого не меняют. Поэтому я сделал копию `sync/` вне репозитория, положил тесты набора рядом с тестами сервера (`conformance` стал dev-зависимостью `server`) и применил к 47 тестам механическую правку из раздела о дефекте (без неё базовый прогон красный). Команда: `cargo mutants --package amby-sync-server -f <файл> … -j 3 --timeout 240`. Первая партия: `http/commit.rs`, `http/feed.rs`, `http/throttle.rs`, `http/account.rs`, `maintenance.rs` (191 мутант, 13 минут). Вторая: `http/blobs.rs`, `http/spaces.rs`, `http/events.rs`, `http/util.rs`, `http/mod.rs`, `admin.rs`, `store.rs`, `db.rs`, `config.rs` (398 мутантов, 33 минуты). Один раз базовый прогон второй партии упал на `json_requests_need_a_json_body` с ошибкой сокета macOS (`os error 22`) при трёх параллельных сборках; повтор с `-j 2` прошёл. ### Что не удалось или не проверено

- CI `sync.yml` не запускался (нет push). Новая задача `container` проверена тем же скриптом локально.
- Windows и Linux-сборка сервера локально не проверялись (только macOS и Docker с Debian). Сигналы и `fsync` каталога написаны с учётом Windows (`cfg(unix)`, ошибка игнорируется), но не запускались.
- Нагрузка и большие объёмы не проверялись: один файл в 512 МиБ, 10 000 записей в коммите и миллионы строк в ленте руками не гонялись (граничные тесты идут на заниженных лимитах).
- Мутации не гонялись по `main.rs`, `clock.rs`, `state.rs`, `app.rs`. Скрипт `npm run sync:mutants` остался только для ядра: у сервера он требует исправленных тестов (мутанты ждут зелёного базового прогона в процессе), поэтому отдельный скрипт для сервера не добавлял.
- Таблица `login_failures` растёт на каждую неудачу, в том числе для выдуманных имён (так и задумано в П16: неизвестные имена считаются как настоящие), и чистится уборкой по окну. Поток запросов с миллионами разных имён за окно раздует её; верхней границы нет. Для самохостинга за прокси это терпимо, для публичной службы нужен общий предел.
- У HTTP-сервера нет собственных таймаутов на медленные соединения; предполагается прокси (Caddy) перед ним.
