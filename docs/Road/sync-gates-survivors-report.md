## Как проверялось

Каждый мутант проверялся `cargo mutants` на небольшой выборке (`--re` по файлу и строке), только по новым тестам, с `CARGO_PROFILE_DEV_OPT_LEVEL=2`, как в `sync-gates.yml`. Полный прогон ворот не запускался. Для проверки мутантов настоящего движка тесты симуляции подключаются через заглушки в `core/tests`: чтобы `cargo mutants` мог передать `--test <имя>` обоим пакетам; заглушки не закоммичены.

Что важно для ворот:

- **Таймауты.** Мутант, который делает цикл бесконечным, вешает ещё и прежние тесты. Тест, который его «убивает», должен выполниться раньше них и закончиться ошибкой: `cargo test` останавливается на первом упавшем файле тестов. Поэтому файлы с защитой от зацикливания названы `a0_…` (идут первыми по алфавиту) и ограничивают время вызова (`merge_text`, `open_body_stream`) потоком с ожиданием; цикл чтения ленты ограничен счётчиком запросов. В таких файлах нет ни одного теста, который мог бы ждать вечно.
- Новые тесты движка лежат в `sim/tests/survivors_*.rs`, тесты чистых функций — в `core/tests/a0_merge_survivors.rs` и `a0_stream_survivors.rs`.

## Сбой эталонного мини-движка (зерно 200019)

`sim/tests/self_check.rs` `the_correct_mini_engine_passes_the_simulation` с `AMBY_SIM_SEED=200019`, шаг 13: «Protection: the vault folder is empty: the pass sent changes to the server (Р8)».

**Это ошибка мини-движка, а не ложное срабатывание инварианта.** На шагах 9–10 у устройства 1 процесс умер, а запрос коммита «не дошёл»: в состоянии остался неподтверждённый коммит. На шаге 13 папка хранилища пуста. Настоящий движок (`sync.rs`, «Д55» и затем «С2, Д7») сначала проверяет пустую папку и останавливается, не отправив ничего; мини-движок сначала досылал неподтверждённый коммит (голова сервера 5 → 6), и только потом проверял пустую папку. Инвариант Р8 («остановка защиты ничего не отправляет») верен. Исправлено в `sim/src/mini.rs`: проверка пустой папки идёт до досылки зависшего коммита, как в настоящем движке. Прогон `self_check.rs` целиком (23 теста) и зерно 200019 зелёные. Замороженные тесты не менялись.

## Ошибка движка (остановка №4)

`apply_plan` делает три раунда переименований и ломает цикл (`break_cycle`) только в раунде без продвижения. Если принимающее устройство получает «обмен имён» двух файлов (a↔b) вместе с независимым переименованием третьего (c→d) в одном проходе, раунд 0 даёт продвижение (c→d), цикл ломается только в раунде 1, и трёх раундов не хватает: файл остаётся под служебным именем `b.md.amby-swap-0`, а следующий же шаг прохода (`push`) отправляет это состояние на сервер. Итог: имена перепутаны на всех устройствах, включая то, где пользователь сделал обмен. Содержимое не теряется. Чистый обмен и цикл из трёх работают (на них есть тесты, зелёные).

- Красный тест: `sim/tests/survivors_apply_decide.rs::sv_a_swap_of_two_names_with_an_independent_rename_is_finished` (`#[ignore]`; запуск `cargo test --release -p amby-sync-sim --test survivors_apply_decide -- --ignored`).
- Воспроизведение и подробности: `side-session-notes/…/apply-swap-bug.md`.
- Мутанты `apply.rs:170:36` и `170:49` (`&&` → `||` в условии разрыва цикла) **лечат** этот случай, поэтому тест, зелёный на настоящем движке, их не убьёт. Они остаются «не решены» до исправления движка; после исправления красный тест станет зелёным и закроет и их.
- Родственное наблюдение, не ошибка: цикл из четырёх и более файлов или два независимых цикла за один проход оставляют часть переименований на следующий проход (они закончатся в нём, имена не теряются).

## Равнозначные мутанты

Равнозначный — такой, у которого нет наблюдаемого отличия от исходного кода (или оно невозможно через открытый интерфейс).

### Шифрование и `conflict_set` (12)

- `crypto/header.rs:154:9` (`||` → `&&` в `check_path`): `starts_with('/') || ends_with('/')` целиком покрыто следующей проверкой «пустой сегмент после `split('/')`» — тот же `InvalidPath`.
- `crypto/header.rs:194:40`, `engine/conflict_set.rs:226:40` (`|` → `^` при сборке байта из двух шестнадцатеричных цифр): `(a << 4) | b`, `b` ≤ 15, биты не пересекаются — `|` и `^` дают одно и то же.
- `crypto/header.rs:305:9`, `309:9`, `313:9` (`visit_string`, `visit_none`, `visit_unit` → `Ok(Default::default())`): `serde_json::from_slice` никогда не вызывает `visit_string` (только `visit_str`/`visit_borrowed_str`) и `visit_none` (`null` приходит в `visit_unit`); результат `Default::default()` для `Value` — `Null`, то есть `visit_unit` не меняется.
- `crypto/padme.rs:17:12` (`len < 2` → `<=`): для `len == 2` дальше `exponent = 1`, `mask = 0`, ответ тот же `2`.
- `crypto/recovery_code.rs:30:52`, `42:44`, `42:72`, `133:46` (`|` → `^`): сдвинутые значения не пересекаются по битам.
- `crypto/recovery_code.rs:135:40` (`written < bytes.len()` → `<=`): после 32 байт в накопителе остаётся 4 бита (меньше 8), условие `bits >= 8` не позволяет дойти до 33-го байта.

### `classify.rs` (3)

- `120:24` (`record.kind == Folder` → `!=` при подборе папок-кандидатов): кандидат нужен только если под ним есть файл с хешем, а путь папки уже добавляют предки этого файла.
- `162:37`, `162:52` (`&&` → `||` в условии `!root.is_empty() && root != dir && !found…`): `root` не бывает пустым, а `root != dir` всегда истинно (путь `dir + суффикс` — это путь пропавшей записи, а не нового файла); повторов нет, потому что пути уникальны.

### `stream.rs` (1), `scan.rs` (2)

- `stream.rs:140:16` (`filled -= SEALED_CHUNK_LEN` → `/=`): в этом месте `filled` всегда равно `SEALED_CHUNK_LEN + 1`, и `(N+1)/N == (N+1)-N == 1`.
- `scan.rs:66:32`, `66:60` (теперь `67:32`, `67:60`; `&&` → `||` в `by_path`): лишние записи (удалённые, папки) попадают только в проверку «этот файл слишком большой» и в `missing_sizes`; они дают другое только для размеров меньше самого малого тела (45 байт), а итоговый список «Не синхронизируется» выходит тот же (отправка отказывает такому файлу сама).

### `sync.rs` (2), `push.rs` (2)

- `sync.rs:266:21` (теперь `318:21`, `||` → `&&` в `differs`): отличие только по `deleted` или только по `kind` невозможно у согласованной записи (у неё всегда отличается ещё и хеш), так что оба варианта дают тот же `differs`.
- `sync.rs:470:17` (теперь `559:17`): в `load_bases` условие «`kind != File` / `is_unmaterialised`» раньше отсечено классом (папки и непроявленные записи не бывают «правленными»).
- `push.rs:62:64` (теперь `64:64`): для папок и непроявленных записей класс не `Same`, и обновлять нечего.
- `push.rs:95:17` (теперь `97:17`, «удалить ветку `(_, Same | Blocked)`»): ветку заменяет `_ => {}` ниже.

### `apply.rs` (9)

- `170:58` `<` → `<=`: на последнем раунде без продвижения разрывать цикл уже нечем.
- `298:58`, `299:35`, `299:40`, `303:23`, `304:26` (`==`, `>=`): граф «переименование → переименование, чей источник — мой приёмник» состоит из простых цепочек и циклов, так что защитный счётчик `steps` недостижим, а «застрявшая цепочка без цикла» недостижима из действий пользователя: переименование на занятое имя выглядит для движка как правка и удаление, а не как переименование (проверено).
- `459:31` (`&&` → `||` в `wants_base && local.len() <= MAX`): отличается только расходом памяти (тело сервера скачивается целиком в память до слияния); файлы и сеть те же.
- `707:29` (`existing == bytes` → `true` в `put_file`): отличается только когда файл набора конфликта уже есть с другим содержимым — этого не бывает при том же идентификаторе набора.

### `decide.rs` (7)

- `109:37` (`>` → `>=` в `leaving`), `540:44` (`>` → `>=`), `559:44` (`<` → `<=`), `395:49` (`>` → `>=`): равные идентификаторы или версии уже исключены предыдущим условием.
- `959:23` (`==` → `!=` в `occupant`): внутри условия пустой блок (только комментарий).
- `1001:13` (удалить ветку `Lc::Deleted` в `known_folder`): ветку заменяет `_ => set_base(...)`; `touched.remove` нужен только для файлов.
- `1006:25` (guard `renamed` → `true`): для не переименованной папки `create_dir` существующей папки ничего не делает (нет события), а `cleanup` защищён живой записью.

### `merge.rs` (14)

- `112:9` (`is_insertion` → `true`): сравнивается с `b.bs == a.be`; если `a` закрывает файл (последняя строка без `\n`), то `a.be` — конец основы, а там начинается только вставка.
- `172:69` (`j + 1` → `j * 1`): при несовпадении `T[i][j] = max(T[i+1][j], T[i][j+1])`, поэтому `T[i+1][j] >= T[i][j]` равносильно исходному.
- `244:17`, `246:21`, `257:18` (`-` → `+`), `257:22`, `262:19` (`+` → `*`), `274:27`, `278:18` (`-` → `+`), `278:22`: одностроковые «места» не расширяют ни одной правки (правка либо внутри, либо вне), закрывающая строка `---` не бывает продолжением, `close * 1 == close`, а `i + 1` в таблице даёт тот же конец (`e` стартует с `i` и сразу считает строку `i`).
- `310:32` (`>` → `<`, `==`, `>=`): для правок-замен ветка «вставка» и ветка «замена» расширяют до одного и того же места, потому что другая сторона всё равно расширяется до этого же места; `>=` равносильно исходному.
- `341:33` (`+` → `-`): `last.be - h.be` в этом месте всегда 0 (места не вложены).
