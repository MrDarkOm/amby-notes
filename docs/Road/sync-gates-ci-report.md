## Как запустить

```bash
git push origin HEAD:gates/run
```

Если ветка уже есть, нужен `--force`. Это именно `push` в ветку, а не кнопка и не расписание: такие запуски работают только для файла на `main`, а `sync/` туда попадает при выпуске. Одновременно идёт один запуск (группа `concurrency: sync-gates`; второй встаёт в очередь, а не отменяет первый). Все действия закреплены на полные SHA (проверены `git ls-remote`), права `contents: read`.

## Мутационное тестирование

- Что покрывается: весь `core/src`, то есть и криптография (в Э1 она уже прогонялась: 346 мутантов), и движок. Сейчас **1501 мутант**. `npm run sync:mutants` тоже берёт весь пакет `amby-sync-core`.
- `cargo-mutants` закреплён на 27.1.0 (как у владельца), 20 частей `--shard k/20 --sharding round-robin` (по 75–76 мутантов; без `round-robin` части выходили неравными).
- **Какие тесты.** Мутанты движка убивают в основном тесты симуляции (`sync/sim/tests`), а не тесты ядра, поэтому берутся оба пакета: `--test-package amby-sync-core --test-package amby-sync-sim`. Особенность 27.1 (замечена при пробе): «базовый» прогон cargo-mutants идёт только по ядру, а мутанты уже по обоим пакетам; полный набор перед запуском отдельно проверяет `sync.yml`.
- **Ускоренный набор.** Из тестов убран `sim/tests/self_check.rs`: он проверяет мини-движок и инварианты самой симуляции и не вызывает `amby_sync_core::engine` (проверено: в файле нет настоящего `Engine`), а один занимает больше времени, чем все остальные вместе (124 с против примерно 80 с в `release`). Все тесты, которые гоняют настоящий движок, остаются. Сборка с `CARGO_PROFILE_DEV_OPT_LEVEL=2`: тесты симуляции без оптимизации идут минутами (`rows_p7.rs` — 4,5 минуты), в `--release` пересборка каждого мутанта дороже (17 с против 9 с на пробе из 23 мутантов); при уровне 2 проверки переполнения и `debug_assert` остаются, а они нужны мутантам арифметики.
- **Таймаут** задан явно: `--timeout 600 --build-timeout 1200`. Автоматический берётся от базового прогона (только ядро, 6–20 с), и выживший мутант, у которого идёт весь набор (на пробе 105 с), получил бы ложный таймаут.
- Коды выхода 2 (выжили) и 3 (таймауты) — это находки, а не падение задания. Каждая часть кладёт свой `mutants.out` в артефакт `mutants-<k>` на 30 дней.
- Итог (`gates-summary`, `$GITHUB_STEP_SUMMARY`): сколько пойманных, выживших, таймаутов, нежизнеспособных; список выживших с файлом и строкой; список таймаутов. Задание итога падает, если не пришла какая-то часть.

## Длинная симуляция

- `sync/simrun`, 20 заданий × 4 процесса (по числу ядер раннера) × 2 режима (`quick`, `folders`) × 400 зёрен = **64 000 сценариев**, зёрна не пересекаются: процесс g берёт зёрна `1 + 400·g .. 400·(g+1)`.
- Упавшие зёрна выводятся в итоге вместе с командой `cargo run --release --manifest-path sync/Cargo.toml -p amby-sync-simrun -- <зерно> 1 <режим>`; полные журналы с трассой — в артефактах `sim-logs-<k>`. Сбой самого транспорта тестового клиента (`INFRA`) выводится отдельно и тоже делает итог красным.
- **Сломанные движки.** Задание `self-check` гоняет `self_check` (все 12 намеренно сломанных мини-движков должны быть пойманы, правильный пройти) с четырёх начальных зёрен: 1, 100001, 200001, 300001 (`AMBY_SIM_SEED`); локально с зерна 300001 все 23 теста прошли (109 с в `release`).
- Замечание про Linux: `simrun` ждёт освобождения портов командой `netstat -an -p tcp`, это запись для macOS; на Linux она ничего не печатает, и ожидание не срабатывает. Это безопасно: на пробе около одного соединения на сценарий, упирается всё в процессор (вывод ключа), а не в порты. `simrun` не менялся.
