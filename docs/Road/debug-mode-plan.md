# Debug-режим Amby: план реализации

Дата: 2026-09-27. Версия контракта: 1. Статус выполнения — в [журнале оркестрации](./debug-mode-orchestration.md).

Пользователь подтвердил полный объём: план, задания Luna и немедленную реализацию.
План рассчитан на разработчика и пользователя, который воспроизводит проблему и
экспортирует отчёт. Текущее незакоммиченное дерево `dev` является исходной точкой;
другие накопленные изменения сохраняются. Версия приложения не меняется.

## Цель

Debug должен объяснять, почему заметка не сохранилась, какой этап операции замедлил
приложение, как обработалось внешнее изменение и что предшествовало ошибке.
При этом диагностика не меняет исходники заметок, не раскрывает личные данные и
не становится причиной заметных задержек.

Полный результат включает управление сбором, структурированные события frontend
и Rust, реальное состояние приложения, историю сессий, расследование цепочек,
измерение длительностей и воспроизводимый безопасный отчёт. DevTools остаётся
дополнительным инструментом, но не заменяет эти возможности.

## Исходные проблемы, подтверждённые аудитом

- Frontend записывает события в буфер и файл без проверки минимального уровня.
  `enabled=true` обходит порог консоли.
- Rust флаг Debug не связан с установленным при запуске `EnvFilter`.
  Запись Rust на диск не следует `logToFile`; bootstrap сразу создаёт путь логов.
- Логи содержат названия и пути; строковые ошибки возвращаются из `errorType`
  целиком. Объекты `Error` теряют содержимое при обычном JSON.stringify.
- Ошибки записи/очистки/команд часто скрываются. Очистка не согласована с очередью.
- Текстовый транспорт не имеет общего стабильного ID, окна и операции.
- UI-список растёт независимо от ограниченного буфера, предыдущая история с диска
  не загружается, временная шкала смешивает replay и live.
- События критических операций уже есть, но нет цепочки, duration и состояния.

В исходном состоянии целевые `logger.test.ts` и `diagnostics.test.ts`: 10/10 passed.
Это baseline, а не доказательство фильтрации, приватности или native поведения.

## Зафиксированные продуктовые решения

1. Выключенный Debug сохраняет безопасный ограниченный базовый журнал в памяти.
   Подробные debug-события выключены. Порог равен max(info, выбранный уровень).
   Включённый Debug строго следует выбранному минимальному уровню.
2. `logToFile` — независимый opt-in для обоих источников. До загрузки настроек
   диск не используется. Browser не изображает native history как существующую.
3. Frontend очищает данные до буфера/консоли/передачи; backend повторно проверяет
   их до любого своего выхода. Экспорт выполняет третью проверку.
4. Произвольные title/name/path/query/body/value/prompt/credentials/message/stack
   не входят в автоматическую диагностику. Идентификаторы документов и свойств
   заменяются стабильными в пределах сессии псевдонимами.
5. Пользователь может явно добавить описание проблемы; оно обозначается как
   добровольно введённое, ограничивается по длине и видно в preview.
6. Снимок состояния использует существующие stores/coordinators. Инспекция не
   выполняет flush, не читает содержимое с диска и не строит второй state model.
7. Неизвестное состояние обозначается как unavailable, а не healthy/zero.
8. Настройки отражают фактическое применение; ошибки IPC/диска/экспорта видны.
9. Очереди, списки и сессии ограничены. По умолчанию: 1000 frontend событий,
   5000 history/capture событий, capture до 5 минут, файл 5 MiB, два архива.
10. Нет отправки наружу, broad filesystem scope, версии/tag/release/promotion.

## Контракт события и транспорта

Структурированное событие: `id`, `timestamp`, `level`, `event`, `source`, безопасные
`metadata`; контекст `sessionId`, `windowId`, `operationId`, `subsystem`,
`durationMs`, `sequence`. Стабильный `id` используется для dedupe; sequence
назначает native collector. Имена событий — машинные коды, без текста заметок.

Rust DTO derive Serialize/Deserialize/Specta и camelCase. Bindings генерируются,
не редактируются вручную. Новый live transport — `amby:debug-event` с DTO;
регулярки разрешены только в совместимом legacy parser, который тоже очищает
данные. Старые небезопасные текстовые файлы не включаются в новый safe report.

IPC: `configure_debug`, `get_debug_status`, `append_debug_events`,
`get_debug_events`, `get_debug_history`, `clear_debug_logs`, `flush_debug_logs`.
Все filesystem операции UI идут через `src/lib/storage.ts` и debug repository.
Нельзя обходить Specta Result проверкой только `.catch()`.

BackendStatus: применённая config, sessionId, buffered/dropped/pending/fileBytes,
безопасный fileError, watcherRunning/indexReady/vaultOpen. FE status содержит
отдельную transportError и backend status либо unavailable.

Read/write note получают явный optional operationId от frontend. Нативный scope
связывает запись, индекс и результат. Нельзя использовать process-global current
operation: параллельные окна и операции перепутаются.

### D-10. Frontend foundation и приватность

Строгая фильтрация всех выходов, безопасная нормализация ошибок и metadata,
bounded буфер/очередь, стабильные ID и сохранение исходного времени, subscribe
на append/evict/clear/status. Operation API обеспечивает start/success/failure
с duration и контекстом. Listener имеет корректную повторную инициализацию и
dispose; listener failure виден и retry возможен. Сериализация circular/huge
metadata не должна срывать пользовательскую операцию.

### D-11. Rust collector и настройки

Tracing layer получает типизированные поля и контекст span; raw stdout formatter
не должен обходить очистку. Порог меняется без перезапуска. Config возвращается
после применения; все окна используют согласованное состояние. Ошибка logger
не должна рекурсивно логировать саму себя.

### D-12. Хранение, clear, flush и history

Один ограниченный сериализованный writer; disk I/O не выполняется под locks
vault/index. Реальные ошибки отражаются в статусе. Ротация имеет лимит хранения,
clear удаляет согласованный набор diagnostic files и не возвращает старые queued
события, flush имеет bounded ожидание. History ограничена, упорядочена и читает
валидные структурированные записи; повреждённая строка не скрывает всю историю.

### D-20. Безопасная инспекция

Overview: open/dirty/conflict документы; scheduled/inFlight/paused/failed autosave;
pending/failed recovery; watcher/index status; активные модули/safe mode; режим
редактора и причины Source-only. В памяти допускается чтение существующего
контента для проверки round-trip только по явной refresh диагностики; в итоговый
snapshot входят только счётчики/коды, без контента/ID/пути. Длительные проверки
ограничиваются размером/количеством и отражают unavailable при превышении.

### D-21. Цепочки и длительности

Сохранение, чтение, запросы базы, поиск, обновление индекса и watcher получают
operation IDs и измерения. Различаются ожидание очереди и выполнение. Результат
пользовательской операции остаётся прежним; конфликты и recoverability не
заменяются logger error handling. На закрытии diagnostics flush идёт после
сохранения/recovery и не отменяет успешное сохранение заметки.

### D-30/D-31. Просмотрщик

Четыре раздела: состояние, события, производительность, отчёт. Виртуальный
ограниченный список, фильтры времени/уровня/источника/subsystem/window/operation,
поиск безопасных полей, раскрытие деталей, группировка одинаковых ошибок.
Pause останавливает отображение, а не сбор. Отдельны clear screen и delete
history. Видны buffer eviction/queue losses/errors. История переживает перезапуск
при включённом persistent logging.

### D-40/D-41. Воспроизведение и отчёт

Start/marker/stop, ограничение 5 минут/5000 записей, capture не зависит от того,
открыт ли dialog. Завершённая сессия остаётся экспортируемой. Export versioned
JSON: версия приложения, runtime/build mode, очищенные события/снимок состояния,
диапазон capture/markers/counters, состав включённых/исключённых данных и явное
описание. Preview соответствует файлу; export через storage/native save dialog.
Отмена экспорта отличима от успеха и ошибки. Startup error report использует
тот же safe contract и остаётся доступен без монтирования workspace.

### D-50. Производительность

Duration summary по операциям: count/avg/p50/p95/max, slowest операции и queue
vs execution. Сэмплы ограничены и очищены. Debug сам не запускает benchmark
пользовательского vault. Дополнительный verbose capture ограничен сессией;
базовые monotonic измерения не делают full serialization на каждый keystroke.

## Завершение

Все Q-сценарии [приёмки](./debug-mode-acceptance.md) имеют actual evidence.
После завершённого batch — build, перед review — полный verify. Rust/IPC требуют
rust:test, generated bindings, строгий Clippy и native build. Browser/native UI
проверяются на synthetic vault; личные настройки и файлы не используются.
Если check падает по исходному unrelated diff, причина сохраняется отдельно;
это не разрешение объявить G6 passed. Нельзя писать в changelog неподтверждённые
результаты или менять версию во время повторных проверок.
