1. Замороженный тест кажется неверным — не менять в той же сессии; решение и исправление — отдельной сессией и
   только после ответа владельца (раньше это решал Opus).
2. Переключение `GATES_PASSED` и снятие разделения на тестовые хранилища.
3. Любой push, тег, версия, выпуск, публикация образа, запуск ворот.
4. Выживший мутант, который указывает на настоящую ошибку движка.

## Правила работы

- **Модели:** оркестратор — Sonnet. Haiku — тексты, переводы, документация, механика, простые правки с готовым
  тестом. Sonnet low — средние задачи. Sonnet medium — данные, движок, слияние, сервер, тесты на мутанты. В каждой
  задаче писать модель и усилие. Opus — не использовать (лимиты).
- **Тесты до кода**, сначала красные. Строгий порядок (тесты — проверка — другая сессия пишет код при
  замороженных тестах) для того, где ошибка теряет данные.
- **Ветки:** работа в `sync/*` от **локальной** `dev` (в `start_session` передавать `source_branch: "dev"`);
  вливание `git merge --no-ff`, без squash. Только локальные коммиты.
- **Перед вливанием** на ветке прогнать `npm run typecheck`, `npm run lint`, `npm run docs:check`; после вливания —
  `npm run verify` и ядро `sync/` в release. Конфликт в `updates/upd_next.md` — оставить обе стороны.
- **Команды, меняющие состояние,** писать как `rtk <команда>` или `rtk proxy <команда>`.
- **Диск:** после вливания удалять worktree сессии (`rtk proxy git worktree remove --force <путь>`); ветка
  остаётся. Перед новыми сессиями — `df -h /System/Volumes/Data`.
- **Отвечать владельцу по-русски, просто и коротко.** Он доверяет технические решения о сохранности данных, но
  данные — превыше всего.
