# Amby Notes: план стабилизации и завершения баз данных для Gemini

Дата: 2026-09-19. Основа: аудит текущей рабочей копии ветки `dev`, версия приложения `0.1.3`, включая незакоммиченные изменения.

Это задание для будущей реализации. Создание документа не означает исправления описанных проблем. Все этапы ниже имеют статус `TODO`, пока исполнитель не подтвердит их критерии готовности.

## 1. Задание исполнителю

Доработай существующую систему баз данных Amby: устрани риски потери данных при переходе на frontmatter, восстанови гарантии изменений и миграций, согласуй свойства заметок и баз, заверши существующие интерфейсы и вычисляемые поля, затем проверь производительность и native-сценарии.

Работай по этапам ST-00—ST-12. Сначала воспроизведи проблему, затем исправь её и проверь результат. Наличие похожей функции, зелёного общего набора тестов или пункта в changelog не является доказательством выполнения этапа.

Не начинай с переписывания приложения или замены SQLite. Сохраняй действующие границы React → storage/IPC → Rust → исходные файлы и производный индекс. Завершай существующие механизмы, если они подходят.

### Объём и отношение к другим планам

- Этот документ объединяет рекомендации аудита от 2026-09-19 и задаёт порядок их реализации.
- `docs/Road/database-codex-execution-plan.md` содержит более широкий продуктовый backlog EX-00—EX-43. Он не отменяется, но его историческое описание хранения в shards нельзя автоматически считать текущим контрактом.
- Calendar, Timeline, специальные вымышленные календари, новые пресеты, полный CSV import/export, облачная синхронизация и совместное редактирование не добавляются в этот цикл. Уже работающие функции нужно сохранить.
- Переход на frontmatter уже начат. Цель — сделать его безопасным и полным; обнаружив неподдерживаемые данные, сохраняй их исходное представление и выдавай диагностику.
- Этот план не разрешает запускать миграции на личном хранилище владельца проекта. Проверки выполняются на одноразовых fixtures.
- Не создавай дополнительные задачи, субагентов, автоматизации или внешние публикации без отдельного указания пользователя.

## 2. Правила работы

1. Прочитай актуальный `AGENTS.md`, инструкции затрагиваемых каталогов, `docs/vault-format.md` и `docs/markdown-compatibility.md`.
2. Проверь `git status --short --branch` и diff. На дату аудита в рабочей копии уже были изменения базы данных, frontmatter, панели свойств и локализации. Не откатывай их и не заменяй файлами из HEAD.
3. Не используй `git reset`, `git clean`, автоматический stash или массовое форматирование для упрощения задачи. Продолжай начатую работу в текущей ветке; новую работу начинай от `dev` согласно правилам репозитория.
4. Выбирай первый незавершённый этап с выполненными зависимостями. Делай небольшие партии с конкретным проверяемым результатом.
5. Перед изменением поведения добавляй тест границы данных или пользовательского результата. Для чистой документации отдельные тесты не нужны.
6. Не редактируй `src/lib/bindings.ts` вручную. Изменения IPC сопровождай генерацией через Rust-тест и обновлением adapters.
7. Все видимые строки добавляй в `src/locales/resources.ts` на всех поддерживаемых языках. Сохраняй границы тем и компонентов.
8. После каждой партии обновляй контракт, если он изменился, и `updates.md`. Не записывай туда обещания как выполненные функции.
9. Выполняй проверки раздела 7. Не отключай тесты, не ослабляй assertions и не меняй ожидаемый результат только ради PASS.
10. Не повышай версию приложения, не коммить, не пушь, не создавай tag/release и не продвигай ветки без соответствующего запроса пользователя. Версия формата данных и версия приложения — разные вещи.
11. Если существенное решение меняет смысл данных и не определено планом, задай один конкретный вопрос и продолжай независимую работу. Обычные технические решения принимай самостоятельно.
12. Записывай ход выполнения в журнал раздела 9. Отмечай `DONE` только с доказательствами; отсутствие native-среды означает `BLOCKED` для этой проверки, а не PASS.

## 3. Исходное состояние и обнаруженные проблемы

### Подтверждённые результаты аудита

- `npm run verify`: PASS; 654 frontend-теста, 306 Rust-тестов, 2 Rust-теста ignored в стандартном запуске. Проверки форматирования, Knip, strict Clippy и bindings прошли.
- ESLint сообщил одно предупреждение о зависимости `React.useCallback` в `database-workspace.tsx`.
- `npm run build`: PASS; есть предупреждение о размере отдельных chunks.
- `npm run db:benchmark -- --size 10000`: PASS. 10 000 строк, 20 свойств; синхронизация заметок — около 1732 мс, rebuild проекции — 5503 мс, первая страница из 100 строк — 28 мс, три поисковых запроса суммарно — 122 мс.
- Этот benchmark создаёт старые `.ambd/records` и `.ambd/views` и не измеряет полный путь новой миграции или записи ячейки. Это историческая точка сравнения, не гарантия скорости новой архитектуры.
- Отдельный запуск текущих функций преобразования подтвердил потери: `1234567890.123456789` превращается в `1234567890.1234567`; Date теряет `end` и `timeZone`; Files сохраняет только имена, обратное преобразование возвращает отсутствие значения.
- Native Tauri UI в этом аудите не запускался. Старые отчёты о других сборках не подтверждают работоспособность текущих изменений.

- Discovery не должен чинить manifest, менять ID, переписывать неизвестную версию, удалять shards или recovery.
- Прекратить подавлять ошибки, от которых зависит сохранность источников. Показать локализованную причину и путь к восстановлению, не выдавая успешную миграцию.

- Исправить неподтверждённые формулировки о безопасности миграции в накопленных release notes без удаления посторонних записей.

**Проверить:** открытие и reindex старого, частично перенесённого, повреждённого и будущего формата; отключённый модуль; незавершённый recovery. Сравнить байты исходных файлов до/после. Изменение производного SQLite допустимо.

**Готово, когда:** обычное чтение или rebuild не меняют существующие источники базы и не уничтожают пути восстановления.

### ST-03. Сериализация свойств без потерь

**Файлы:** `format.rs`, `frontmatter.rs`, `validation.rs`, `yaml_sync.rs`, fixtures и colocated tests.

**Сделать:**

- Убрать преобразование exact decimal через `f64`; хранить число в форме, сохраняющей точность. Обработать отрицательные значения, дроби, экспоненту и границы диапазона согласно контракту.
- Сохранять Date целиком: начало, конец, часовой пояс и точность. Поддержать чтение прежней скалярной даты.
- Сохранять Files целиком: `assetId`, тип, относительный путь, имя, MIME, размер и неизвестные поля. Реализовать обратное чтение; файлы вложений не переносить и не удалять побочным эффектом конвертации.
- Сохранить устойчивость Select/Status/MultiSelect к переименованию option. Название не должно быть единственным идентификатором, если оно может меняться.
- Relations сохраняют полные ID и неизвестные поля; missing/outsideDatabase остаются отдельными состояниями.
- Различить отсутствие значения и невозможность преобразования. Ошибка не должна превращаться в пропуск записи с результатом «успех».
- Сохранять нетронутые YAML/Markdown, BOM, переводы строк и неизвестные поля. Если безопасный splice невозможен, отказать в операции с понятной причиной; не пересериализовывать весь документ ради одного поля.

**Проверить:** round-trip всех типов; известные примеры R2; вложенные/opaque значения; `0`, `false`, пустота; невалидные данные; идентичность нетронутых частей документа. Проверять также через реальный путь записи и rebuild, не только чистые функции.

**Готово, когда:** поддерживаемые значения восстанавливаются семантически без потерь, нетронутые байты сохраняются, неподдерживаемые данные остаются исходными и явно диагностируются.

### ST-04. Общий протокол мутаций, CAS и recovery

**Файлы:** `mutations.rs`, `mutation_state.rs`, `views.rs`, `rows.rs`, `commands/database.rs`, существующие history/recovery/atomic-write helpers.

**Сделать:**

- Использовать общий план операции для записи ячеек, batch, двусторонних relations и изменений схемы/представлений. Не строить параллельный save layer.
- До первой записи проверить generation, состояние модуля, lock/read-only, ownership, ограничения типов, безопасные пути и ожидаемые ревизии всех изменяемых ресурсов.
- Разрешать note ID через индекс с повторной проверкой фактического ID и принадлежности. Не выбирать первую заметку с duplicate ID и не обходить границы вложенной базы или служебных каталогов.
- Создать backups и durable journal до публикации файлов. Записывать состояние шагов, итог операции и данные для идемпотентного повтора после перезапуска.
- Использовать atomic helpers и повторную проверку конфликтов максимально близко к публикации. Документировать оставшееся окно гонки с внешним редактором; не называть несколько независимых файлов аппаратно атомарной транзакцией.
- При частичном сбое выполнить безопасный rollback либо оставить обнаруживаемый recovery-required outcome. Не откатывать поверх новых внешних правок.
- Для relations планировать исходную и обратные стороны вместе; учитывать cardinality, lock целевой базы, self-relations и отсутствие target. Не игнорировать ошибки.
- Публиковать согласованную SQLite-проекцию после durable результата. Различать «не сохранено», «сохранено, индекс требует восстановления» и «операция требует recovery».
- Координировать watcher и блокировки. Не держать общий mutex подключения SQLite во время долгого обхода/чтения файлов без необходимости.

## 7. Команды и правила проверки

После каждой завершённой партии: сфокусированные проверки затронутого поведения, форматирование только изменённых файлов и `npm run build`. Перед передачей на review — `npm run verify`.

После Rust-изменений: `npm run rust:test`; для существенных backend-изменений также `npm run rust:clippy`. Изменение command/type требует проверки генерации bindings. Перед итоговой передачей используй полный gate из актуального `package.json`.

```sh
npm run verify
npm run build
npm run rust:test
npm run rust:clippy
npm run bindings:check
```

Не нужно без причины повторять отдельно команды, которые уже успешно выполнены внутри `verify`; повтор оправдан изменениями или новой проверяемой гипотезой. Если `bindings:check` сравнивает намеренно изменённый generated-файл с HEAD, докажи воспроизводимость генерации и честно зафиксируй отличие; не скрывай его staging/reset или ручной правкой.

Для изменений хранения/IPC/watcher и итоговой приёмки:

```sh
npm run test:e2e
npm run test:storage:live
npm run test:native:ui
npm run db:benchmark -- --size 10000
npm run db:benchmark -- --size 50000
npm run db:benchmark -- --size 100000
npm run tauri build
```

До ST-12 benchmark нового формата можно запускать на меньшей целевой выборке через адаптированный harness; результаты прежнего генератора подписывать как legacy. Не запускать нагрузку на личном vault. Native build обязателен при изменении Tauri configuration/plugins/permissions/IPC/packaging/updater либо нужно точно объяснить, почему он недоступен.

Ручные сценарии выполняются в `npm run dev` и `npm run tauri dev`, где применимо. Зафиксируй реальные действия: создать базу → добавить свойства/строки → изменить из панели и таблицы → фильтровать → закрыть/открыть → внешняя правка → конфликт → recovery → rebuild. Для UI-изменений приложи screenshots/recordings без пользовательских данных.
