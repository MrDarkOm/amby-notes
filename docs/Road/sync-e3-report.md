## Находки при написании

- **Копия конфликта у двух устройств** (Д46): детерминированное имя означает, что два устройства могут независимо сделать одну копию; в приложение внесено «если путь копии занят записью сервера с тем же содержимым, копия не создаётся». Нашла симуляция на мини-движке.
- Тест тишины («тихий проход») нельзя строить на счётчиках отчёта: повтор незавершённого коммита меняет сервер, хотя счётчики нули. Симуляция считает проход тихим, только если не сдвинулась голова сервера.
- Редкий сбой транспорта сервера в процессе под большой нагрузкой на macOS (`Invalid argument` при чтении заголовка ответа, несколько раз на десятки тысяч запросов; на 18 000 последовательных и параллельных запросов не воспроизвёлся). Тестовый клиент повторяет такой запрос (счётчик `TRANSPORT_RETRIES`); причина не найдена, вынесено как вопрос.

## Правки после проверки Opus (21.10)

Проверка Opus повторила красный прогон: 138 тестов падают только на `todo!()`. Приложение В принято, все пометки заменены на «проверено Opus, 21.10». Внесено одним коммитом:

- **Д56, Д57 изменены:** при `resync` на пути остаётся локальная версия и уходит на сервер, отличающаяся серверная становится копией конфликта. Тесты: возврат сервера из копии и откат версии ([opus_review.rs](../../sync/sim/tests/opus_review.rs)); мини-движок поправлен.
- **Д70, подсказка о переименовании:** `CycleRequest.rename_hints`; тесты «переименование с правкой — одна запись» и «подсказка используется один раз». В Э4 плана записано, что приложение передаёт подсказки.
- **Д71, предел размера файла:** `EngineConfig.max_file_bytes`, причина `TooBigForMemory`; тест в обе стороны. В Э4 записано потоковое шифрование тела.
- **Д72, настоящий сброс:** сервер без пользователя и пространства, пользователь не создаётся заново; устройство останавливается, ничего не трогает (тест на настоящем сервере, и для мини-движка).
- В Э4 записано: приложение повторяет проходы с нарастающей паузой (Д19).

Красная проверка после правок: `expected red: stub 144, assertion 0, other 0`; сломанные движки по-прежнему ловятся. В этом же прогоне один раз упал тест Э2 `blobs.rs::a_body_belongs_to_its_space_and_its_owner` тем же сбоем транспорта сервера (отдельно проходит, 16 из 16): это тот же редкий сбой, он не связан с кодом Э3.

Новые тесты: 6 против настоящего движка (красные на `todo!()`) и 3 против мини-движка (зелёные).

### Результат

- `npm run sync:test`: **512 тестов зелёные** (1 игнорируется — перезапись семян фаззинга). Красной проверки больше нет: все 144 теста настоящего движка и ядра проходят.
- **Симуляция, финальный прогон** (коммит c35d689, `npm run sync:sim:run`, 3 процесса: два по `quick`, один с папками): **1862 случайных сценария за 1 ч 36 мин, 0 падений**. До этого такие же прогоны (около 1600 + 1750 сценариев на предыдущих версиях кода) нашли **два настоящих дефекта движка**, оба исправлены и проверены тем же зерном; перед каждым перезапуском все тесты проходили заново:
  - зерно **2000522** (quick): два устройства независимо создали разные файлы по одному пути и разошлись навсегда; исправление — правило Д49 для двух живых записей на одном пути: путь сохраняет запись с меньшим `item_id`, на всех устройствах одинаково, второй файл уходит на имя копии конфликта;
  - зерно **2000547** (quick): «известная» запись, переименованная на занятый путь, застревала на устаревшей базе (проход `Busy` из-за повторных `version_conflict`); исправление — проигравшая запись ставится на имя копии, переименование уходит на сервер.
    Узкое место прогона — не процессор, а порты: тестовый клиент сервера открывает новое соединение на каждый запрос, а macOS держит порт 30 секунд. Поэтому `simrun` ждёт, пока в TIME_WAIT меньше 9000 соединений, и повторяет зерно, если упал сам транспорт; скорость около 30 сценариев в минуту. «Десятки тысяч» на этой машине потребовали бы около суток, поэтому прогон ограничен двумя часами. Однократный сбой транспорта (`Invalid argument` при чтении ответа) на зерне 5000058 повторился отдельно успешно; это тот же редкий сбой, что описан выше.
- **Фаззинг** `body_open_stream` (с семенами `fuzz/seeds`): 30 минут — **1 991 102 запуска**, ещё 5 минут в конце — 490 144 запуска; **падений нет**, покрытие 913 ветвей.
- **Мутанты чистых функций** (`names`, `consistency`, `rules`, `stream`; `cargo mutants`, тесты ядра): 103 мутанта за 11 минут: **98 пойманы, 3 выжили, 2 таймаута** (таймаут — бесконечный цикл, считается пойманным). Выжившие все в `stream.rs`:
  - `stream.rs:140` `filled -= SEALED_CHUNK_LEN` → `/=`: **равносильный мутант** — в этой точке `filled` всегда равно куску плюс один байт, и `-=` и `/=` дают 1;
  - `stream.rs:157` `<` → `<=` в `read_up_to`: **равносильный** — чтение в пустой срез даёт 0 и цикл выходит;
  - `stream.rs:161` условие `ErrorKind::Interrupted` → `false`: **настоящая дыра тестов** — нет теста с источником, который отвечает `Interrupted`; движок должен повторить чтение. Тест не добавлен (правило задания); предложение: источник, который раз в несколько вызовов отвечает `Interrupted`.
- **Мутанты движка** (остальные файлы `engine/`, 496 штук): **отложены по решению владельца, 22.10**; проверка поломками для движка пойдёт одним прогоном позже, перед включением синхронизации на настоящих заметках. Пробный запуск (16 мутантов, 2 выжили в `apply.rs:145`, в цикле разбора отложенных переименований) показал, что полный набор на этой машине занимает около 12 часов (тесты движка идут по 1–2 минуты на мутанта и упираются в порты); для будущего прогона нужен ускоренный набор тестов или Linux.

### Как устроен движок (решения реализации, не отменяющие Д)

- Файлы: `sync.rs` (шаги Д10, защиты, курсор, отчёт), `scan.rs` (обзор диска, быстрая проверка Д12), `classify.rs` (переименования: единственная пара хэшей, целая папка, подсказка Д70), `feed.rs` (лента, заголовки, подделка, формат новее), `decide.rs` (таблица Р7 как функция без ввода-вывода), `apply.rs` (Д17), `push.rs` (загрузки с докачкой, коммиты). Подробно — в `sync/MAP.md`.
- **Запись папки есть только у пустой папки** (так требуют тесты: папки с файлами не считаются записями). Папка, в которой нет ничего, становится записью; при появлении файлов запись остаётся.
- **Запись, которую нельзя материализовать здесь** (имя Windows, исключённый путь, слишком большой файл), хранится в базе с `mtime_ns = i64::MIN` — приватное соглашение внутри `ItemRecord`, публичные типы не менялись. Такая база повторяется каждым проходом, никогда не читается как удаление и даёт запись в списке «не синхронизируется».
- Для **известной** записи, которая упёрлась в имя или размер, база не меняется, курсор держится, запись в списке (приходит снова при следующем проходе).
- **Согласие `resync`** стирает связь с сервером в памяти сразу, а в состоянии — только когда проход дошёл до записи, чтобы остановка не оставила половину изменений.
- **Незавершённый коммит** повторяется после проверки пустой папки (иначе защита Д55 пропускала бы чужую старую отправку) и после пробы головы ленты (`ServerBehind`).
- Обмен имён по циклу ломается временным именем `*.amby-swap-N` (не временный файл Р4, чтобы `cleanup_staged` его не удалил).
- Запись в симуляции новых файлов не знает прежнюю идентичность недозагруженного тела: при докачке новая запись берёт `item_id` из записи о загрузке по хэшу и размеру.

### Что не удалось, ограничения, вопросы к Opus

1. **Коммиты** сделаны не по темам из задания (состояние и цикл, загрузка, конфликты, …), а по состоянию работы: движок писался целиком, части не компилируются порознь. Всего 7 коммитов.
2. **Ошибки записи на диск, кроме `NoSpace`** (например, нет прав на один файл), останавливают весь проход: у `FsError` нет варианта «запрещено». Безопасно (данные целы), но один недоступный файл блокирует синхронизацию. Для Э4: добавить вариант или считать `Io` ошибкой записи.
3. **Переименование на имя, недопустимое на этой системе** оставляет файл на старом месте с записью в базе «не материализовано»; следующий обход выгрузит файл как новую запись по старому пути (дубликат на сервере). Безопасно, но шумно. Нужен ответ Opus: оставить или держать курсор.
4. **Конфликт «два живых элемента на одном пути»** (Д49) решён правилом меньшего `item_id`; в Д этого нет. Копия при этом не попадает в список конфликтов (Д47) — только появляется файлом. Нужно решить, вносить ли правило в приложение В.
5. Два раза за конец сессии `npm run sync:test` останавливался на тестах Э2 `conformance` (`retention`, `feed`) сразу после остановки мутантов; отдельно эти тесты проходят (13 и 18), последний полный прогон `cargo test --workspace` зелёный. Это тот же редкий сбой транспорта сервера, что и в отчёте Э2.
