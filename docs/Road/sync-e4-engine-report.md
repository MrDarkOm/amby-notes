# Синхронизация, Э4 (движок в приложении): отчёт

Дата: 23 октября 2026 года. Ветка `sync/e4-engine` (от `dev`, `cacf6c3`). План: [sync-plan.md](../sync-plan.md), раздел 6 («Строгость по риску»: для интерфейса и связки с приложением порядок облегчённый — тесты первым коммитом, потом код, одна проверка Opus; мутации и независимые эталоны не обязательны).

Что умеет синхронизация теперь: хранилище можно **включить** (новое пространство на сервере или существующее), после чего заметки, вложения, пустые папки и имена на любых языках передаются между компьютерами зашифрованными; правка появляется на другом компьютере сама. Включить можно **только на хранилище, которое пользователь отметил как тестовое**, пока не пройдены ворота перед настоящими заметками (мутации движка и долгая симуляция).

## Что сделано

Подробности — в [sync/MAP.md](../../sync/MAP.md) и [src-tauri/src/MAP.md](../../src-tauri/src/MAP.md). Коротко:

- **Порты.** `LocalFs` — `src-tauri/src/sync/vault_fs.rs`: атомарная запись через временный файл рядом, снимок `sync-overwrite` перед заменой (даже при выключенной истории; ошибка снимка отменяет запись), корзина `.amby/trash/` ровно для названного файла (не для всей «связки» заметки), переименование без перезаписи (ссылка + удаление, папка — проверка), путь не может выйти из хранилища (ни `..`, ни ссылка на пути). `StateStore` — `state_db.rs`: SQLite с номером схемы, одна транзакция на операцию, повреждённый файл откладывается, файл новее схемы не трогается, блокировка файлом. `Remote` — `remote.rs` поверх асинхронного клиента, `Clock`, `Random` — `SystemClock`, `OsRandom`.
- **Сессия** (`session.rs`): проходы по событиям файлов (через правило Р4, включая собственные записи Amby и файлы `.amby/`), по уведомлениям сервера (свои коммиты не будят), по просьбе пользователя и раз в 5 минут; пауза Д19 5, 10, 20… секунд до 5 минут; остановки Р8 ждут ответа; незавершённый журнал (`planned`/`inProgress`, нечитаемый тоже) задерживает отправку; блокировка сессии на хранилище.
- **Среда** (`runtime.rs`): включение (новое пространство с именем по Ф34 или существующее, ключ пространства хранится в состоянии обёрнутым ключом аккаунта, поэтому хранилище запускается без сети), возобновление при открытии хранилища и после входа/выхода, отключение сохраняет связь.
- **Наблюдатель и редакторы.** Записи синхронизации **не** регистрируются как собственные записи приложения: наблюдатель сообщает о них как о правке другой программы, поэтому открытый редактор получает обычный конфликт (проверено настоящим наблюдателем системы). События пачки склеиваются (`EventBatch`): каждый путь один раз после пачки.
- **Подсказки о переименовании (Д70)**: команды переименования и перемещения записывают пары до выполнения.
- **Интерфейс** (`sync-vault-panel.tsx`): включение (новое/существующее пространство, отметка тестового хранилища и предупреждение), статус, остановки Р8 с понятным текстом, список конфликтов с тремя вариантами, список «Не синхронизируется» с причинами; русский и английский.
- **Ворота**: `gate.rs`, константа `GATES_PASSED = false`; снимается отдельным коммитом после согласия владельца.
- **Перенесённое из Э3**: `FsError::AccessDenied` (один недоступный файл не останавливает проход), файл не выгружается второй раз под старым путём, копия по Д71 в списке конфликтов, тест `Interrupted`, повторное использование соединений тестового клиента. Потоковое шифрование тела **не** сделано: файлы крупнее 256 МБ остаются в списке «Не синхронизируется».
- **Документы**: `.amby/sync/` и таблица «какие файлы `.amby/` синхронизируются» в `docs/vault-format.md`; тест держит таблицу и правила движка вместе.

## Решения реализации, не отменяющие приложения Б и В

- Копия конфликта получает тот же `amby-id`, что и файл (Р7: «проверить на Э4»). Проверка по коду показала **дефект индексатора**: копия сортируется раньше файла (`Name.0123…` < `Name.md`) и забирала стабильный ID, а оригинал получал ключ конфликта и переставал редактироваться. Исправлено (см. ниже), а не вынесено в `.amby/sync/conflicts/`, как предполагал план: копия остаётся видимым файлом, ID не теряет оригинал.
- Событие `hello` потока уведомлений будит проход только если голова ленты дальше курсора; свои коммиты не будят.
- Сервер, не отвечающий, и пропавшая папка хранилища — разные вещи: `VaultMissing` сам проверяется заново с нарастающей паузой, остальные остановки ждут пользователя.

Все проверки перед отчётом пройдены; числа — по итоговым прогонам.

- `npm run verify` (docs:check, version:check, typecheck, lint, vitest 2669, format:check, knip, rust:fmt, **строгий Clippy**, `rust:test` 944, bindings:check) — зелёный.
- `npm run build` — зелёный. `npm run sync:lint` (fmt, Clippy, cargo-deny) — зелёный; `npm run sync:test` — зелёный (61 набор тестов, включая 13 + 3 новых тестов клиента и соединений, 5 тестов переносов Э3, 3 теста `Interrupted`); `npm run sync:req-check` — все требования названы.
- **Сила теста `Interrupted`**: убран повтор чтения при `ErrorKind::Interrupted` в `stream.rs` — 2 из 3 новых тестов падают, выживший мутант закрыт.
- **Те же сценарии симуляции через настоящие порты** (`ports_scenarios_tests.rs`): все пять строк таблицы Р7, снимок и корзина (Р8), массовое изменение с согласием, оставшийся временный файл, недоступный файл. Сами сценарии `sync/sim` на настоящих портах **не** запускались целиком: симуляция написана для виртуальной файловой системы и общей памяти, и перекладывать её на SQLite и диск значит переписывать её. Вместо этого сценарии построчно повторены.
- **Два хранилища на одном Mac через сервер в процессе** (`session_tests.rs`, 28 тестов, `runtime_tests.rs`, 12): передача файлов в обе стороны, конфликт и три способа его разрешить, остановки Р8 (массовое изменение с двух сторон, пропавшая папка, сброс сервера, отключённое устройство), незавершённый журнал, сеть, которая пропала и вернулась, повтор с нарастающей паузой, остановка без зависания, копия хранилища на другом компьютере, повторный запуск, подсказка о переименовании. Прогнаны по три раза подряд без сбоев.
- **Наблюдатель настоящей системой**: тест файловой системы запускает `notify`, пишет через `VaultFs` и ждёт событие по пути: запись синхронизации не скрыта от наблюдателя.
- **Нативная проверка двух компьютеров, пройдена** (`npm run test:native:sync-vault`): два настоящих окна приложения против одного сервера, настоящий React-экран, IPC, Rust, наблюдатель. 11 шагов на A и 10 на B: вход, предупреждение и отметка тестового хранилища на экране, «Включить синхронизацию» (новое пространство на A, существующее на B, найденное по названию), файлы приходят без кнопки, правка B приходит на A **как внешнее изменение** (событие наблюдателя), прежняя версия в истории с причиной `sync-overwrite`, удаление A приходит в корзину B, обе стороны «Всё синхронизировано» без конфликтов, выключение сохраняет связь. **Сервер в этой проверке — программа из репозитория, а не контейнер**: Docker на этом Mac не запущен (`colima` выключена). Проверка на контейнере и на двух физических компьютерах — ручной сценарий, **не пройден**.
- Вид экрана: панель показана в браузере с настоящим кодом и подставным портом в светлой и тёмной темах (выключено, «Всё синхронизировано», остановка с 245 файлами, конфликт, «Не синхронизируется», нет связи): читается, ничего не наезжает.

## Вопросы к Opus

1. **Ворота.** Отметка тестового хранилища хранится в самом хранилище (`state.db`, ключ `test_vault`): достаточно ли этого, или отметка должна жить в данных приложения (скопированное хранилище не должно «унаследовать» разрешение)? Сейчас повторное включение отметки не требует.
2. **Ключ пространства в состоянии.** Обёрнутый ключ аккаунта VK лежит в `state.db` ради запуска без сети. Он не секретнее, чем на сервере; нужно ли это в плане (Р5, Р10)?
3. **Копия конфликта и `amby-id`** (Р7, «проверить на Э4»). Сделано не как в плане (`.amby/sync/conflicts/`), а правкой индексатора: копия не забирает идентификатор и не блокирует файл; «Оставить оба» присваивает копии новый `amby-id`. Возражения? Остаётся окно: при инкрементальном индексе копия, пришедшая раньше файла, получит идентификатор до полного обновления.
4. **Конфликт `.amby/properties.json`.** Копия лежит рядом в `.amby/`, а правило Р4 такие имена не синхронизирует; «Заменить копией» работает локально. Нужно ли особое слияние по ключам (Р7)?
5. **События потока уведомлений.** Свои коммиты и `hello` без новых коммитов не будят проход (иначе после каждой загрузки идёт лишний проход). Достаточно ли пяти минут как запасного опроса?
6. **Папка, которую нельзя прочитать целиком** (нет прав на подпапку) останавливает проход ошибкой, а не помечает файлы «нет доступа»: иначе файлы подпапки выглядели бы удалёнными. Верно?
7. **Потоковое шифрование тела (Д71)** не сделано; файлы больше 256 МБ — в списке «Не синхронизируется». Делать ли в Э5?
8. **Мутанты `placed_as`, `unplaced` и `AccessDenied`** в движке добавлены без собственной проверки силой тестов; их закроет прогон мутантов перед воротами.
9. **Тесты, написанные вместе с кодом**, а не до него: `frontmatter::with_replaced_amby_id` (два теста), `rules_doc_tests` (таблица `.amby/` в документе против правил). Остальное — до кода.

### Решения и ловушки

- Копия конфликта не забирает `amby-id` (правка индексатора, не `.amby/sync/conflicts/`); «Оставить оба» даёт копии новый id.
- Ловушки среды: на macOS редкая ошибка `Invalid argument` и паника `ureq` при возврате соединения в пул — тестовый клиент повторяет запрос и ловит панику. Сначала пробовал только повтор при ошибке — паника проходила мимо.
- Нативная проверка: команды чтения/записи файла в приложении меняют CRLF на LF, поэтому в странице проверки только LF; побайтово это проверяют Rust-тесты. Ожидание «прошёл проход» должно учитывать `lastSyncMs > время записи` и `uploaded >= 1`, иначе гонка.
- Тесты, написанные вместе с кодом, а не до него: `with_replaced_amby_id`, `rules_doc_tests`.
- `cargo`-команды запускать из корня worktree; `timeout`/`sleep` на macOS и в оболочке ограничены.
