# Базы данных Amby: пошаговая инструкция для Codex

Дата составления: 2026-09-12. Основа: аудит текущего кода ветки `dev` и ответы владельца проекта.

Это инструкция для будущей реализации. Наличие пункта в документе **не означает**, что функция уже реализована или проверена. При создании этого документа приложение не изменялось.

## 1. Задание исполнителю

Доработай существующую систему баз данных Amby до удобного универсального инструмента для больших личных коллекций: свойства, страницы записей, представления, связи, шаблоны, вычисления, массовые операции и переносимость данных.

Выполняй небольшие задачи по порядку ниже. Не заменяй реализацию повторным составлением общего плана. Перед изменением найди фактический код соответствующей функции: часть работы уже сделана. Завершай существующий механизм, если он подходит, и не создавай рядом второй механизм с тем же назначением.

Работай последовательно одним исполнителем. Этот документ не требует создания отдельных задач в приложении, запуска субагентов, автоматизаций, публикаций или платных сервисов.

### Подтверждено пользователем

- Нужна совокупность возможностей: представления, свойства, связи, формулы, удобное редактирование и шаблоны.
- Первые сценарии: персонажи, миры и творчество. Архитектура должна оставаться универсальной.
- Целевой масштаб: десятки тысяч записей и больше. Для проверки использовать 10 000, 50 000 и 100 000 записей.
- Это личные большие базы. Облачная совместная работа не является требованием данного задания.
- Одинаковые названия записей разрешены. Записи различаются по устойчивому ID.
- Пользователя нужно спрашивать о существенных продуктовых деталях по ходу работы.

### Сохраняемые решения проекта

- Каждая запись — обычная Markdown-заметка с `amby-id`.
- `ambd.json` и `.ambd/records`, `.ambd/views`, `.ambd/templates` — исходные данные базы. Их нельзя считать удаляемым кэшем.
- SQLite `.amby/notes.db` — перестраиваемый индекс. Потеря SQLite не должна уничтожать названия, значения, связи, представления или шаблоны.
- `.amby/properties.json` содержит долговечные локальные свойства заметок; не удалять его при очистке индекса.
- Одна заметка имеет одну owning database, определяемую текущими правилами файлового контейнера. Показывать её в других местах можно через связи и встроенные представления.
- Источником истины для связей служат полные ID, а не заголовки и не пути.
- Новые возможности расширяют текущие storage/IPC, Rust domain modules, Zustand stores и editor lifecycle.

### Граница этого задания

В обязательный объём входят все пункты EX-00—EX-43. Специальный календарь вымышленного мира в EX-40 зависит от ответа пользователя. При отсутствии ответа выполнить обычную временную шкалу, сохранить открытый вопрос и явно указать отсутствие специального календаря. Не выдавать его за реализованный.

Cloud sync, одновременное редактирование несколькими людьми, публичные формы, публичные сайты, произвольные автоматизации и объединение нескольких источников в один изменяемый dataset требуют отдельного задания. Не добавлять их в этот цикл самостоятельно. Это границы согласованного плана, а не заявление о полном совпадении Amby со всеми продуктами и функциями Notion.

## 2. Как выполнять план небольшой моделью

### Перед каждым рабочим циклом

1. Прочитай актуальный `AGENTS.md` в репозитории и дополнительные инструкции в затрагиваемых каталогах, если они появились.
2. Прочитай разделы 1—7 этого документа и запись о текущей задаче в журнале раздела 10.
3. Выполни `git status --short --branch`. Посмотри diff файлов, которые собираешься менять.
4. Не стирай, не откатывай и не переноси чужие незакоммиченные изменения. Не запускай автоматически `git reset`, `git clean`, `git stash` или массовое форматирование.
5. Продолжай текущую рабочую ветку, если реализация уже началась. Новую feature/fix-ветку начинай от `dev` по правилам `AGENTS.md`; не переключай dirty checkout с потерей работы.
6. Выбери первый незавершённый EX-пункт с закрытыми зависимостями. Одна рабочая партия — один проверяемый результат внутри этого пункта.
7. Если пункт включает backend и UI, делай подшаги отдельно: контракт → backend → IPC/adapters → UI → сквозная проверка. Не объявляй весь пункт DONE после первого подшага.
8. Напиши пользователю коротко, какой результат делаешь и как проверишь его.

Не загружай весь проект или весь документ в один усечённый tool output. Сначала найди нужные заголовки, затем читай выбранный диапазон строк. Например:

```sh
rg -n '^### EX-|^## 10\.' docs/Road/database-codex-execution-plan.md
rg -n 'apply_database_value_batch|rebuild_database_projection' src-tauri/src/commands/database.rs
```

Если вывод содержит `truncated`, перечитай недостающий небольшой фрагмент. Не считай непрочитанную часть проверенной.

### Цикл реализации

1. Прочитай перечисленные в задаче файлы и найди места вызова через `rg`.
2. Для изменения поведения сначала добавь минимальный тест, который проверяет пользовательский результат или границу сохранности данных. Для чистой документации и простой косметики отдельные тесты не нужны.
3. Зафиксируй исходное поведение тестом или ручным воспроизведением. Не создавай тест, который только повторяет структуру реализации.
4. Внеси минимальное связное изменение. Не реорганизуй соседние модули без необходимости.
5. Проверь failure path: ошибку нельзя заменять пустым результатом, успешным уведомлением или очисткой черновика.
6. Обнови связанные контракты и `updates.md`. В changelog описывай только действительно появившийся результат на русском.
7. Отформатируй только затронутые файлы, выполни проверки из раздела 6.
8. Запиши результат и следующий подшаг в журнал. Поставь DONE только после выполнения критериев задачи.
9. Продолжай следующую доступную задачу в пределах активной работы. Если выполнение прервано, оставь точное состояние для продолжения; не заявляй о выполнении всего задания.

### Когда задавать вопросы

- Не спрашивай повторно о подтверждённых решениях из раздела 1.
- Самостоятельно выбирай названия функций, разбиение файлов и обычные технические детали в рамках контрактов.
- Спрашивай, если решение меняет смысл данных, правила удаления, поведение вымышленных дат или пользовательский сценарий, которого нет в задании.
- Задавай один конкретный вопрос с примером и рекомендуемым вариантом. Не отправляй пользователю длинную анкету.
- Пока ждёшь, выполняй задачи, не зависящие от ответа. Не считай молчание согласием на изменение исходных данных.
- Препятствие в native runner или на одной платформе записывай с командой и фактической ошибкой. Не имитируй PASS и не выключай проверку ради зелёного результата.

## 5. Инварианты и незакрытые решения

### Сохранность данных

1. I/O frontend проходит только через storage/IPC. Запрет не обходится ради preview, import или benchmark.
2. Перед изменением durable формата, rename/move, frontmatter и восстановления прочитай оба основных контракта из `docs/vault-format.md` и `docs/markdown-compatibility.md`.
3. Сохраняй BOM, line endings, неизвестные JSON/YAML/Markdown поля и opaque nodes. Неизвестные типы показывай read-only с диагностикой.
4. Новая миграция требует отдельной версии формата/миграции, read-only preflight, backup, журнала, повторяемости, восстановления и документированного rollback. Версия формата не равна версии приложения.
5. Не изменяй существующие `amby-id` ради одинаковых названий. Дубликаты ID продолжают быть ошибкой; дубликаты названий становятся нормальным состоянием.
6. `operationId`, ожидаемые revisions и `vaultGeneration` проверяются backend. Повтор одной операции безопасен; повтор ID с другим payload отклоняется.
7. Успешная запись исходных файлов и ошибка последующего обновления индекса — разные результаты. Не создавай дубликат записи повторной отправкой create после ошибки индекса.
8. Для многоресурсной операции используй существующий журнал и атомарную публикацию отдельных файлов. Одна SQL-транзакция сама по себе не делает несколько файлов атомарными.
9. Rollback не перезаписывает более новое внешнее изменение. Такой случай становится конфликтом с сохранёнными данными восстановления.
10. Чтение UI во время многоресурсной публикации не должно считать частичный результат окончательным. Обновляй видимую проекцию после завершения операции.
11. Не удаляй orphan shards, отсутствующие relation targets, assets и recovery автоматически.
12. Для новых query/schema типов расширяй существующие tagged unions и общую валидацию. Не размножай `any`, не передавай сырой SQL/JS через IPC.

### Предлагаемая техническая схема названий для EX-04—EX-06

Пользователь подтвердил различение записей по ID, но не выбирал конкретное имя поля или файловый шаблон. Следующее — рабочее техническое предложение, которое нужно сверить с реальным кодом в EX-04:

- Полный `amby-id` остаётся единственным ID записи.
- Для явно заданного названия использовать отдельное namespaced поле Markdown, например `amby-title`; не занимать пользовательский generic `title` и не перезаписывать его.
- Если новое поле отсутствует, сохранить текущий fallback: заголовок Markdown → имя файла. Сканирование не добавляет новое поле автоматически.
- Для новых database rows использовать безопасное файловое имя с уникальным полным ID или другим гарантированно collision-safe суффиксом. Обрезать только читаемую часть с учётом ограничений путей. Не полагаться на уникальность короткого отображаемого ID.
- Изменение отображаемого названия не должно требовать переименования файла. Явное файловое переименование остаётся отдельной существующей операцией.
- Введение нового поля и согласование приоритета заголовков требуют проверки чтения старой версией, сохранения Markdown и повсеместного отображения одинакового названия.
- Существующее неизвестное/некорректное поле с выбранным именем нельзя молча захватывать. Выявить такой случай preflight и показать конфликт.

Если аудит выявит несовместимость предложения, сначала исправь контракт и объясни конкретную причину изменения. Не внедряй частично разные правила в таблицу, дерево и индекс.

Полезные стартовые команды:

```sh
npm run test -- src/components/workspace/database src/lib/storage/database-port.test.ts

```

`npm run verify` сейчас включает version check, TypeScript, ESLint, Vitest, Prettier, Knip, Rustfmt, strict Clippy, Rust tests и bindings check. Общая проверка может выявить существующий drift. Записывай исходную ошибку; исправляй относящееся к своей задаче. Не форматируй весь репозиторий и не исключай тесты.

`bindings:check` сравнивает generated file с Git HEAD. При намеренном изменении IPC незакоммиченный generated diff может приводить к ненулевому коду. Дополнительно проверь, что повторная генерация не меняет полученный файл, но не называй исходный gate PASS. Не коммить автоматически ради обхода проверки.

### 2026-09-12 — устранение задержки загрузки строк

- Причина задержки подтверждена кодом и измерением: `set_database_module_enabled`
  всегда перечитывал все manifests и record shards, а watcher затем мог запустить
  несколько таких же полных rebuild параллельно. В debug benchmark на 10k строк
  полный rebuild занимал 5.156 s при загрузке первой страницы за 28.9 ms.
- Исправлено: здоровая проекция переиспользуется после metadata-only stamp-проверки
  source-файлов; при изменениях watcher группирует события, записи обновляются
  incremental-путём, представления — отдельным refresh, а structural changes
  сохраняют безопасный полный rebuild. При incremental update дочерние relation,
  option, file и conflict rows сначала удаляются, поэтому устаревшие значения не
  накапливаются.
- Проверки этой партии: `npm run build`, `npm run lint`, `npm run format:check`,
  `git diff --check`, Rust database tests — 71 PASS, 1 ignored, export bindings —
  1 PASS; `npm run db:benchmark -- --size 10000` PASS (sync 1.848 s, rebuild
  5.156 s, first page 28.9 ms, three searches 124.9 ms). `cargo clippy --all-targets`
  остановлен на 4 существующих предупреждениях в bundle/index/property-store/
  desktop-e2e тестах, изменённые database targets ошибок не дали.
- Tauri dev перезапустил backend после изменений без ошибок компиляции; native
  визуальная проверка полного пользовательского сценария не подтверждена, потому
  что dev-window не появился в доступных UI-поверхностях текущего окружения.
- Следующий точный подшаг: завершить независимые schema/template/relation
  operations, затем native disposable-vault and measured benchmark gates;
  текущий batch оставлен без commit.
