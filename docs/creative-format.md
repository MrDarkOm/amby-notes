# Творческий модуль Amby: контракт формата (редакция 3)

Дата: 13 октября 2026 года.
Версия формата: 3.
Статус: **действующий контракт данных плоской мастерской**. Заменяет вложенную модель
редакции 2 от 6 октября 2026 года.
План перехода и подтверждённые проверки этапа 0 — в [creative-workshop-plan.md](creative-workshop-plan.md).

---

## 1. Архитектурные принципы

1. **Заметка — данные, модуль — проекция и оформление.** Каждая сущность (персонаж, локация,
   глава, арка, якорь, заметка) — обычный Markdown-файл с метаданными во frontmatter.
   Каждый раздел — стандартная база данных Amby ([database-format.md](database-format.md)).
   Без творческого модуля хранилище остаётся полностью читаемым и структурированным.
2. **Папка мастерской — переносимая единица (W1).** Все данные мастерской находятся внутри
   единой корневой папки мастерской с маркером `amby-workshop.json`. В хранилище может быть
   одна или несколько мастерских; связи между разными мастерскими не поддерживаются.
3. **Плоская организация баз и принадлежность через связи (W2, W5).** В мастерской нет
   вложенности папок проектов и вселенных. Базы сущностей мира, историй, арок, якорей и заметок
   расположены на одном верхнем уровне мастерской. Принадлежность сущности историям или вселенной
   задаётся исключительно свойствами-связями (Relation по ULID заметки).
4. **История как прикреплённая база текста (W3).** Единственное место физической вложенности —
   папка текста истории: карточка истории является строкой общей базы «Истории», а сама папка —
   прикреплённой базой данных страниц текста. Внутри папки истории других вложенных папок нет.
5. **Один источник фактов и атомарность.** Значения и связи хранятся во frontmatter заметок.
   Файл маркера мастерской и файл настроек текста истории фиксируют конфигурацию и схемы,
   но не дублируют значения свойств. Запись ведётся через Rust-слой атомарных операций
   с журналированием и поддержкой отката.

## 2. Структура каталогов мастерской

```text
Мастерская/
├── amby-workshop.json          ← маркер мастерской (формат v3)
├── Вселенные/                  ← база вселенных (ленивая, W11)
├── Истории/                    ← база историй (базовая)
│   └── Моя история/            ← прикреплённая база текста истории (W3)
│       ├── Моя история.md      ← карточка истории (строка базы «Истории»)
│       ├── Моя история.json    ← манифест базы текста истории
│       ├── amby-story.json     ← настройки текста (уровни, форматы, свойства)
│       ├── Глава 1.md          ← страницы текста (строки базы текста)
│       └── Глава 2.md …
├── Персонажи/                  ← база персонажей (базовая)
├── Локации/                    ← база локаций (базовая)
├── Арки/                       ← база сюжетных линий (ленивая, W11)
├── Якоря/                      ← база якорных событий (ленивая, W11)
└── Заметки/                    ← общая база заметок (ленивая, W11)
    └── Идеи/                   ← блокнот (подпапка базы «Заметки», W7)
```

## 3. Файл-маркер мастерской `amby-workshop.json`

Файл находится в корне папки мастерской. Наличие файла `amby-workshop.json` с валидным ULID
и `formatVersion: 3` определяет папку как мастерскую Amby.

```json
{
  "formatVersion": 3,
  "workshopId": "01JAX000000000000000000001",
  "name": "Моя мастерская",
  "icon": "icon:feather",
  "tags": ["Фэнтези", "Комиксы"],
  "revision": "rev_01JAX…",
  "sections": [
    {
      "id": "stories",
      "role": "stories",
      "name": "Истории",
      "databaseId": "01JAX000000000000000000002",
      "path": "Истории"
    },
    {
      "id": "characters",
      "role": "characters",
      "name": "Персонажи",
      "databaseId": "01JAX000000000000000000003",
      "path": "Персонажи",
      "storiesPropertyId": "01JAX000000000000000000005"
    },
    {
      "id": "locations",
      "role": "locations",
      "name": "Локации",
      "databaseId": "01JAX000000000000000000004",
      "path": "Локации",
      "storiesPropertyId": "01JAX000000000000000000006"
    }
  ]
}
```

### Спецификация полей `amby-workshop.json`

| Поле            | Тип            | Назначение                                                                                      |
| --------------- | -------------- | ----------------------------------------------------------------------------------------------- |
| `formatVersion` | целое (`3`)    | Версия формата. Значения выше 3 открывают мастерскую только для чтения без модификации маркера. |
| `workshopId`    | ULID string    | Стабильный уникальный идентификатор мастерской.                                                 |
| `name`          | string         | Отображаемое название мастерской.                                                               |
| `icon`          | string / null  | Закодированное значение иконки (`IconValue`).                                                   |
| `tags`          | string[]       | Пользовательские теги мастерской.                                                               |
| `revision`      | string         | Непрозрачный хэш/ревизия для защиты от конфликтов параллельной записи (CAS).                    |
| `sections`      | SectionEntry[] | Список зарегистрированных разделов мастерской (базовых, ленивых и авторских).                   |

### Элемент `sections`

```typescript
type SectionEntry = {
  id: string // Уникальный строковый ID раздела в мастерской (часто совпадает с role)
  role: WorkshopRole // Предопределённая системная роль или "custom"
  name: string // Пользовательское название папки/базы
  databaseId: string // ULID базы данных Amby
  path: string // Относительный путь к папке базы от корня мастерской
  storiesPropertyId?: string // ID свойства «Истории» в этой базе (разделы мира), см. §6
  universePropertyId?: string // ID свойства «Вселенная» (у разделов `stories` и `anchors`), см. §6
  arcsPropertyId?: string // ID свойства «Арки» (только у раздела `anchors`), см. §6
  charactersPropertyId?: string // ID свойства «Персонажи» (только у раздела `arcs`), см. §6
}

type WorkshopRole =
  "stories" | "characters" | "locations" | "universes" | "arcs" | "anchors" | "notes" | "custom"
```

Поля `storiesPropertyId`, `universePropertyId`, `arcsPropertyId` и `charactersPropertyId` необязательны и **аддитивны**: версия формата
остаётся 3, а мастерская без них читается и работает (привязка к историям тогда недоступна, пока
не выполнена операция `add_story_links`, §6). Неизвестные поля файла и записей разделов
сохраняются при любой перезаписи.

## 4. Базы данных мастерской и их роли

Все разделы мастерской являются стандартными базами Amby. Роль определяет специализированное
отображение в интерфейсе модуля (панель, галереи, досье, фильтры).

| Роль         | База по умолчанию | Создание                | Назначение и стартовые свойства                                                                                                                                                                                                                                                                                                                    |
| ------------ | ----------------- | ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `stories`    | `Истории`         | При создании мастерской | Каталог всех произведений. Заметки — карточки историй. Свойства: «Статус» (Status), «Синопсис» (Text). Свойство «Вселенная» (Relation на `universes`, не более одной цели, без обратной стороны) появляется вместе с базой «Вселенные» и записывается как `universePropertyId`.                                                                    |
| `characters` | `Персонажи`       | При создании мастерской | Досье действующих лиц. Заготовка `characters`: «Истории» (Relation на `stories`, без ограничения числа, без обратной стороны; ID — `storiesPropertyId`), «Значимость» (Select: Главные / Второстепенные / Эпизодические), «Портрет» (Files), шаблон досье с разделами «Основное», «Характеристика», «Внешность», «Биография».                      |
| `locations`  | `Локации`         | При создании мастерской | Места действия. Заготовка `locations`: «Истории» (Relation на `stories`, как у персонажей), «Тип» (Select: Город / Район / Место / Природа), «Изображение» (Files), шаблон описания.                                                                                                                                                               |
| `universes`  | `Вселенные`       | Ленивое (W11)           | Карточки вымышленных миров/сеттингов. Свойства: «Описание» (Text), «Изображение» (Files).                                                                                                                                                                                                                                                          |
| `arcs`       | `Арки`            | Ленивое (W11)           | Сюжетные линии (W8). Свойства: «Истории» (Relation на `stories`, multiple), «Персонажи» (Relation на `characters`, multiple; ID — `charactersPropertyId`), «Тип» (Select: Линия персонажа / Сюжетная / Мини-арка), «Статус» (Status), «Метка» (Select с цветом).                                                                                   |
| `anchors`    | `Якоря`           | Ленивое (W11)           | Закреплённые ключевые события мира и историй (W8). Свойства: «Истории» (Relation на `stories`, multiple), «Участники» (Relation на `characters`, multiple), «Арки» (Relation на `arcs`, multiple; только если база арок уже есть, иначе добавляется позже), «Вселенная» (Relation на `universes`, не более одной цели; так же), «Описание» (Text). |
| `notes`      | `Заметки`         | Ленивое (W11)           | Заметки автора мастерской (W7). Свойство: «Истории» (Relation на `stories`, multiple). Организуется блокнотами через подпапки.                                                                                                                                                                                                                     |
| `custom`     | Любое имя         | По действию автора      | Авторские разделы («Организации», «Бестиарий», «Артефакты»). Как у любого раздела мира, в базе есть «Истории».                                                                                                                                                                                                                                     |

### Ленивое создание (W11)

Базы «Вселенные», «Арки», «Якоря» и «Заметки» не загромождают диск при создании новой мастерской:

- В интерфейсе боковой панели их блоки присутствуют всегда.
- Сама папка и манифест базы создаются автоматически в момент добавления первой записи
  в соответствующий раздел (или при явном нажатии «Создать базу»).
- Создание базы выполняется журналируемой операцией `create_workshop_section`; первая запись
  создаётся следующим шагом. Для «Вселенных» та же операция добавляет «Вселенную» в базу «Истории»
  (§6).

## 5. Модель истории и файл настроек `amby-story.json` (W3, W4)

История — это супер-заметка с прикреплённой базой текста.

- **Карточка истории:** `<Мастерская>/Истории/<Имя истории>/<Имя истории>.md` — файл строки общей базы «Истории». Не входит в собственную базу текста.
- **Манифест базы текста:** `<Мастерская>/Истории/<Имя истории>/<Имя истории>.json` — описывает прикреплённую базу страниц текста.
- **Файл настроек текста:** `<Мастерская>/Истории/<Имя истории>/amby-story.json` — описывает уровни структуры текста, доступные форматы страниц и системные свойства.

### Frontmatter карточки истории

Карточка — обычная заметка со служебными полями; значения записываются как строки YAML в двойных
кавычках с экранированием (так же, как `amby-title` у строк баз), поэтому кавычка, обратная черта или
двоеточие в названии не ломают frontmatter:

```yaml
---
amby-id: "01JAY000000000000000000002" # ULID заметки-карточки
amby-title: "Дом О'Брайена" # отображаемое название (W10)
amby-story-id: "01JAY000000000000000000001" # storyId из amby-story.json
---
```

`amby-story-id` связывает карточку с файлом настроек в той же папке; сейчас его пишет только создание
истории, а чтение и сверку при обнаружении модуль не выполняет — ключ нужен для будущего восстановления
карточки (`storyMissingMainFile`) и не должен меняться вручную. Байты карточки заносятся в журнал
операции, и при возобновлении записываются те же байты. Название истории — это имя папки и файлов,
поэтому оно проходит ту же проверку имени, что и название раздела: без `/ \ : * ? " < > |`, управляющих
символов, начальной и конечной точки и зарезервированных имён; пробелы по краям обрезаются.

### Содержимое `amby-story.json`

```json
{
  "formatVersion": 3,
  "storyId": "01JAY000000000000000000001",
  "text": {
    "levels": [
      { "id": "01JAY_LVL_1", "icon": "icon:book" },
      { "id": "01JAY_LVL_2", "icon": "icon:bookmark" },
      { "id": "01JAY_LVL_3", "icon": "icon:file-text" }
    ],
    "formats": [
      { "id": "01JAY_FMT_1", "kind": "manuscript" },
      { "id": "01JAY_FMT_2", "kind": "screenplay" },
      { "id": "01JAY_FMT_3", "kind": "comic" },
      { "id": "01JAY_FMT_4", "kind": "note" }
    ],
    "properties": {
      "level": "01JAY_PROP_LEVEL",
      "parent": "01JAY_PROP_PARENT",
      "order": "01JAY_PROP_ORDER",
      "format": "01JAY_PROP_FORMAT",
      "status": "01JAY_PROP_STATUS",
      "anchors": "01JAY_PROP_ANCHORS",
      "arcs": "01JAY_PROP_ARCS"
    }
  }
}
```

### Схемы уровней текста (W4)

Схема уровней выбирается автором при создании истории:

1. **«Роман»** (по умолчанию): Книга → Глава → Сцена (3 уровня).
2. **«Рассказ»**: Страница (1 уровень).
3. **«Комикс»**: Книга → Том → Глава → Страница (4 уровня; термин «Арка» исключён из схемы текста, так как закреплён за сюжетными линиями W8).
4. **«Своя»**: Пользовательский список от 1 до 6 уровней.

Уровни текста реализуются через свойство Select в манифесте базы текста. Идентификаторы `levels[].id` соответствуют ULID вариантов Select. Названия и цвета вариантов хранятся в манифесте базы текста, в `amby-story.json` хранится их иерархический порядок и значки.

### Системные свойства страницы текста истории

| Свойство  | Тип базы        | Назначение                                                                                                                                             |
| --------- | --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `level`   | Select          | Уровень страницы в иерархии произведения.                                                                                                              |
| `parent`  | Relation (self) | Родительская страница той же базы текста (односторонняя связь, maxItems: 1).                                                                           |
| `order`   | Text            | Лексикографический ключ сортировки порядка следования (напр. `"a0"`, `"a1"`).                                                                          |
| `format`  | Select          | Формат страницы (`manuscript`, `screenplay`, `comic`, `note`).                                                                                         |
| `status`  | Status          | Статус готовности (группы `notStarted`, `inProgress`, `done`).                                                                                         |
| `anchors` | Relation        | Необязательно. Связь с общей базой «Якоря» (W9, без числа ограничения, без обратной стороны); свойство появляется, когда база «Якоря» существует (§6). |
| `arcs`    | Relation        | Необязательно. Связь с общей базой «Арки» (W9, так же); появляется, когда существует база «Арки» (§6).                                                 |

## 6. Правила связей и отношений (W5, W6, W8, W9)

### Связи сущностей с историями и вселенными (W5, W6)

**Свойства.** Модуль находит свойства-связи не по названию (автор может его переименовать), а по
ID, записанному в `amby-workshop.json`:

- у записи каждого раздела мира (персонажи, локации, арки, якоря, заметки, авторские разделы)
  `storiesPropertyId` — ID свойства «Истории»: Relation на базу `stories`, без ограничения числа
  целей и **без обратной стороны** (`inversePropertyId: null`). Связь пишется только в заметку
  сущности, карточка истории не правится;
- у записи раздела `stories` `universePropertyId` — ID свойства «Вселенная»: Relation на базу
  `universes`, не более одной цели (`maxItems: 1`), без обратной стороны. Свойство создаётся вместе
  с базой «Вселенные».

Названия свойств задаёт язык интерфейса (`labels` `property:stories`, `property:universe`).
Создание: `create_workshop` — «Истории» у персонажей и локаций; `create_workshop_section` — «Истории»
в любую создаваемую базу мира, а при ленивом создании «Вселенных» — ещё и «Вселенная» в базе
«Истории». Это одна журналируемая операция над несколькими файлами (новая база, манифест
«Историй», файл мастерской); точка фиксации — файл мастерской, при сбое или падении на любом шаге
оба файла возвращаются побайтно.

**Принадлежность.** Сущность в истории, если выполнено хотя бы одно:

1. её «Истории» содержит ID карточки этой истории;
2. любая связь страницы текста **этой истории** указывает на неё («упоминание в тексте»). Читаются
   только строки базы текста самой истории; в заметку сущности упоминание ничего не пишет.

Сущность во вселенной, если она в какой-либо истории, у которой «Вселенная» = эта вселенная.
Сама вселенная считается лежащей в своих историях. «Вся мастерская» — все сущности. Удаление
истории или вселенной ничего не удаляет (W12).

**Навигация (W6).** Переключателя «История | Вселенная» нет. Список в шапке панели задаёт фильтр
для всех частей мира: история, вселенная или «Вся мастерская». Сущность без связи «Истории» и без
упоминания ни в одном тексте показывается только в «Вся мастерская», отдельной группой «Без истории»
в конце. У строки при выборе вселенной или всей мастерской — до двух названий историй и «+N». Те же
правила применяют блоки персонажей и локаций на страницах истории и вселенной.

**Создание из панели.** При выбранной истории сущность создаётся командой `create_workshop_entity`
сразу со связью на карточку истории: значение «Истории» записывается тем же действием, что и сама
заметка. При выбранной вселенной или «Вся мастерская» связь не пишется. Если у раздела нет
`storiesPropertyId`, команда с историей отказывает (`storyLinksUnavailable`), без истории создаёт
страницу как обычно.

**Мастерские без свойств.** Мастерская, созданная до появления этих полей, не мигрируется.
Для раздела без `storiesPropertyId` (или раздела `stories` без `universePropertyId` при уже
существующих «Вселенных») панель предлагает «Связать». Это журналируемая операция
`add_story_links` (по образцу `add_text_status`): `expectedWorkshopRevision`, снимок в истории,
журнал, откат. Если в базе раздела уже есть подходящая связь (на нужную базу, с нужным
ограничением, без обратной стороны), операция принимает её и меняет только файл мастерской;
иначе добавляет свойство и записывает его ID.

### Правило связей глав с якорями и арками (W9)

Поскольку база текста у каждой истории является изолированной базой со своим `databaseId`,
стандартное ядровое свойство Relation с двусторонним `inversePropertyId` не может связать
одну общую базу «Якоря» со всеми отдельными базами текста.

- Связи «глава → якоря» и «глава → арки» сохраняются исключительно в свойствах страниц текста
  конкретной истории: «Якоря» (Relation на базу `anchors`) и «Арки» (Relation на базу `arcs`), без
  обратной стороны и без ограничения числа. Их ID записаны в `amby-story.json` рядом со статусом:
  `text.properties.anchors`, `text.properties.arcs`; модуль находит их только по ID. Если свойство
  удалено из базы, запись в файле считается устаревшей: поле в каталоге пусто, а операция ниже
  заводит свойство заново.
- Обратное отображение («в каких главах участвует якорь/арка») строится запросом по проекции.
- Привязка и отвязка — запись значения свойства страницы (существующая операция правки отношения
  `update_database_relation_value` с полным списком целей страницы, расчёт от строки на экране и
  ревизия строки защищают чужие значения). Значение якоря или арки не пишется в их заметку.

**Свойства самих якорей и арок** (записи раздела в `amby-workshop.json`, необязательные и
аддитивные): у `anchors` — `arcsPropertyId` («Арки», Relation на `arcs`, без обратной стороны) и
`universePropertyId` («Вселенная», Relation на `universes`, `maxItems: 1`, без обратной стороны);
у `arcs` — `charactersPropertyId` («Персонажи», Relation на `characters`). Якорь, связанный со
вселенной, — событие вселенной (W8).

**Ленивое добавление связей.** Базы «Арки», «Якоря» и «Вселенные» появляются в любом порядке (W11),
поэтому недостающие свойства добавляются там, где это одна операция, и по требованию иначе:

- `create_story`, если базы «Якоря» и/или «Арки» уже существуют (и лежат на диске), сразу создаёт
  базу текста с нужными свойствами и записывает их ID в `amby-story.json`;
- создание «Якорей» после «Арок» и «Вселенных» кладёт «Арки» и «Вселенную» в новую базу и записывает
  `arcsPropertyId` и `universePropertyId`; создание «Арок» после «Якорей» тем же журналируемым
  действием добавляет «Арки» в базу «Якоря» (`manifest_write`) и записывает `arcsPropertyId`;
  создание «Арок» записывает ещё `charactersPropertyId`, если база «Персонажи» есть;
- во всех остальных случаях — команда **`ensure_plot_links`** (журналируемая: `operationId`,
  снимок, журнал с исходными байтами манифеста, побайтный откат, повтор с тем же запросом отвечает
  записанным, с другим — `OperationIdReused`). Одна цель — одна база и один файл структуры:
  - `target: "story"` (+ `storyId`, `expectedRevision` — ревизия `amby-story.json`): база текста
    истории и `amby-story.json`; добавляет «Якоря» и «Арки» для тех баз, что существуют;
  - `target: "anchors"` (`expectedRevision` — ревизия `amby-workshop.json`): база «Якоря» и файл
    мастерской; добавляет «Арки» и «Вселенную» для баз, что существуют.

  Подходящее свойство, которое уже есть (Relation на нужную базу, с нужным ограничением и без
  обратной стороны), принимается: пишется только ID. Если нечего добавлять, ничего не пишется и
  ревизия не проверяется (`changed: false`). Точка фиксации — файл структуры; сбой или падение до
  неё возвращает оба файла побайтно. Интерфейс вызывает операцию при первой привязке (перед записью
  значения), если свойства страницы ещё нет.

**Принадлежность и порядок якорей истории.** Якорь и арка относятся к истории так же, как сущность
мира (§6): по связи «Истории» или по привязке к странице текста этой истории. Порядок якорей в
истории (чистая функция модели `orderStoryAnchors`): якорь, привязанный к страницам истории, стоит
там, где стоит самая ранняя из его страниц в порядке дерева текста (обход в глубину); два якоря
одной страницы — в порядке списка на странице. Якоря без страниц этой истории — группа «Впереди» в
ручном порядке автора (`manualOrder` первого вида базы), затем по времени создания и названию.
Якорь двух историй стоит в каждой по её страницам. Ручное переупорядочивание действует только
внутри «Впереди».

**События вселенной и якоря без истории (часть 6б).** Якорь со значением «Вселенная»
(`universePropertyId`) — событие этой вселенной (W8). `create_workshop_entity` принимает
необязательный `universeId` (ID заметки из базы «Вселенные»): только для раздела `anchors`, только если
у раздела есть `universePropertyId` и свойство ещё есть в манифесте, и только для существующей заметки
вселенной; значение пишется той же записью, что и заметка, любое нарушение отказывает до записи
(`storyLinksUnavailable`, для не-якоря — `invalidParent`). Если свойства нет, интерфейс сначала вызывает
`ensure_plot_links` с целью `anchors` и показывает его ошибку, а не пропускает её. Тот же вызов делается
сразу после ленивого создания «Вселенных» при существующих «Якорях» и «Якорей» при существующих
«Вселенных», если у якорей остался недостающий «Арки» или «Вселенная» (чистая `anchorLinksMissing`).
Якорь **без истории** — без связи «Истории», без привязки к странице любого текста и без связи
«Вселенная»; при «Вся мастерская» такие якоря стоят в конце отдельной группой, остальные — в ручном
порядке автора. При выбранной вселенной сверху группа «События вселенной», затем якоря её историй.

## 7. Правило разрешения коллизий имён (W10)

В общей базе мастерской (например, «Якоря» или «Персонажи») разные истории могут содержать
сущности с одинаковыми именами (например, событие «Финал» или персонаж «Алекс»):

1. **Имя файла:** Файловая система требует уникальности путей внутри одной папки. Механизм
   `unique_row_path` автоматически разрешает коллизии добавлением числового суффикса:
   `Финал.md`, `Финал 2.md`, `Финал 3.md`.
2. **Отображаемое имя:** Во frontmatter заметки всегда сохраняется исходное название автора:
   `amby-title: "Финал"`.
3. **Отображение в интерфейсе:** Все представления творческого модуля (дерево рукописи, досье,
   списки связей, поиск, таблицы баз) используют `display_title` (`amby-title`), поэтому
   пользователь везде видит чистое авторское название «Финал» без системных цифровых индексов.
   Путь создания из панели (`create_workshop_entity`) идёт через ту же запись строки, что и
   `create_database_row`, поэтому правило действует для всех общих баз; проверяется тестом
   `two_pages_with_one_title_in_a_shared_database_get_two_files_and_show_one_title`.
4. Разделение сущностей по подпапкам историй внутри общих баз не используется (W10).

## 8. Заметки и блокноты (W7)

- База «Заметки» — общая для мастерской с мульти-связью «Истории» (§6).
- **Блокнот** — подпапка внутри папки базы «Заметки» (`Заметки/Идеи/`), вложенные блокноты
  допустимы (`Заметки/Идеи/Сюжеты/`). Блокноты общие для мастерской, а не для истории. Ничего,
  кроме папки, блокнот не хранит: ни файла, ни записи в `amby-workshop.json`, ни свойства заметки.
- **Принадлежность.** Заметка в блокноте остаётся строкой базы «Заметки»; её место в блокноте —
  `category_path` строки (`["Идеи", "Сюжеты"]`), заметка в корне базы — «без блокнота». Связь
  «Истории» от блокнота не зависит: одна заметка может лежать в блокноте и быть привязана к
  любым историям, перенос в другой блокнот связи не меняет.
- **Что считается блокнотом.** Видимая папка базы, не являющаяся символьной ссылкой, не содержащая
  манифеста другой базы и не являющаяся папкой заметки с вложениями (в ней есть одноимённый
  `<имя>.md`). Скрытые и служебные папки (`.ambd` и др.) в список не попадают. Пустой блокнот —
  блокнот: список блокнотов берётся из папок, а не из `category_path` строк.
- **Чтение списка.** `list_notebooks(databaseId)` (только чтение): папка базы берётся из индекса и
  проверяется на вхождение в хранилище, обход идёт без перехода по ссылкам, не глубже 12 уровней и
  не больше 2000 блокнотов (иначе `truncated`). Для каждого блокнота возвращаются имена от корня
  базы (`segments`), путь на диске и `itemCount` — число элементов прямо в папке кроме блокнотов
  (заметки, их папки с вложениями, любые другие файлы). Скрытые файлы (`.DS_Store`) не считаются.
- **Создание заметки в блокноте.** `create_workshop_entity` принимает необязательный `notebook` —
  имена папок от корня базы (`[]` или отсутствие — корень). До любой записи каждое имя проходит
  проверку имени папки (`normalize_entry_name`; `..`, `/`, скрытые, зарезервированные имена
  отклоняются, имя не должно меняться при обрезке пробелов), каждая папка должна существовать,
  быть обычной видимой папкой-блокнотом внутри базы (после канонизации), а раздел — быть базой
  «Заметки». Иначе `InvalidName` / `InvalidParent`, на диске ничего не меняется. Связь с историей
  пишется в той же записи, что и заметка. Повторяющееся имя получает `Имя 2.md` внутри папки
  блокнота (одинаковые имена в разных блокнотах не переименовываются).
- **Создание, переименование и удаление блокнота — обычные файловые операции хранилища**
  (создание папки, переименование с обновлением ссылок, перемещение, корзина), собственных путей
  записи у модуля нет:
  - имя блокнота проверяется панелью до записи по тем же правилам, что имя папки; совпадение с
    соседним блокнотом без учёта регистра — отказ;
  - переименование — только на месте, внутри базы;
  - перенос заметки между блокнотами — перемещение файла с обновлением ссылок; совпадение имени
    в целевом блокноте — отказ без перезаписи; открытая заметка остаётся открытой по новому пути
    (тот же путь, что у дерева файлов);
  - **удаление блокнота не удаляет заметок.** До любой записи проверяется, что в блокноте и во
    вложенных лежат только заметки (по числу элементов на диске и строк базы), что список заметок
    полон и что при переносе в родителя ни одно имя не совпадёт (ни с заметкой, ни с соседним
    блокнотом, ни между переносимыми). Если не так — отказ с перечислением названий. Иначе после
    подтверждения заметки переносятся в родителя, список папок читается заново и только если
    блокнот и вложенные пусты, папка уходит в корзину (восстановимая; удаление «насовсем» из
    настроек для этого заменяется корзиной хранилища). Оборвавшийся перенос папку не трогает:
    каждая заметка лежит либо на старом, либо на новом месте, пользователь получает сообщение.
- Сквозные темы заметок оформляются стандартными тегами (`tags` во frontmatter).

## 9. Обработка повреждений и проектов прежних форматов

### Проекты прежнего формата v2

- Папка, содержащая файл `amby-project.json` (формат v2):
  - Диагностируется как `legacyProjectFormat` («проект прежнего формата»).
  - Доступна в Amby как обычные папки и базы данных.
  - Творческий модуль v3 не изменяет, не конвертирует и не удаляет файлы проектов v2.
  - Миграция с v2 на v3 не выполняется (пользователей v2 нет).

### Повреждённые или неполные данные в мастерской

1. **Пропавшая база (`missingDatabase`):**
   Если папка базы, указанная в `amby-workshop.json`, удалена с диска:
   - Мастерская остаётся полностью работоспособной.
   - Раздел помечается предупреждением в каталоге диагностик.
   - Пользователю предлагается воссоздать базу или удалить запись о разделе.
2. **История без главного файла (`storyMissingMainFile`):**
   Если папка `Истории/<Имя>/` существует и содержит страницы, но файл `<Имя>.md` отсутствует:
   - Страницы текста доступны для чтения через базу текста.
   - В каталоге мастерской генерируется диагностика `storyMissingMainFile`.
   - Модуль предлагает создать карточку истории заново с привязкой существующей базы.
3. **Повреждённый манифест базы (`brokenManifest`):**
   Если файл `<Имя>.json` или `amby-story.json` содержит невалидный JSON:
   - Механизм границ (`discovery.rs`) изолирует повреждённую базу от остального дерева.
   - Мастерская продолжает работать для всех остальных исправных баз.
   - Диагностика указывает точный путь к повреждённому файлу.
4. **Удаление истории или вселенной (W12):**
   Удаление карточки истории или вселенной очищает только саму историю/вселенную.
   Сущности мира (персонажи, локации, арки, якоря), ссылавшиеся на неё, **не удаляются**:
   неразрешённые ULID сохраняются во frontmatter и автоматически восстанавливаются при
   создании сущности с тем же ID или очищаются автором вручную.

## 10. Rust-слой и транзакционность

- Все изменения мастерской выполняются с фиксацией в журнале восстановления
  `.amby/recovery/creative/<operationId>.json`.
- Создание мастерской, истории или раздела атомарно: сбой на промежуточном шаге
  полностью откатывает созданные папки и манифесты до исходного состояния хранилища. Операции,
  меняющие манифест существующей базы (`add_text_status`, `update_text_levels`, `add_story_links`,
  `ensure_plot_links`, создание «Вселенных», создание «Арок» при существующих «Якорях»), записывают в журнал исходные байты манифеста и возвращают их при откате.
- Возобновление операции с тем же `operationId` после падения берёт запланированные ID и байты
  файла мастерской из журнала (как `create_story`): тот же набор баз, те же ID свойств.
- Повтор команды с тем же `operationId` возвращает сохранённый результат (`replayed`).
- Проекция мастерской кешируется в SQLite-индексе и автоматически обновляется
  по событиям файлового наблюдателя (`watcher`).

## 11. Досье и сюжет страницы

Досье — оформление редактора, а не данные: рамка вокруг редактора заметки (`editorFrame` оболочки),
в которой блоки считаются по запросу и ничего не пишут в заметку. Рамка одна и та же структура для
любой заметки, поэтому редактор не пересоздаётся, когда приходит ответ; блоки стоят справа, а на узкой
панели (меньше 640 пикселей) уходят под текст. Бэкенд опрашивается, только если в хранилище есть
мастерские, и только заметка раздела мастерской получает оформление.

**Страница раздела мира** (всё, кроме текста, заметок и «Историй»): шапка со значением ключевых
свойств, блоки «Разделы» (заголовки страницы), «Появляется в» (страницы текста, ссылающиеся на неё) и
«Связи» (остальные связи в обе стороны). Дополнительно, по роли раздела:

- **Персонаж** — блок «Арки»: арки, у которых «Персонажи» (`charactersPropertyId` раздела `arcs`)
  содержит персонажа, с цветом арки (`arcColor`). Это входящие ссылки через это свойство, поэтому их
  нет и в «Связях»; без арок блока нет.
- **Арка** — блоки «Якоря арки» и «Главы». Якоря арки — якоря, у которых «Арки» (`arcsPropertyId`
  раздела `anchors`) содержит арку; их порядок задаёт текст каждой истории (`orderStoryAnchors`), истории
  идут по каталогу (при нескольких — с названием истории), якоря, не привязанные ни к одной странице,
  стоят в конце под подписью «Не привязаны к тексту». «Главы» — страницы текста, где привязана арка, по
  историям в порядке текста; если страниц больше одной, подпись охвата «от … до …» (первая и последняя).
  «Появляется в» у арки заменено «Главами», а входящие связи от якорей не повторяются в «Связях».

**Страница текста истории**, если в мастерской есть база якорей или арок, получает блок «Сюжет страницы»
по образцу досье: «Якоря этой страницы» (в порядке списка на странице), «Отталкиваемся от» (ближайший
привязанный якорь до страницы в порядке текста, не считая якорей самой страницы), «Должны прийти к»
(ближайший после; если таких нет — первый якорь «Впереди») и «Арки» страницы с цветом. Якорь стоит там,
где стоит самая ранняя из его страниц (`pageNeighbours`). Пустой блок показывается тихой строкой; весь
блок не показывается, если в мастерской нет ни одного якоря и ни одной арки. Каждый пункт открывает
свою страницу. Данные берутся из тех же строк, что читает панель (база текста, якоря, арки), и из
