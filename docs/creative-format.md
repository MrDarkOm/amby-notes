# Творческий модуль Amby: контракт формата (редакция 2)

Дата: 6 октября 2026 года.
Версия формата: 2 (черновик).
Статус: **контракт; слой Rust реализован** (обнаружение проектов, создание проекта и
раздела — этап 1, часть 1), интерфейс и блок `text` ещё нет. Заменяет редакцию 1 от 4 октября
(общая база «Сущности», оверлеи типов, база «Связи», `.amby-creative/`). Формат
редакции 1 не выпускался и существовал только в незакоммиченном коде, поэтому
миграция с него не предусмотрена.

План работ и этапы — в [плане переработки](creative-module-claude-plan.md).

## 1. Принципы

1. **Заметка — данные, модуль — оформление.** Каждая сущность (персонаж, глава,
   локация) — обычная Markdown-заметка с полями во frontmatter. Каждый раздел —
   обычная база Amby. Без модуля всё остаётся читаемым: папки, заметки, таблицы.
2. **Папка — это проект.** Проект целиком лежит в одной папке и переносится
   вместе с ней. Ссылки внутри проекта — по стабильным ID, пути в файле структуры
   — относительные.
3. **Один источник каждого факта.** Значения и связи — во frontmatter через
   контракт баз ([database-format.md](database-format.md)). Файл структуры хранит
   только устройство проекта, но не значения. SQLite — перестраиваемая проекция.
4. **Модуль не создаёт параллельных механизмов.** Текст пишется существующим
   редактором и автосохранением, разделы показываются компонентами баз, запись
   идёт через Rust и существующие атомарные операции.

## 2. Виды проектов и вложенность

Проект бывает двух видов. Вид задаётся полем `kind` в файле структуры.

| Вид          | Назначение                                                                            |
| ------------ | ------------------------------------------------------------------------------------- |
| `collection` | Сборник: группирует истории. Если у него есть свои разделы мира — это вселенная.      |
| `story`      | История: текст произведения и её собственные разделы. Может лежать в сборнике или вне |

Принадлежность истории сборнику определяется **вложенностью папок**: история
принадлежит ближайшему сборнику выше по дереву. Отдельного списка историй в
сборнике нет — второй список разошёлся бы с файловой системой.

```text
Palooverse/                    ← сборник-вселенная
├── amby-project.json          (kind: collection)
├── Персонажи/                 ← общий раздел вселенной (база)
├── Локации/
├── История первая/
│   ├── amby-project.json      (kind: story)
│   ├── Текст/                 ← книги, арки, главы (база)
│   └── Заметки/
└── История вторая/
    └── …

Одиночные истории/             ← сборник без общих разделов
├── amby-project.json
└── Рассказ/
    ├── amby-project.json
    └── …
```

Правила:

- Сборник в сборнике в версии 2 не поддерживается: вложенный сборник
  показывается с диагностикой, данные не трогаются.
- История вне сборника — самостоятельный проект.
- Раздел принадлежит тому проекту, в чьей папке лежит. История видит свои
  разделы и разделы своего сборника.
- В истории, лежащей во вселенной, новый персонаж по умолчанию создаётся в общем
  разделе вселенной; «только в этой истории» — явный выбор при создании (если у
  истории есть собственный раздел той же роли).

### Переносимость

- Сборник переносится целиком без потерь.
- История, вынесенная из вселенной, сохраняет текст и свои разделы. Связи с
  общими сущностями становятся неразрешёнными, но ID остаются в заметках; при
  возврате связи восстанавливаются. Модуль не удаляет и не «чистит» такие ID.
- Копирование проекта внутри того же хранилища создаёт конфликт ID. До появления
  отдельной операции «дублировать с новыми ID» копия диагностируется существующими
  правилами дубликатов и не считается вторым проектом.

## 3. Файл структуры `amby-project.json`

Лежит в корне папки проекта. Имя не совпадает с manifest базы (`ambd.json`),
файл не скрытый.

```json
{
  "formatVersion": 2,
  "kind": "story",
  "projectId": "01JA…",
  "name": "MoleHills",
  "icon": "…",
  "tags": ["Комикс"],
  "groups": [
    { "id": "work", "name": "Произведение" },
    { "id": "world", "name": "Мир" }
  ],
  "sections": [
    {
      "id": "text",
      "role": "text",
      "group": "work",
      "databaseId": "db_…",
      "path": "Текст"
    },
    { "id": "notes", "role": "notes", "group": "work", "databaseId": "db_…", "path": "Заметки" },
    {
      "id": "characters",
      "role": "characters",
      "group": "world",
      "databaseId": "db_…",
      "path": "Персонажи"
    }
  ],
  "text": {
    "levels": [
      { "id": "01JA…", "icon": "…" },
      { "id": "01JB…", "icon": "…" },
      { "id": "01JC…", "icon": "…" },
      { "id": "01JD…", "icon": "…" }
    ],
    "formats": [
      { "id": "01JE…", "kind": "manuscript" },
      { "id": "01JF…", "kind": "screenplay" },
      { "id": "01JG…", "kind": "comic" },
      { "id": "01JH…", "kind": "note" }
    ],
    "properties": {
      "level": "prop_…",
      "parent": "prop_…",
      "order": "prop_…",
      "format": "prop_…"
    }
  }
}
```

| Поле            | Смысл                                                                                                                                                                                    |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `formatVersion` | Целое. Больше известного — проект открывается только для чтения, файл не переписывается.                                                                                                 |
| `kind`          | `collection` или `story`.                                                                                                                                                                |
| `projectId`     | Стабильный ID проекта. Имя и путь папки идентификатором не являются.                                                                                                                     |
| `name`, `icon`  | Отображение. `icon` — закодированное значение `IconValue`.                                                                                                                               |
| `tags`          | Свободные метки проекта («Комикс», «Рассказы»).                                                                                                                                          |
| `groups`        | Заголовки групп боковой панели и их порядок.                                                                                                                                             |
| `sections`      | Разделы в порядке показа. Источник идентичности — `databaseId`; `path` — относительная подсказка.                                                                                        |
| `text`          | Только для `story`: уровни произведения (порядок и значок; `id` — вариант Select), форматы страниц (`id` варианта Select и `kind`) и роли системных свойств базы текста по `propertyId`. |

Правила:

- Неизвестные поля сохраняются при записи. Порядок ключей и форматирование файла
  модуль не гарантирует, содержимое — гарантирует.
- Если `databaseId` найден по другому пути, раздел работает, а `path`
  обновляется при следующем явном изменении структуры. Если база не найдена —
  раздел показывается как отсутствующий, запись о нём не удаляется.
- База в папке проекта, не перечисленная в `sections`, остаётся обычной базой.
  Модуль предлагает добавить её как раздел, но не добавляет сам.
- Файл изменяется только явными действиями со структурой (создать/убрать/
  переупорядочить раздел, изменить уровни). Открытие проекта файл не пишет.

## 4. Разделы

Раздел — обычная база Amby: папка с манифестом `<имя папки>.json` (`ambd.json` — прежнее
имя, читается), видами и заметками.

- `role` — необязательная подсказка модулю, какие поверхности предложить:
  `text`, `notes`, `characters`, `locations`, `anchors`. Раздел без роли — пользовательский.
  **Якоря** (`anchors`) — ключевые, неизменные события истории: обычная база без особых
  свойств, которую вкладка «Произведения» показывает отдельной частью; в базовый набор не входит,
  создаётся действием «Раздел» (или кнопкой в самой части «Якоря»).
- Базовый набор новой истории: **Текст, Заметки, Персонажи, Локации.** Базовый
  набор сборника-вселенной: Персонажи, Локации. Простой сборник создаётся без
  разделов.
- Остальное создаёт автор действием «Раздел»: пустой раздел или заготовка
  (например, «Организации», «Предметы»). Заготовка задаёт только иконку и
  стартовые свойства; дальше это обычная база без особого статуса.
- **Заготовки** (`preset` у `create_project_section`; базовые «Персонажи» и «Локации»
  создаются с ними): `characters` (иконка, «Значимость» — Select «Главные / Второстепенные /
  Эпизодические», «Портрет» — файлы, вид «Галерея» с группировкой по значимости, шаблон «Досье»
  с заголовками «Основное», «Характеристика», «Внешность», «Биография»), `locations` («Тип» —
  Город / Район / Место / Природа, «Изображение», галерея по типу, шаблон «Описание», «История»),
  `organizations` и `items` («Значимость», «Изображение», галерея по значимости, шаблон
  «Описание», «История»). Заготовка сработает один раз при создании: свойства, вид и шаблон
  строятся вместе с манифестом (`build_new_property`, ID заданы заранее), файл шаблона
  `.ambd/templates/<id>.json` пишется следом и откатывается вместе с базой; дальше раздел —
  обычная база без особого статуса. Названия берутся из `labels` (`preset:*`, `importance:*`,
  `kind:*`, `heading:*`, `view:gallery`, `template:dossier`) по языку интерфейса.
- Категории внутри раздела («Районы / Города», «Good / СМИ») — сохранённые виды
  базы с фильтром, а не сущности модуля.
- Убрать раздел из проекта — значит убрать запись из `sections`. База и заметки
  остаются на диске. Удаление базы — отдельное действие через корзину.

## 5. Текст произведения

Раздел с ролью `text` — одна база, в которой лежат все единицы текста истории.

- **Уровни.** Уровень заметки — значение свойства Select. Отдельного идентификатора
  у уровня нет: `text.levels[].id` — это `id` варианта этого Select, выданный при
  создании свойства существующей операцией `create_database_property` (ULID).
  Имя и цвет уровня живут только в варианте базы и переименовываются там же;
  в `levels` хранятся порядок уровней и `icon`. Порядок задаёт массив `levels`
  («Книга → Арка → Глава → Страница», «Книга → Глава → Сцена» и т. п.), а не порядок
  вариантов в Select. Имена «Книга», «Арка», «Глава», «Страница» существуют только
  в шаблоне создания (токены локализации) и после создания в формате не хранятся.
- **Висячий уровень.** Если вариант удалён в базе, запись в `levels` остаётся и
  показывается как висячая с диагностикой; значения в заметках не правятся, а
  вариант, которого нет в `levels`, — обычное значение без уровня в дереве.
  Модуль ничего не удаляет и не «чинит» сам.
- **Родитель** — одиночная односторонняя связь на заметку той же базы.
  Родитель не хранит список детей.
- **Порядок** — текстовый дробный ключ в самой заметке, сравнивается побайтно;
  при равенстве — по `amby-id`. Перенос меняет только переносимую заметку.
  Заметка без ключа идёт после заметок с ключами.
- **Формат** — свойство Select, выбирается при создании страницы. Варианты, как и
  у уровней, получают ULID при создании свойства; название и цвет хранит только база.
  Соответствие варианта и вида формата записывается в `text.formats` при создании
  свойства: `[{ "id": <id варианта>, "kind": "manuscript" | "screenplay" | "comic" | "note" }]`.
  Вариант без записи в `formats` и запись с неизвестным `kind` ведут себя как
  обычный текст; неизвестный `kind` при записи сохраняется. Удалённый в базе вариант
  оставляет висячую запись в `formats` с диагностикой, заметки не правятся.
  В версии 2 поведение по `kind` не ветвится: все форматы открываются обычным
  редактором, а ветвление появится вместе со сценарным редактором (этап 5).
- Циклы «родитель → потомок» отклоняются до записи.
- **Уровень родителя.** Родитель стоит на уровне выше страницы по порядку `text.levels`:
  тот же или более глубокий уровень отклоняется (`ParentLevelNotShallower`), пропуск уровня
  разрешён (Книга → Глава). Уровень, которого нет в `levels` (значение пусто или вариант
  удалён), не сравнивается и ничего не ограничивает. Проверка стоит в `create_text_page` и
  `move_text_page`; сначала проверяется цикл.
- Имена и расположение файлов от порядка и уровня не зависят: перестановка
  ничего не переименовывает и не перемещает.

Сборка рукописи — последовательное чтение по дереву и экспорт в Markdown как
новый файл; исходные заметки не изменяются.

## 6. Связи

1. **Поля-связи** — обычные свойства Relation баз: персонаж → организации, глава
   → персонажи, глава → локация. Работают между разделами истории и сборника.
   Для полей, где одна цель участвует в сотнях источников (персонажи главы),
   предпочтительна односторонняя связь; обратный список строится запросом.
2. **Отношения с подписью** между произвольными сущностями («враг», «владеет»).
   Сейчас Relation указывает ровно на одну базу (`targetDatabaseId`). Отношения
   требуют связи на несколько баз в ядре; до этой доработки они **не входят в
   формат** и не имитируются отдельным хранилищем.

Карта связей показывает оба вида и для каждого ребра знает источник (свойство
и заметку). Раскладка карты (координаты, скрытые карточки) — данные вида, а не
факты; их место хранения определяется на этапе карты.

## 7. Обнаружение и запись

- Проекты находит Rust-индекс при сканировании хранилища и по событиям watcher;
  интерфейс не читает файлы структуры сам.
- Создание проекта и раздела — одна backend-операция: preflight путей и
  коллизий, создание баз и свойств, запись файла структуры последним шагом,
  восстановление после сбоя. Повтор операции не создаёт второй набор.
- Все записи идут через `src/lib/storage.ts` и Rust с действующими проверками
  ревизий и поколения хранилища. Модуль не правит Markdown строковыми операциями.
- Шаблон новой заметки применяется механизмом шаблонов баз.

## 8. Зависимости и отключение

- Модуль зависит от `amby.databases`: без баз не активируется; отключение баз
  сначала останавливает модуль.
- При выключенном модуле файлы, базы и заметки доступны как обычно. Файл
  структуры не удаляется и не изменяется.

## 10. Досье сущности

Досье — оформленное представление одной заметки раздела мира; отдельного
файла или формата у него нет.

- **Шапка:** портрет или обложка, название, ключевые свойства. Источник —
  свойства базы и frontmatter заметки.
- **Текст:** тело заметки. Разделы досье («Основное», «Характеристика», «Внешность», «Биография»)
  — обычные заголовки в этом же файле; модуль показывает их оглавлением и
  позволяет перейти к разделу. Подстраницы для разделов не создаются: одна
  сущность — один файл.
- **Стартовые разделы** задаёт шаблон базы. Для «Персонажей» по умолчанию:
  «Основное», «Характеристика», «Внешность», «Биография». Автор меняет шаблон обычными средствами
  баз; изменение шаблона не переписывает существующие заметки.
- **Визуал:** свойство-файлы; изображения лежат во вложениях самой заметки и
  переносятся вместе с ней.
- **«Появляется в»** и **«Связи»** вычисляются запросом и в заметку не
  записываются. Блоки стоят справа от текста и переносятся под него на узком окне.

Поля страницы текста (участники, место, статус, синопсис) показываются в
существующей правой инфо-панели, а не в отдельной колонке модуля. Карточка в
виде «Карточки» показывает номер, название, синопсис и статус.

## 11. Реализация слоя Rust (этап 1, часть 1)

Код — `src-tauri/src/project/` ([карта](../src-tauri/src/project/MAP.md)), порт —
`src/lib/storage/project-port.ts`. Что зафиксировано при реализации:

- **Обнаружение.** Индекс (таблицы `project_*` в SQLite) перестраивается при открытии
  хранилища, командой `refresh_projects` и после каждого создания. Watcher только шлёт
  событие `project:changed` (файл структуры или папка создана/удалена/переименована);
  интерфейс вызывает `refresh_projects`. Раздел сопоставляется с базой по `databaseId` при
  чтении каталога: найденный по другому пути — `moved`, ненайденный — `missing`, запись
  остаётся в файле.
- **Диагностики** (`code`): `duplicateProjectId`, `nestedCollection`, `storyInsideStory`,
  `invalidProjectFile`, `unsupportedFormatVersion`, `invalidSection`,
  `duplicateSectionId`, `unsafeSectionPath`, `symlinkIgnored`. История внутри истории
  допускается как самостоятельный проект с предупреждением; её сборник — ближайший сборник
  выше.
- **Создание.** Одна операция с `operationId`: preflight без записи, журнал
  `.amby/recovery/projects/<operationId>.json`, папка, базы разделов (с ID, зафиксированными
  в журнале), файл структуры последним — это точка фиксации. До неё незавершённое
  откатывается: удаляется только то, что создала операция (манифест — только если байты
  совпадают с пересчитанными по журналу, папка — только пустая); иначе `RecoveryRequired`,
  журнал сохраняется. При открытии хранилища то же делается после сбоя процесса;
  неочищаемый журнал уходит в `quarantine/`. Тот же `operationId` с тем же запросом
  возвращает записанный ответ (`replayed`), с другим — `OperationIdReused`.
- **Состав.** Базовые разделы задаёт Rust: история — «Текст», «Заметки» (группа «Произведение»),
  «Персонажи», «Локации» (группа «Мир»); сборник с флагом `baseSections` — «Персонажи»,
  «Локации»; простой сборник — без разделов. Названия по умолчанию русские, интерфейс
  передаёт свои через `labels` (`section:<роль>`, `group:<id>`), потому что имя раздела —
  имя папки на диске.
- **Блок `text`.** База «Текст» создаётся вместе с четырьмя системными свойствами —
  «Уровень» (Select), «Родитель» (односторонняя связь на ту же базу, не более одного),
  «Порядок» (текст), «Формат» (Select) — и блок `text` пишется в файл структуры в той же
  операции: при `create_project` для истории с базовыми разделами и при `create_project_section`
  с ролью `text` (одна на историю). Варианты уровней (Книга, Арка, Глава, Страница) и форматов
  (Рукопись, Сценарий, Комикс, Заметка) получают ULID; `text.levels[].id` и `text.formats[].id` —
  это ID вариантов, имён в файле нет. Имена свойств, уровней и форматов берутся из
  `labels` (`property:*`, `level:*`, `format:*`) по активному языку. Определения свойств строятся
  той же функцией, что и `create_database_property` (`build_new_property`), с заранее
  выбранными ID: так повтор и очистка после сбоя пересчитывают тот же манифест побайтно.
- **Каталог.** `ProjectSummary.text` сопоставляет блок с базой при чтении: у уровня и формата
  имя и цвет берутся из варианта, состояние `ok`, `dangling` (вариант удалён в базе) или
  `unresolved` (базы текста нет). Висячая запись остаётся в файле, заметки не правятся,
  в каталог добавляется диагностика `danglingTextLevel`, `danglingTextFormat` или
  `missingTextProperty`. Неизвестный `kind` формата передаётся как есть.
- **Страницы.** `create_text_page` создаёт заметку сразу со значениями уровня, формата,
  порядка и родителя (одна запись, страница не существует «наполовину»); без формата берётся
  вариант `manuscript`. `move_text_page` меняет у одной страницы родителя и порядок одной
  записью через `apply_value_batch` (ревизия страницы, история, повтор по `operationId`) и
  отказывает до записи, если страница стала бы собственным предком. Ключ порядка (`0-9A-Za-z`,
  до 64 знаков) считает вызывающий. Цикл, попавший в файлы иначе (внешняя правка, выбор в
  таблице), дерево обязано пережить: проверка есть только у этих двух команд.
- **Раздел в проекте.** `create_project_section` требует `expectedProjectRevision`, пишет
  файл через снимок истории и сохраняет неизвестные поля и BOM; роль `text` допустима
  только у истории и только одна. Для проекта неизвестной версии — `ProjectReadOnly`, внутри
  него ничего создавать нельзя (`ParentProjectReadOnly`).

## 12. Интерфейс (этап 1, часть 2)

Код — `src/components/workspace/creative/` ([карта](../src/components/workspace/creative/MAP.md)).

- **Боковой раздел «Мастерская»** — обычная панель модуля (id `creative`) с деревом:
  сборники → истории → группы → разделы, значок предупреждения у раздела без базы, замок
  у проекта только для чтения, сворачиваемая сводка диагностик. Действия: «Новый проект» в
  шапке, «+» у проекта (новая история в сборнике, раздел в истории), «Раздел» внутри.
- **Страница проекта** — вкладка `creative:<projectId>`: шапка (значок, название, вид, метки),
  вкладки «Обзор» и разделов с подписями групп, обзор с карточками разделов (у сборника ещё
  и истории). Раздел показывается обычным рабочим пространством базы без своего заголовка.
  Раздел с ненайденной базой объясняется на месте, проект неизвестной версии открыт только
  для чтения.
- **Создание** — диалоги «Новый проект» (история, вселенная, сборник; внутри сборника
  только история) и «Новый раздел» (название, группа, тип). Названия базовых разделов и
  групп берутся из ключей `creative.sections.*` и `creative.groups.*` по активному языку и
  передаются как `labels`; на русском и английском это «Текст/Text», «Заметки/Notes»,
  «Персонажи/Characters», «Локации/Locations», «Произведение/Work», «Мир/World».
- **Группировка галереи** (R9) — галерея группируется по свойству Select или Status как
  доска: заголовок группы с числом карточек всего вида, карточки группы, «Загрузить ещё» по
  группе; порядок, скрытие и пустые группы — из настроек группы. Это доработка баз
  (`gallery-lanes-view.tsx`), доступная всем базам, а не только модулю.
- **Не сделано:** список баз в папке проекта, не внесённых в `sections`, переименование
  проекта и смена значка со страницы, контекст страницы текста (этап 2, интерфейс).

## 13. Досье и заготовки (хвосты этапа 1)

- **Заготовки** — §4. Код: `project/presets.rs`, `project/props.rs`; в диалоге «Новый раздел» вместо
  роли выбирается заготовка (роль ставится сама: «Персонажи» → `characters`).
- **Досье** — оформление страницы раздела мира, не отдельный файл. Страница получает его, когда
  её база — раздел проекта с ролью, кроме `text` и `notes` (`worldSectionOf`). Под названием
  показываются портрет (первое изображение из свойства-файлов) и ключевые свойства с названиями
  (до 8 непустых, без файлов и связей), справа от текста — «Разделы» (заголовки `##` страницы,
  переход к ним), «Появляется в» (страницы текста истории, чьи связи указывают на страницу) и
  «Связи» (остальные связи в обе стороны, по свойствам); на узкой панели блоки уходят под текст.
  Ширину решает ширина самой панели, а не окна. Блоки считаются запросом
  `list_note_references` по проекции и в заметку не пишутся. Стартовые заголовки приходят
  из шаблона базы («Досье»): `create_database_row` применяет его, как любой шаблон.
- Обычная заметка вне проектов, заметка текста и заметка раздела «Заметки» ничего не получают;
  без проектов бэкенд не опрашивается. Редактор для страницы с досье не пересоздаётся при ответе:
  `DossierFrame` стоит вокруг него и не меняет структуру дерева.
