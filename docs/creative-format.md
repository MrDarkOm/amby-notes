## 1. Архитектурные принципы

1. **Заметка — данные, модуль — проекция и оформление.** Каждая сущность (персонаж, локация,
   глава, арка, якорь, заметка) — обычный Markdown-файл с метаданными во frontmatter.
   Каждый раздел — стандартная база данных Amby ([database-format.md](database-format.md)).
   Без творческого модуля хранилище остаётся полностью читаемым и структурированным.
2. **Папка мастерской — переносимая единица (W1).** Все данные мастерской находятся внутри
   единой корневой папки мастерской с маркером `amby-workshop.json`. В хранилище одна
   мастерская: та, чья папка названа в настройке модуля (§2.1). Другие найденные маркеры —
   диагностика, их данные не читаются и не меняются; связи между мастерскими не поддерживаются.
3. **Плоская организация баз и принадлежность через связи (W2, W5).** В мастерской нет
   вложенности папок проектов и вселенных. Базы сущностей мира, историй, арок, якорей и заметок
   расположены на одном верхнем уровне мастерской. Принадлежность сущности историям или вселенной
   задаётся исключительно свойствами-связями (Relation по ULID заметки).
4. **История как прикреплённая база текста (W3).** Единственное место физической вложенности —
   папка текста истории: карточка истории является строкой общей базы «Истории», а сама папка —
   прикреплённой базой данных страниц текста. Внутри папки истории других вложенных папок нет.
5. **Один источник фактов и атомарность.** Значения и связи хранятся во frontmatter заметок.
   Файл маркера мастерской и файл настроек текста истории фиксируют конфигурацию и схемы,
   но не дублируют значения свойств. Запись ведётся через Rust-слой атомарных операций
   с журналированием и поддержкой отката.

## 2. Структура каталогов мастерской

```text
Мастерская/
├── amby-workshop.json          ← маркер мастерской (формат v3)
├── Вселенные/                  ← база вселенных (создаётся при инициализации, W11)
├── Истории/                    ← база историй (базовая)
│   └── Моя история/            ← прикреплённая база текста истории (W3)
│       ├── Моя история.md      ← карточка истории (строка базы «Истории»)
│       ├── Моя история.json    ← манифест базы текста истории
│       ├── amby-story.json     ← настройки текста (уровни, форматы, свойства)
│       ├── Глава 1.md          ← страницы текста (строки базы текста)
│       └── Глава 2.md …
├── Персонажи/                  ← база персонажей (базовая)
├── Локации/                    ← база локаций (базовая)
├── Арки/                       ← база сюжетных линий (при инициализации, W11)
├── Якоря/                      ← база якорных событий (при инициализации, W11)
└── Заметки/                    ← общая база заметок (при инициализации, W11)
    └── Идеи/                   ← блокнот (подпапка базы «Заметки», W7)
```

В папке каждой базы лежит её манифест `<Имя>.json` (формат баз, [database-format.md](database-format.md));
заготовки персонажей, локаций и авторских разделов добавляют шаблон досье в служебную папку `.ambd`.
Названия папок баз — по языку интерфейса в момент инициализации.
Журналы операций лежат не в мастерской, а в хранилище: `.amby/recovery/creative/<operationId>.json`
(§10); это данные восстановления, а не кеш.

### 2.1. Где лежит мастерская (W1, этап 8)

- **Настройка.** `moduleSettings.creative.workshopPath` в `workspace.json` хранилища: путь папки
  мастерской относительно корня хранилища, `/`-разделитель, без `.`, `..` и скрытых частей. Не
  задана — по умолчанию папка в корне хранилища с локализованным названием («Мастерская» /
  «Workshop»). Выбор — диалогом выбора папки приложения; Rust (`resolve_workshop_folder`)
  канонизирует выбранный путь и принимает только существующую папку строго внутри хранилища
  (ссылка наружу — то место, куда она ведёт, то есть отказ). Смена настройки файлы не перемещает.
- **Какая мастерская активна.** Каталог по-прежнему перечисляет все найденные маркеры. Активна та, чья
  папка совпадает с настройкой (без учёта регистра). Если настройка не задана и найдена ровно одна
  мастерская — она активна, и настройка сама не пишется; из нескольких — лежащая в папке по умолчанию.
  Остальные находки — диагностика `otherWorkshop` (интерфейс; в Rust её нет): их файлы не
  читаются в панель и не меняются.
- **Нет активной.** Панель показывает путь и кнопку «Инициализировать» (`init_workshop`, §10). Папка,
  которой нет или которая пуста (допустимы только `.DS_Store`, `Thumbs.db`, `desktop.ini`), принимается;
  всё остальное — `Failed { code: "folderNotEmpty" }` до первой записи, чтобы не смешивать мастерскую
  с чужими файлами. Родитель пути должен существовать.

## 3. Файл-маркер мастерской `amby-workshop.json`

Файл находится в корне папки мастерской. Мастерской считается любая папка вне скрытых и служебных
папок (имя с точки, `.ambd` и др.) с файлом `amby-workshop.json`, у которого есть `formatVersion` (целое от 1),
`workshopId` (идентификатор из букв, цифр, `-` и `_` до 128 знаков; на деле ULID) и непустое `name`
(до 200 знаков). Файл больше 1 МиБ, не JSON или без этих полей — диагностика `invalidWorkshopFile`,
мастерская не показывается. Папка с повторным `workshopId` (копия) — `duplicateWorkshopId`, вторая
не считается мастерской. Символьная ссылка вместо файла — `symlinkIgnored`.

```json
{
  "formatVersion": 3,
  "workshopId": "01JAX000000000000000000001",
  "name": "Моя мастерская",
  "icon": "icon:feather",
  "tags": ["Фэнтези", "Комиксы"],
  "sections": [
    {
      "id": "stories",
      "role": "stories",
      "name": "Истории",
      "databaseId": "01JAX000000000000000000002",
      "path": "Истории"
    },
    {
      "id": "characters",
      "role": "characters",
      "name": "Персонажи",
      "databaseId": "01JAX000000000000000000003",
      "path": "Персонажи",
      "storiesPropertyId": "01JAX000000000000000000005"
    },
    {
      "id": "locations",
      "role": "locations",
      "name": "Локации",
      "databaseId": "01JAX000000000000000000004",
      "path": "Локации",
      "storiesPropertyId": "01JAX000000000000000000006"
    }
  ]
}
```

### Спецификация полей `amby-workshop.json`

| Поле            | Тип            | Назначение                                                                                                                                      |
| --------------- | -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `formatVersion` | целое (`3`)    | Версия формата. Любое другое значение (в том числе выше 3) — `unsupportedFormatVersion`: мастерская открыта только для чтения, файл не пишется. |
| `workshopId`    | ULID string    | Стабильный уникальный идентификатор мастерской.                                                                                                 |
| `name`          | string         | Отображаемое название мастерской.                                                                                                               |
| `icon`          | string         | Необязательно: закодированное значение иконки (`IconValue`); при очистке ключ удаляется.                                                        |
| `tags`          | string[]       | Пользовательские теги мастерской.                                                                                                               |
| `sections`      | SectionEntry[] | Список зарегистрированных разделов мастерской (базовых, ленивых и авторских), порядок задаёт автор.                                             |

**Ревизия файла не хранится в нём.** Это SHA-256 сырых байтов файла вместе с BOM, её считает код
(`raw_revision`); интерфейс получает её как `fileRevision` и возвращает как
`expectedWorkshopRevision` (проверка «сравнить и записать»). Любая правка файла вне приложения
меняет ревизию, и следующая запись получает `RevisionConflict`.

### Элемент `sections`

```typescript
type SectionEntry = {
  id: string // Уникальный ID раздела: равен role у ролей кроме custom, у custom — ULID
  role: WorkshopRole // Предопределённая системная роль или "custom"
  name: string // Название папки/базы (по умолчанию — id)
  databaseId: string // ULID базы данных Amby
  path: string // Подсказка: путь к папке базы от корня мастерской (по умолчанию — name)
  storiesPropertyId?: string // ID свойства «Истории» в этой базе (разделы мира), см. §6
  universePropertyId?: string // ID свойства «Вселенная» (у разделов `stories` и `anchors`), см. §6
  arcsPropertyId?: string // ID свойства «Арки» (только у раздела `anchors`), см. §6
  charactersPropertyId?: string // ID свойства «Персонажи» (только у раздела `arcs`), см. §6
}

type WorkshopRole =
  "stories" | "characters" | "locations" | "universes" | "arcs" | "anchors" | "notes" | "custom"
```

Запись без `id`, `role` или `databaseId` пропускается (`invalidSection`), повтор `id` — `duplicateSectionId`,
пустой путь, начало с `/`, обратная косая или часть пути `.` / `..` — `unsafeSectionPath`; остальные записи работают.
`path` — только подсказка: каталог сопоставляет раздел с базой по `databaseId`, поэтому перенесённая база
работает (раздел `moved`), а исчезнувшая показывается как `missing` (§9). Роль, кроме `custom`, в мастерской
одна (`sectionAlreadyExists`). Название раздела (и мастерской, и истории) становится именем папки и проходит проверку
`normalize_entry_name`: без пробелов по краям, до 100 знаков, без `/ \ : * ? " < > |` и управляющих
знаков, без начальной и конечной точки, без имён устройств Windows (`CON`, `COM1`…), служебных папок и
имён `amby-workshop.json`, `amby-story.json`, `amby-project.json`. Совпадение с соседней папкой
считается без учёта регистра (`PathCollision`). Теги — до 32, каждый до 64 знаков; значок — до 256 КиБ.

Поля `storiesPropertyId`, `universePropertyId`, `arcsPropertyId` и `charactersPropertyId` необязательны и **аддитивны**: версия формата
остаётся 3, а мастерская без них читается и работает (привязка к историям тогда недоступна, пока
не выполнена операция `add_story_links`, §6). Неизвестные поля файла и записей разделов
сохраняются при любой перезаписи.

## 4. Базы данных мастерской и их роли

Все разделы мастерской являются стандартными базами Amby. Роль определяет специализированное
отображение в интерфейсе модуля (панель, галереи, досье, фильтры).

| Роль         | База по умолчанию | Создание                | Назначение и стартовые свойства                                                                                                                                                                                                                                                                                                                    |
| ------------ | ----------------- | ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `stories`    | `Истории`         | При инициализации       | Каталог всех произведений. Заметки — карточки историй. Свойства: «Статус» (Status), «Синопсис» (Text). Свойство «Вселенная» (Relation на `universes`, не более одной цели, без обратной стороны) появляется вместе с базой «Вселенные» и записывается как `universePropertyId`.                                                                    |
| `characters` | `Персонажи`       | При инициализации       | Досье действующих лиц. Заготовка `characters`: «Истории» (Relation на `stories`, без ограничения числа, без обратной стороны; ID — `storiesPropertyId`), «Значимость» (Select: Главные / Второстепенные / Эпизодические), «Портрет» (Files), шаблон досье с разделами «Основное», «Характеристика», «Внешность», «Биография».                      |
| `locations`  | `Локации`         | При инициализации       | Места действия. Заготовка `locations`: «Истории» (Relation на `stories`, как у персонажей), «Тип» (Select: Город / Район / Место / Природа), «Изображение» (Files), шаблон описания.                                                                                                                                                               |
| `universes`  | `Вселенные`       | При инициализации (W11) | Карточки вымышленных миров/сеттингов. Свойства: «Описание» (Text), «Изображение» (Files).                                                                                                                                                                                                                                                          |
| `arcs`       | `Арки`            | При инициализации (W11) | Сюжетные линии (W8). Свойства: «Истории» (Relation на `stories`, multiple), «Персонажи» (Relation на `characters`, multiple, без обратной стороны; только если база персонажей есть; ID — `charactersPropertyId`), «Тип» (Select: Линия персонажа / Сюжетная / Мини-арка), «Статус» (Status). Цвет арки не хранится: он считается по её ID.        |
| `anchors`    | `Якоря`           | При инициализации (W11) | Закреплённые ключевые события мира и историй (W8). Свойства: «Истории» (Relation на `stories`, multiple), «Участники» (Relation на `characters`, multiple), «Арки» (Relation на `arcs`, multiple; только если база арок уже есть, иначе добавляется позже), «Вселенная» (Relation на `universes`, не более одной цели; так же), «Описание» (Text). |
| `notes`      | `Заметки`         | При инициализации (W11) | Заметки автора мастерской (W7). Свойство: «Истории» (Relation на `stories`, multiple). Организуется блокнотами через подпапки.                                                                                                                                                                                                                     |
| `custom`     | Любое имя         | По действию автора      | Авторские разделы («Организации», «Бестиарий», «Артефакты»). Как у любого раздела мира, в базе есть «Истории».                                                                                                                                                                                                                                     |

### Создание баз (W11, изменено на этапе 8)

Все семь баз (Истории, Персонажи, Локации, Вселенные, Арки, Якоря, Заметки) создаёт инициализация
одной журналируемой операцией `init_workshop` вместе со всеми связями между ними (§6): «Истории» у
каждой базы мира, «Вселенная» у Историй и у Якорей, «Арки» у Якорей, «Персонажи» у Арок. ID всех
свойств записаны в файле мастерской. Точка фиксации — файл мастерской; при сбое или падении на любом
шаге всё созданное возвращается, повтор создаёт один набор.

Ленивое создание остаётся как восстановление: мастерская, созданная на этапах 2–7, может не иметь
части баз и связей. Панель определяет это без записи (`workshopGaps`) и показывает плашку «Создать
недостающие разделы»; кнопка вызывает `complete_workshop`, которая существующими журналируемыми
операциями (`create_workshop_section`, `add_story_links`, `ensure_plot_links`) добавляет только
отсутствующее: Вселенные, Арки, Якоря, Заметки — в таком порядке, чтобы каждая база взяла связи у уже
созданных; затем «Истории» разделам мира, «Вселенную» историям и якорям, «Арки» якорям, «Якоря» и
«Арки» текстам историй. Занятая чужой папкой база и заблокированная база пропускаются (`skipped`),
остальное делается. Повтор ничего не пишет. Раздел автора (`custom`) создаётся по действию автора
(`create_workshop_section`).

## 5. Модель истории и файл настроек `amby-story.json` (W3, W4)

История — это супер-заметка с прикреплённой базой текста.

- **Карточка истории:** `<Мастерская>/Истории/<Имя истории>/<Имя истории>.md` — файл строки общей базы «Истории». Не входит в собственную базу текста.
- **Манифест базы текста:** `<Мастерская>/Истории/<Имя истории>/<Имя истории>.json` — описывает прикреплённую базу страниц текста.
- **Файл настроек текста:** `<Мастерская>/Истории/<Имя истории>/amby-story.json` — описывает уровни структуры текста, доступные форматы страниц и системные свойства.

### Frontmatter карточки истории

Карточка — обычная заметка со служебными полями; значения записываются как строки YAML в двойных
кавычках с экранированием (так же, как `amby-title` у строк баз), поэтому кавычка, обратная черта или
двоеточие в названии не ломают frontmatter:

```yaml
---
amby-id: "01JAY000000000000000000002" # ULID заметки-карточки
amby-title: "Дом О'Брайена" # отображаемое название (W10)
amby-story-id: "01JAY000000000000000000001" # storyId из amby-story.json
---
```

`amby-story-id` связывает карточку с файлом настроек в той же папке; сейчас его пишет только создание
истории, а чтение и сверку при обнаружении модуль не выполняет — ключ нужен для будущего восстановления
карточки (`storyMissingMainFile`) и не должен меняться вручную. Байты карточки заносятся в журнал
операции, и при возобновлении записываются те же байты. Название истории — это имя папки и файлов,
поэтому оно проходит ту же проверку имени, что и название раздела (§3). Каталог показывает название
из `amby-title` карточки, а при его отсутствии — имя папки; `cardNoteId` берётся из `amby-id`.

История найдена, если в папке `Истории/<Имя>/` есть три файла: `<Имя>.md`, `<Имя>.json` и
`amby-story.json` (`storyId` из него уникален по хранилищу). Без карточки история не показывается
(`storyMissingMainFile`), без `amby-story.json` — тоже (`storyMissingConfigFile`); манифест базы текста, которого нет или который
не разбирается, оставляет историю в каталоге без базы текста (`brokenManifest`, §9). Скрытые папки
и файлы в папке «Истории» (имя с точки) пропускаются.

### Содержимое `amby-story.json`

```json
{
  "formatVersion": 3,
  "storyId": "01JAY000000000000000000001",
  "text": {
    "levels": [
      { "id": "01JAY_LVL_1", "icon": "icon:book" },
      { "id": "01JAY_LVL_2" },
      { "id": "01JAY_LVL_3" }
    ],
    "formats": [
      { "id": "01JAY_FMT_1", "kind": "manuscript" },
      { "id": "01JAY_FMT_2", "kind": "screenplay" },
      { "id": "01JAY_FMT_3", "kind": "comic" },
      { "id": "01JAY_FMT_4", "kind": "note" }
    ],
    "properties": {
      "level": "01JAY_PROP_LEVEL",
      "parent": "01JAY_PROP_PARENT",
      "order": "01JAY_PROP_ORDER",
      "format": "01JAY_PROP_FORMAT",
      "status": "01JAY_PROP_STATUS",
      "anchors": "01JAY_PROP_ANCHORS",
      "arcs": "01JAY_PROP_ARCS"
    }
  }
}
```

Идентификаторы в примере условные; настоящие — ULID. Уровни создаются без `icon` (значок задаётся
в настройках истории, `update_text_levels`). Свойство `status` записывается при создании истории; у
историй, созданных до него, его нет, и `add_text_status` добавляет его позже. `anchors` и `arcs`
записываются, только если свойства существуют (§6). Неизвестные поля файла сохраняются при любой
перезаписи; BOM и окончания строк тоже. Файл больше 1 МиБ считается повреждённым.

### Схемы уровней текста (W4)

Схема уровней выбирается автором при создании истории:

1. **«Роман»** (по умолчанию): Книга → Глава → Сцена (3 уровня).
2. **«Рассказ»**: Страница (1 уровень).
3. **«Комикс»**: Книга → Том → Глава → Страница (4 уровня; термин «Арка» исключён из схемы текста, так как закреплён за сюжетными линиями W8).
4. **«Своя»**: Пользовательский список от 1 до 6 уровней.

Названия уровней отправляет интерфейс на активном языке (`textLevels`, от 1 до 6 непустых названий, без
повторов без учёта регистра; запрос проверяется до записи). Уровни текста реализуются через свойство
Select в манифесте базы текста. Идентификаторы `levels[].id` соответствуют ULID вариантов Select.
Названия и цвета вариантов хранятся в манифесте базы текста, в `amby-story.json` — их иерархический
порядок и значки. Каталог сверяет записи файла с вариантами при каждом чтении: удалённый в базе
вариант остаётся в файле, показывается как `dangling` (диагностика `danglingTextLevel` /
`danglingTextFormat`), страницы с ним не правятся. Уровень можно переименовать, переставить или
добавить; убрать (даже неиспользуемый) нельзя — отказ `UnknownTextLevel` до записи.

### Системные свойства страницы текста истории

| Свойство  | Тип базы        | Назначение                                                                                                                                             |
| --------- | --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `level`   | Select          | Уровень страницы в иерархии произведения.                                                                                                              |
| `parent`  | Relation (self) | Родительская страница той же базы текста (односторонняя связь, maxItems: 1).                                                                           |
| `order`   | Text            | Лексикографический ключ сортировки порядка следования (напр. `"a0"`, `"a1"`).                                                                          |
| `format`  | Select          | Формат страницы (`manuscript`, `screenplay`, `comic`, `note`).                                                                                         |
| `status`  | Status          | Статус готовности (группы `notStarted`, `inProgress`, `done`).                                                                                         |
| `anchors` | Relation        | Необязательно. Связь с общей базой «Якоря» (W9, без числа ограничения, без обратной стороны); свойство появляется, когда база «Якоря» существует (§6). |
| `arcs`    | Relation        | Необязательно. Связь с общей базой «Арки» (W9, так же); появляется, когда существует база «Арки» (§6).                                                 |

**Правила страниц.** Страница создаётся (`create_text_page`) значениями и заметкой одной записью; ключ
порядка — строка из букв и цифр до 64 знаков (дробный индекс base-62, сравнение побайтовое; иначе
`InvalidOrderKey`). Перемещение (`move_text_page`) пишет родителя и ключ одной записью. Родитель должен стоять на
уровне мельче страницы (`ParentLevelNotShallower`; уровень можно пропустить, например сцена прямо под
книгой), петля отклоняется первой (`ParentCycle`), устаревшая страница — `RevisionConflict` с ревизией на
диске. Страница без родителя, с пропавшим родителем или в петле от внешней правки показывается в
корне. Интерфейс заранее проверяет те же правила (`planMove`) и не даёт ход, который отклонит бэкенд.

## 6. Правила связей и отношений (W5, W6, W8, W9)

### Связи сущностей с историями и вселенными (W5, W6)

**Свойства.** Модуль находит свойства-связи не по названию (автор может его переименовать), а по
ID, записанному в `amby-workshop.json`:

- у записи каждого раздела мира (персонажи, локации, арки, якоря, заметки, авторские разделы)
  `storiesPropertyId` — ID свойства «Истории»: Relation на базу `stories`, без ограничения числа
  целей и **без обратной стороны** (`inversePropertyId: null`). Связь пишется только в заметку
  сущности, карточка истории не правится;
- у записи раздела `stories` `universePropertyId` — ID свойства «Вселенная»: Relation на базу
  `universes`, не более одной цели (`maxItems: 1`), без обратной стороны. Свойство создаётся вместе
  с базой «Вселенные».

Названия свойств задаёт язык интерфейса (`labels` `property:stories`, `property:universe`).
Создание: `init_workshop` — «Истории» у каждой базы мира и «Вселенная» у «Историй» (все базы уже
известны операции, так что ни одна связь не добавляется позже); `create_workshop_section` (раздел автора
и восстановление) — «Истории» в создаваемую базу мира, а при создании «Вселенных» в мастерской без них —
ещё и «Вселенная» в базе «Истории». Это одна журналируемая операция над несколькими файлами (новая база, манифест
«Историй», файл мастерской); точка фиксации — файл мастерской, при сбое или падении на любом шаге
оба файла возвращаются побайтно.

**Принадлежность.** Сущность в истории, если выполнено хотя бы одно:

1. её «Истории» содержит ID карточки этой истории;
2. любая связь страницы текста **этой истории** указывает на неё («упоминание в тексте»). Читаются
   только строки базы текста самой истории; в заметку сущности упоминание ничего не пишет.

Сущность во вселенной, если она в какой-либо истории, у которой «Вселенная» = эта вселенная.
Сама вселенная считается лежащей в своих историях. «Отдельные истории» — всё, что не входит ни в одну
вселенную: истории без значения «Вселенная» и сущности, которые лежат хотя бы в одной такой истории или
не лежат ни в одной; сущность, лежащая и в истории вселенной, и в отдельной истории, видна в обоих
охватах. Удаление истории или вселенной ничего не удаляет (W12).

**Навигация (W6).** Переключателя «История | Вселенная» нет; осей две. Внизу панели, под «Создать», —
карточка вселенных: её список начинается с постоянного пункта «Отдельные истории» (это не вселенная, он
есть всегда и выбран по умолчанию), затем вселенные из базы «Вселенные» (названия берутся из строк базы) и
действие «Новая вселенная». Выбранная вселенная — охват: её истории и всё, что к ним относится, плюс её
события; «Отдельные истории» — охват отдельных историй. Вверху — карточка историй: «Все истории» (все
истории охвата) или одна из историй охвата; выбранная история сужает охват до себя. Приоритет: история >
вселенная > отдельные истории; режима «вся мастерская» нет. Если выбранная история не входит в новый охват
или удалена, она сбрасывается на «Все истории»; удалённая вселенная — на «Отдельные истории». Выбор
запоминается по хранилищу (`story`: «all» или ID истории, `universe`: «standalone» или ID вселенной;
«Вселенные» в списке мира не показываются). Сущность без связи «Истории» и без упоминания ни в одном тексте
показывается только в «Отдельных историях», отдельной группой «Без истории» в конце. У строки при выборе
вселенной или всех историй — до двух названий историй и «+N». Те же правила применяют блоки персонажей
и локаций на страницах истории и вселенной.

**Создание из панели.** При выбранной истории сущность создаётся командой `create_workshop_entity`
сразу со связью на карточку истории: значение «Истории» записывается тем же действием, что и сама
заметка. При выбранной вселенной или «Отдельных историях» без выбранной истории связь не пишется. Если у раздела нет
`storiesPropertyId`, команда с историей отказывает (`storyLinksUnavailable`), без истории создаёт
страницу как обычно.

**История, созданная во вселенной, получает связь сразу.** Если при создании истории из панели выбрана
вселенная, после `create_story` в строку-карточку истории в базе «Истории» записывается «Вселенная» =
выбранная вселенная (`update_database_relation_value`, полный список целей, ревизия строки читается заново).
Если у раздела историй ещё нет `universePropertyId`, сначала выполняется `add_story_links`. Это отдельная запись
после создания: её сбой не откатывает историю, она остаётся (видна в «Отдельных историях»), а панель сообщает
причину. При выбранных «Отдельных историях» связь не пишется.

**Мастерские без свойств.** Мастерская, созданная до появления этих полей, не мигрируется.
Для раздела без `storiesPropertyId` (или раздела `stories` без `universePropertyId` при уже
существующих «Вселенных») панель предлагает «Связать». Это журналируемая операция
`add_story_links` (по образцу `add_text_status`): `expectedWorkshopRevision`, снимок в истории,
журнал, откат. Если в базе раздела уже есть подходящая связь (на нужную базу, с нужным
ограничением, без обратной стороны), операция принимает её и меняет только файл мастерской;
иначе добавляет свойство и записывает его ID.

### Правило связей глав с якорями и арками (W9)

Поскольку база текста у каждой истории является изолированной базой со своим `databaseId`,
стандартное ядровое свойство Relation с двусторонним `inversePropertyId` не может связать
одну общую базу «Якоря» со всеми отдельными базами текста.

- Связи «глава → якоря» и «глава → арки» сохраняются исключительно в свойствах страниц текста
  конкретной истории: «Якоря» (Relation на базу `anchors`) и «Арки» (Relation на базу `arcs`), без
  обратной стороны и без ограничения числа. Их ID записаны в `amby-story.json` рядом со статусом:
  `text.properties.anchors`, `text.properties.arcs`; модуль находит их только по ID. Если свойство
  удалено из базы, запись в файле считается устаревшей: поле в каталоге пусто, а операция ниже
  заводит свойство заново.
- Обратное отображение («в каких главах участвует якорь/арка») строится запросом по проекции.
- Привязка и отвязка — запись значения свойства страницы (существующая операция правки отношения
  `update_database_relation_value` с полным списком целей страницы, расчёт от строки на экране и
  ревизия строки защищают чужие значения). Значение якоря или арки не пишется в их заметку.

**Свойства самих якорей и арок** (записи раздела в `amby-workshop.json`, необязательные и
аддитивные): у `anchors` — `arcsPropertyId` («Арки», Relation на `arcs`, без обратной стороны) и
`universePropertyId` («Вселенная», Relation на `universes`, `maxItems: 1`, без обратной стороны);
у `arcs` — `charactersPropertyId` («Персонажи», Relation на `characters`). Якорь, связанный со
вселенной, — событие вселенной (W8).

**Ленивое добавление связей.** Базы «Арки», «Якоря» и «Вселенные» появляются в любом порядке (W11),
поэтому недостающие свойства добавляются там, где это одна операция, и по требованию иначе:

- `create_story`, если базы «Якоря» и/или «Арки» уже существуют (и лежат на диске), сразу создаёт
  базу текста с нужными свойствами и записывает их ID в `amby-story.json`;
- создание «Якорей» после «Арок» и «Вселенных» кладёт «Арки» и «Вселенную» в новую базу и записывает
  `arcsPropertyId` и `universePropertyId`; создание «Арок» после «Якорей» тем же журналируемым
  действием добавляет «Арки» в базу «Якоря» (`manifest_write`) и записывает `arcsPropertyId`;
  создание «Арок» записывает ещё `charactersPropertyId`, если база «Персонажи» есть;
- во всех остальных случаях — команда **`ensure_plot_links`** (журналируемая: `operationId`,
  снимок, журнал с исходными байтами манифеста, побайтный откат, повтор с тем же запросом отвечает
  записанным, с другим — `OperationIdReused`). Одна цель — одна база и один файл структуры:
  - `target: "story"` (+ `storyId`, `expectedRevision` — ревизия `amby-story.json`): база текста
    истории и `amby-story.json`; добавляет «Якоря» и «Арки» для тех баз, что существуют;
  - `target: "anchors"` (`expectedRevision` — ревизия `amby-workshop.json`): база «Якоря» и файл
    мастерской; добавляет «Арки» и «Вселенную» для баз, что существуют.

  Подходящее свойство, которое уже есть (Relation на нужную базу, с нужным ограничением и без
  обратной стороны), принимается: пишется только ID. Если нечего добавлять, ничего не пишется и
  ревизия не проверяется (`changed: false`). Точка фиксации — файл структуры; сбой или падение до
  неё возвращает оба файла побайтно. Интерфейс вызывает операцию при первой привязке (перед записью
  значения), если свойства страницы ещё нет.

**Принадлежность и порядок якорей истории.** Якорь и арка относятся к истории так же, как сущность
мира (§6): по связи «Истории» или по привязке к странице текста этой истории. Порядок якорей в
истории (чистая функция модели `orderStoryAnchors`): якорь, привязанный к страницам истории, стоит
там, где стоит самая ранняя из его страниц в порядке дерева текста (обход в глубину); два якоря
одной страницы — в порядке списка на странице. Якоря без страниц этой истории — группа «Впереди» в
ручном порядке автора (`manualOrder` первого вида базы), затем по времени создания и названию.
Якорь двух историй стоит в каждой по её страницам. Ручное переупорядочивание действует только
внутри «Впереди».

**События вселенной и якоря без истории (часть 6б).** Якорь со значением «Вселенная»
(`universePropertyId`) — событие этой вселенной (W8). `create_workshop_entity` принимает
необязательный `universeId` (ID заметки из базы «Вселенные»): только для раздела `anchors`, только если
у раздела есть `universePropertyId` и свойство ещё есть в манифесте, и только для существующей заметки
вселенной; значение пишется той же записью, что и заметка, любое нарушение отказывает до записи
(`storyLinksUnavailable`, для не-якоря — `invalidParent`). Если свойства нет, интерфейс сначала вызывает
`ensure_plot_links` с целью `anchors` и показывает его ошибку, а не пропускает её. Тот же вызов делается
сразу после ленивого создания «Вселенных» при существующих «Якорях» и «Якорей» при существующих
«Вселенных», если у якорей остался недостающий «Арки» или «Вселенная» (чистая `anchorLinksMissing`).
Якорь **без истории** — без связи «Истории», без привязки к странице любого текста и без связи
«Вселенная»; в «Отдельных историях» такие якоря стоят в конце отдельной группой, перед ними — якоря
отдельных историй в ручном порядке автора; события вселенных там не показываются. При выбранной вселенной
сверху группа «События вселенной», затем якоря её историй.

## 7. Правило разрешения коллизий имён (W10)

В общей базе мастерской (например, «Якоря» или «Персонажи») разные истории могут содержать
сущности с одинаковыми именами (например, событие «Финал» или персонаж «Алекс»):

1. **Имя файла:** Файловая система требует уникальности путей внутри одной папки. Механизм
   `unique_row_path` автоматически разрешает коллизии добавлением числового суффикса:
   `Финал.md`, `Финал 2.md`, `Финал 3.md`.
2. **Отображаемое имя:** Во frontmatter заметки всегда сохраняется исходное название автора:
   `amby-title: "Финал"`.
3. **Отображение в интерфейсе:** Все представления творческого модуля (дерево рукописи, досье,
   списки связей, поиск, таблицы баз) используют `display_title` (`amby-title`), поэтому
   пользователь везде видит чистое авторское название «Финал» без системных цифровых индексов.
   Путь создания из панели (`create_workshop_entity`) идёт через ту же запись строки, что и
   `create_database_row`, поэтому правило действует для всех общих баз; проверяется тестом
   `two_pages_with_one_title_in_a_shared_database_get_two_files_and_show_one_title`.
4. Разделение сущностей по подпапкам историй внутри общих баз не используется (W10).

## 8. Заметки и блокноты (W7)

- База «Заметки» — общая для мастерской с мульти-связью «Истории» (§6).
- **Блокнот** — подпапка внутри папки базы «Заметки» (`Заметки/Идеи/`), вложенные блокноты
  допустимы (`Заметки/Идеи/Сюжеты/`). Блокноты общие для мастерской, а не для истории. Ничего,
  кроме папки, блокнот не хранит: ни файла, ни записи в `amby-workshop.json`, ни свойства заметки.
- **Принадлежность.** Заметка в блокноте остаётся строкой базы «Заметки»; её место в блокноте —
  `category_path` строки (`["Идеи", "Сюжеты"]`), заметка в корне базы — «без блокнота». Связь
  «Истории» от блокнота не зависит: одна заметка может лежать в блокноте и быть привязана к
  любым историям, перенос в другой блокнот связи не меняет.
- **Что считается блокнотом.** Видимая папка базы, не являющаяся символьной ссылкой, не содержащая
  манифеста другой базы и не являющаяся папкой заметки с вложениями (в ней есть одноимённый
  `<имя>.md`). Скрытые и служебные папки (`.ambd` и др.) в список не попадают. Пустой блокнот —
  блокнот: список блокнотов берётся из папок, а не из `category_path` строк.
- **Чтение списка.** `list_notebooks(databaseId)` (только чтение): папка базы берётся из индекса и
  проверяется на вхождение в хранилище, обход идёт без перехода по ссылкам, не глубже 12 уровней и
  не больше 2000 блокнотов (иначе `truncated`). Для каждого блокнота возвращаются имена от корня
  базы (`segments`), путь на диске и `itemCount` — число элементов прямо в папке кроме блокнотов
  (заметки, их папки с вложениями, любые другие файлы). Скрытые файлы (`.DS_Store`) не считаются.
- **Создание заметки в блокноте.** `create_workshop_entity` принимает необязательный `notebook` —
  имена папок от корня базы (`[]` или отсутствие — корень). До любой записи каждое имя проходит
  проверку имени папки (`normalize_entry_name`; `..`, `/`, скрытые, зарезервированные имена
  отклоняются, имя не должно меняться при обрезке пробелов), каждая папка должна существовать,
  быть обычной видимой папкой-блокнотом внутри базы (после канонизации), а раздел — быть базой
  «Заметки». Иначе `InvalidName` / `InvalidParent`, на диске ничего не меняется. Связь с историей
  пишется в той же записи, что и заметка. Повторяющееся имя получает `Имя 2.md` внутри папки
  блокнота (одинаковые имена в разных блокнотах не переименовываются).
- **Создание, переименование и удаление блокнота — обычные файловые операции хранилища**
  (создание папки, переименование с обновлением ссылок, перемещение, корзина), собственных путей
  записи у модуля нет:
  - имя блокнота проверяется панелью до записи по тем же правилам, что имя папки; совпадение с
    соседним блокнотом без учёта регистра — отказ;
  - переименование — только на месте, внутри базы;
  - перенос заметки между блокнотами — перемещение файла с обновлением ссылок; совпадение имени
    в целевом блокноте — отказ без перезаписи; открытая заметка остаётся открытой по новому пути
    (тот же путь, что у дерева файлов);
  - **удаление блокнота не удаляет заметок.** До любой записи проверяется, что в блокноте и во
    вложенных лежат только заметки (по числу элементов на диске и строк базы), что список заметок
    полон и что при переносе в родителя ни одно имя не совпадёт (ни с заметкой, ни с соседним
    блокнотом, ни между переносимыми). Если не так — отказ с перечислением названий. Иначе после
    подтверждения заметки переносятся в родителя, список папок читается заново и только если
    блокнот и вложенные пусты, папка уходит в корзину (восстановимая; удаление «насовсем» из
    настроек для этого заменяется корзиной хранилища). Оборвавшийся перенос папку не трогает:
    каждая заметка лежит либо на старом, либо на новом месте, пользователь получает сообщение.
- Сквозные темы заметок оформляются стандартными тегами (`tags` во frontmatter).

## 9. Прежний формат и повреждённые данные

### Проекты формата v2 (`amby-project.json`, вложенная модель)

Миграции нет: пользователей формата v2 не было. Прежний формат — **только диагностика**.

- Файл `amby-project.json` в любой видимой папке хранилища даёт диагностику `legacyProjectFormat`
  (предупреждение, путь файла). Панель показывает такие папки одной свёрнутой строкой внизу, а не
  баннером. Код дальше этот файл не читает: сборники, истории и разделы v2 не
  становятся мастерскими, переключателя области и пометки «не в тексте» больше нет.
- Папки, заметки и базы такого проекта остаются обычными: они видны в дереве файлов и открываются как
  любые базы. Модуль v3 их не изменяет, не переписывает и не удаляет.
- Имя `amby-project.json` зарезервировано: так нельзя назвать новую папку мастерской, раздела или
  истории.

### Диагностики каталога

Обнаружение (`discovery.rs`) только читает: оно ничего не чинит и не пишет. Каждая находка — запись
`ProjectDiagnostic { code, severity, path, workshopId?, storyId?, detail? }`; интерфейс показывает счётчик
и раскрывающийся список (`creative.diagnostic.<code>`, неизвестный код выводится как есть).

| Код                                                         | Важность       | Когда                                                                                                                       | Что происходит                                                                                      |
| ----------------------------------------------------------- | -------------- | --------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| `legacyProjectFormat`                                       | предупреждение | найден `amby-project.json` (v2)                                                                                             | файл не читается и не меняется, см. выше                                                            |
| `symlinkIgnored`                                            | предупреждение | `amby-workshop.json` — символическая ссылка                                                                                 | мастерская не показывается                                                                          |
| `unreadableWorkshopFile`                                    | ошибка         | файл не читается                                                                                                            | мастерская не показывается                                                                          |
| `invalidWorkshopFile`                                       | ошибка         | не JSON, больше 1 МиБ, нет `formatVersion` / `workshopId` / `name`                                                          | мастерская не показывается                                                                          |
| `duplicateWorkshopId`                                       | ошибка         | второй файл с тем же `workshopId` (копия папки)                                                                             | первая по глубине и пути остаётся, копия не показывается                                            |
| `otherWorkshop` (интерфейс)                                 | предупреждение | найден маркер не той мастерской, что названа настройкой (§2.1)                                                              | мастерская не используется, её файлы не читаются в панель и не меняются                             |
| `unsupportedFormatVersion`                                  | предупреждение | `formatVersion` не 3                                                                                                        | мастерская только для чтения (`WorkshopReadOnly` при записи)                                        |
| `invalidSection`, `duplicateSectionId`, `unsafeSectionPath` | предупреждение | запись `sections` неполная, повторная или с небезопасным путём                                                              | запись пропускается, остальные работают                                                             |
| `storyMissingMainFile`                                      | предупреждение | в папке истории нет `<Имя>.md`, но есть `amby-story.json` или `<Имя>.json`                                                  | история не показывается; страницы остаются обычными заметками (дерево файлов)                       |
| `storyMissingConfigFile`                                    | предупреждение | есть карточка, нет `amby-story.json`                                                                                        | история не показывается                                                                             |
| `brokenManifest`                                            | ошибка         | `amby-story.json` не читается или не разбирается — **или** манифест базы текста `<Имя>.json` отсутствует или не разбирается | в первом случае история не показывается; во втором показывается без базы текста (`databaseId` пуст) |
| `duplicateStoryId`                                          | ошибка         | второй `amby-story.json` с тем же `storyId`                                                                                 | копия не показывается                                                                               |
| `missingTextProperty`                                       | предупреждение | свойство из блока `text` (`detail` — ключ) не найдено в базе                                                                | поле каталога пусто; запись в файле не трогается                                                    |
| `danglingTextLevel`, `danglingTextFormat`                   | предупреждение | вариант Select из `text.levels` / `text.formats` удалён в базе                                                              | запись остаётся в файле, вариант `dangling`; страницы с ним не правятся                             |

Повреждение изолировано: остальные мастерские, истории и базы работают. Автоматического восстановления нет;
`amby-story-id` карточки пока не используется для воссоздания файла настроек (§5).

### Пропавшая или перенесённая база раздела

Каталог сопоставляет раздел с базой по `databaseId` (через `db_databases`), а не по `path`:

- база найдена по записанному пути — `ok`; найдена в другом месте — `moved` (работает, в подсказке новый путь);
- базы с таким ID нет — `missing`. Запись остаётся в файле, вкладка раздела помечена предупреждением и
  объясняет «верните папку на место, и раздел заработает». Отдельной диагностики для этого нет, базу
  модуль сам не воссоздаёт. Автор может убрать запись в настройках мастерской (`remove_workshop_section`;
  папка и данные остаются); роль освобождается только после этого, и тогда раздел можно создать заново.

### Версия выше известной

Мастерская или история с `formatVersion`, отличным от 3, открывается только для чтения: запись отвечает
`WorkshopReadOnly` / `StoryReadOnly`, файл не переписывается. Страница мастерской показывает плашку
«формат новее известного».

### Удаление истории или вселенной (W12)

Удаление карточки истории или вселенной очищает только саму историю/вселенную. Сущности мира
(персонажи, локации, арки, якоря), ссылавшиеся на неё, **не удаляются**: идентификаторы остаются во
frontmatter, модуль их не чистит; автор убирает такую связь правкой свойства.

## 10. Rust-слой и транзакционность

Команды `src-tauri/src/commands/project.rs` (типы — `project/model.rs`, привязки генерируются Specta в
`src/lib/bindings.ts`, порт — `src/lib/storage/project-port.ts`). Все требуют включённого модуля баз
(`ModuleDisabled`) и открытого хранилища; команды записи и `refresh_projects` ещё принимают
`expectedGeneration` (`VaultGenerationConflict`, если хранилище сменилось). `resolve_workshop_folder` проверяет только открытое хранилище. Чтения `list_projects`,
`list_note_references`, `list_text_stats` и `list_notebooks` поколения не проверяют.

| Команда                                                                   | Назначение                                                                                                                | Журнал        |
| ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- | ------------- |
| `list_projects`, `refresh_projects`                                       | каталог из индекса; вторая сначала пересобирает индекс из файлов                                                          | нет           |
| `init_workshop`                                                           | папка по `path`, `amby-workshop.json`, все семь баз с заготовками и всеми связями (§2.1, §4); имя = имя папки             | да            |
| `complete_workshop`                                                       | отсутствующие базы и связи существующими операциями ниже; ничего не меняет в имеющемся                                    | да (по шагам) |
| `resolve_workshop_folder`                                                 | выбранная в диалоге папка → путь внутри хранилища (только чтение)                                                         | нет           |
| `create_story`                                                            | папка, карточка, манифест базы текста, `amby-story.json`                                                                  | да            |
| `create_workshop_section`                                                 | новая база и запись в файле мастерской; для «Вселенных» и «Арок» ещё связь в другой базе                                  | да            |
| `update_workshop`, `reorder_workshop_sections`, `remove_workshop_section` | название, значок, теги; порядок записей; убрать запись (не папку); «Истории» убрать нельзя (`CannotRemoveStoriesSection`) | да            |
| `update_text_levels`, `add_text_status`                                   | уровни текста; свойство статуса у старой истории                                                                          | да            |
| `add_story_links`, `ensure_plot_links`                                    | свойства «Истории» / «Вселенная»; «Якоря» / «Арки» (§6)                                                                   | да            |
| `create_workshop_entity`                                                  | страница раздела мира со связями одной записью (`storyId`, `notebook`, `universeId`)                                      | нет           |
| `create_text_page`, `move_text_page`                                      | страница текста; родитель и порядок одной записью (§5)                                                                    | нет           |
| `list_note_references`, `list_text_stats`, `list_notebooks`               | связи заметки в обе стороны (досье); слова и времена страниц; блокноты базы «Заметки» (§8)                                | нет           |

Операции без журнала пишут один файл (или одну запись базы) и защищены ревизией строки.

**Журнал.** Операции с журналом выполняются как одна транзакция: предпроверка без записи (поколение,
имена, родитель, совпадение без учёта регистра, ревизия), журнал `.amby/recovery/creative/<operationId>.json`
(без перезаписи; прежнюю папку `.amby/recovery/projects/` восстановление тоже читает), папки и базы с
идентификаторами из журнала и в конце файл структуры. Точка фиксации — файл структуры, дошедший до
запланированных байтов: ошибка после неё всё равно отвечает успехом. До неё откат (`recovery::rollback`)
убирает только созданное операцией: манифест — если он побайтно равен пересчитанному из журнала, папку —
если она пуста; всё остальное остаётся, ответ `RecoveryRequired`, журнал сохранён. Операции, меняющие
манифест существующей базы (`add_text_status`, `update_text_levels`, `add_story_links`, `ensure_plot_links`,
создание «Вселенных», создание «Арок» при существующих «Якорях»), записывают в журнал исходные байты
манифеста и возвращают их при откате.

- Возобновление операции с тем же `operationId` после падения берёт запланированные ID и байты
  файла мастерской из журнала (как `create_story`): тот же набор баз, те же ID свойств.
- Повтор команды с тем же `operationId` и тем же запросом возвращает сохранённый результат
  (`replayed`); с другим запросом — `OperationIdReused`.
- При открытии хранилища `recover_pending_projects` обходит журналы: незавершённые откатывает или
  признаёт завершёнными, а те, что не удалось убрать, переносит в папку `quarantine/` рядом. Открытию
  хранилища это не мешает.
- Проекция мастерской (таблицы `project_*` в индексе SQLite) — перестраиваемый кеш: пересобирается одной
  транзакцией при открытии хранилища, по `refresh_projects` и после каждого создания; наблюдатель
  присылает событие `project:changed` (изменился файл структуры или создана, удалена, переименована папка),
  интерфейс откладывает его и вызывает `refresh_projects`. Журналы, в отличие от индекса, пересобрать нельзя.

**Ошибки** (`ProjectError`, поле `kind`): `ModuleDisabled`, `VaultNotOpen`, `VaultGenerationConflict`;
`InvalidOperationId`, `OperationIdReused`; `InvalidName {field, reason}`, `InvalidParent`, `PathCollision`;
`WorkshopNotFound`, `StoryNotFound`, `SectionNotFound`, `PageNotFound`; `WorkshopReadOnly`, `StoryReadOnly`;
`RevisionConflict {actualRevision}`; `UnsupportedRole`; `CannotRemoveStoriesSection`; `StatusAlreadyConfigured`,
`StoryLinksAlreadyConfigured`, `StoryLinksUnavailable`; `TextNotConfigured`, `UnknownTextLevel`,
`UnknownTextFormat`, `InvalidOrderKey`, `ParentCycle`, `ParentLevelNotShallower`; `RolledBack`,
`RecoveryRequired`; `Failed {code, message}` для остального (например `sectionAlreadyExists`,
`missingStoriesSection`, `textSchemaBroken`, `interrupted`). Варианты `UnsupportedPreset`,
`CannotRemoveTextSection` и `LevelInUse` объявлены, но нынешний код их не возвращает.

## 11. Досье и сюжет страницы

Досье — оформление редактора, а не данные: рамка вокруг редактора заметки (`editorFrame` оболочки),
в которой блоки считаются по запросу и ничего не пишут в заметку. Рамка одна и та же структура для
любой заметки, поэтому редактор не пересоздаётся, когда приходит ответ; блоки стоят справа, а на узкой
панели (меньше 640 пикселей) уходят под текст. Бэкенд опрашивается, только если в хранилище есть
мастерские, и только заметка раздела мастерской получает оформление.

**Страница раздела мира** (всё, кроме текста, заметок и «Историй»): шапка со значением ключевых
свойств, блоки «Разделы» (заголовки страницы), «Появляется в» (страницы текста, ссылающиеся на неё) и
«Связи» (остальные связи в обе стороны). Дополнительно, по роли раздела:

- **Персонаж** — блок «Арки»: арки, у которых «Персонажи» (`charactersPropertyId` раздела `arcs`)
  содержит персонажа, с цветом арки (`arcColor`). Это входящие ссылки через это свойство, поэтому их
  нет и в «Связях»; без арок блока нет.
- **Арка** — блоки «Якоря арки» и «Главы». Якоря арки — якоря, у которых «Арки» (`arcsPropertyId`
  раздела `anchors`) содержит арку; их порядок задаёт текст каждой истории (`orderStoryAnchors`), истории
  идут по каталогу (при нескольких — с названием истории), якоря, не привязанные ни к одной странице,
  стоят в конце под подписью «Не привязаны к тексту». «Главы» — страницы текста, где привязана арка, по
  историям в порядке текста; если страниц больше одной, подпись охвата «от … до …» (первая и последняя).
  «Появляется в» у арки заменено «Главами», а входящие связи от якорей не повторяются в «Связях».

**Страница текста истории**, если в мастерской есть база якорей или арок, получает блок «Сюжет страницы»
по образцу досье: «Якоря этой страницы» (в порядке списка на странице), «Отталкиваемся от» (ближайший
привязанный якорь до страницы в порядке текста, не считая якорей самой страницы), «Должны прийти к»
(ближайший после; если таких нет — первый якорь «Впереди») и «Арки» страницы с цветом. Якорь стоит там,
где стоит самая ранняя из его страниц (`pageNeighbours`). Пустой блок показывается тихой строкой; весь
блок не показывается, если в мастерской нет ни одного якоря и ни одной арки. Каждый пункт открывает
свою страницу. Данные берутся из тех же строк, что читает панель (база текста, якоря, арки), и из
каталога; нового IPC нет.
