# Аудит Windows — 28 сентября 2026

## Область проверки

Проверена локальная рабочая копия Amby 0.1.5 на ветке `dev`, включая текущие
незакоммиченные исправления. Среда: Windows NT 10.0, build 26200.9457,
WebView2 154.0.4258.37, Node.js 22.20.0, Rust/Cargo 1.95.0.

Ручные сценарии выполнены в отдельном нативном окне с одноразовыми заметками,
настоящими редакторами и Tauri IPC. Тестовый профиль, настройки, SQLite и
WebView отделены от пользовательского профиля. Обычное окно разработки
оставлено работающим. Пользовательские заметки не использовались как тестовые
данные.

Для замеров добавлена локальная диагностическая панель вне React-приложения:
интервалы `requestAnimationFrame`, long tasks, события фокуса, замены DOM
редактора и состояние автосохранения. Экспорт проходит через `storage.ts`.
Фронтенд собран без HMR; конфигурация разбиения чанков отличается от обычной
производственной сборки. Это проверка настоящего приложения в WebView2,
но не сертификация установщика или измерение release-бинарника.

### Потеря каретки: причина и исправление

В `tree/sidebar-tree.tsx` эффект восстановления клавиатурного фокуса зависел
от `flatRows`. Автосохранение и файловые события обновляли дерево, после чего
эффект снова фокусировал выбранную строку. Предыдущее исправление стабильности
`editorProps` в Tiptap не закрывало этот путь.

До исправления первый ввод сохранился, а продолжение без клика не попало в
заметку. Диагностика зарегистрировала уход фокуса из редактора примерно через
1,1 секунды после ввода, без нового клика. DOM редактора при этом не заменялся.

Эффект теперь проверяет владельца фокуса перед планированием и внутри RAF.
Редактор и другие панели сохраняют фокус; клавиатурная навигация дерева
продолжает работать. Регрессионный тест падал до изменения и проходит после.

После исправления последовательно проверены ввод, несколько автосохранений,
обычная клавиша, Backspace и продолжение ввода без клика. Все контрольные фразы
прочитаны с диска. Уход фокуса зафиксирован только при намеренном нажатии кнопки
экспорта замеров. Такой же сценарий прошёл в CodeMirror и заметке из 1000 абзацев.

### Защита Markdown от потерь не применяется в интерфейсе

Файл со сноской `Footnote[^1]` и определением `[^1]: ...` открылся в Live
Preview. Диагностика одновременно сообщила `source: 0`, `livePreview: 1`
и причину несовместимости `footnotes`.

`tiptap/markdown-compatibility.ts` явно отклоняет сноски. Однако
`roundTripCheck` вызывается тестами и диагностикой, а выбор режима в
`editor/document-editor.tsx` опирается на `noteEditingPolicy`, проверяющую
состояние frontmatter. Проверка возможности точного Markdown round trip
не включена в эту политику.

Это нарушение контракта `docs/markdown-compatibility.md` и потенциальный риск
изменения неподдерживаемого Markdown при редактировании. Потеря содержимого
в этом сценарии не утверждается: исходный файл оставался целым, редактирование
тестовой сноски выполнялось после явного переключения в Source mode.

Нужно проверять совместимость перед допуском документа в Live Preview и при
явном выборе этого режима. Проверку следует связывать с содержимым/ревизией,
не повторять полный разбор при каждом обновлении метаданных автосохранения.

### Главный поток и масштаб хранилища

`commands/notes.rs` (`read_note`, `write_note`, `get_note_properties`) и
`commands/vault.rs` (`load_vault`, `load_active_vault`, `list_files`) используют
синхронные Tauri команды. Они выполняют файловую работу и работу с индексом.
`use-vault-data.ts` вызывает `refreshTree` после пакета событий watcher;
`load_active_vault` вызывает `active.refresh()`.

Согласно [документации Tauri о командах](https://v2.tauri.app/develop/calling-rust/),
синхронные команды по умолчанию выполняются в главном потоке; тяжёлая работа
может блокировать интерфейс. Это подтверждённый архитектурный риск. Замеры
ниже показывают стоимость обновления, но не являются измерением длительности
конкретного зависания окна пользователя.

Тест `desktop_e2e_large_vault_smoke_reports_scan_reopen_update_and_search`
запущен на этой машине в debug-профиле. Он создаёт заметки в трёх папках,
открывает хранилище, открывает его повторно, изменяет один файл, передаёт событие
в очередь watcher, вызывает `active.refresh()` и выполняет поиск.

| Заметок | Первое открытие | Повторное открытие | Изменение одного файла + refresh | Поиск   |
| ------- | --------------- | ------------------ | -------------------------------- | ------- |
| 1000    | 1,425 с         | 715 мс             | 351 мс                           | 1,15 мс |
| 10 000  | 13,393 с        | 6,849 с            | 3,428 с                          | 2,84 мс |

При росте числа заметок в 10 раз обновление одного файла стало примерно в
10 раз медленнее. Следующий шаг: профилировать `ActiveVault::refresh`,
вынести блокирующую работу из главного потока, сохранив порядок записей,
проверку ревизий и поколений хранилища. Затем повторить замеры в release-профиле.

## Нативный интерфейс

В тестовом хранилище после накопленных исправлений длительное зависание при
переключении Excalidraw не воспроизведено. Выполнены по три перехода текст →
Excalidraw с возвратами на пустом холсте и на синтетическом рисунке из 1000
прямоугольников. Рисунок действительно отобразился; его внешнее изменение
было прочитано через watcher.

| Сценарий                                                         | Максимальный интервал RAF | Long tasks              | Результат                                   |
| ---------------------------------------------------------------- | ------------------------- | ----------------------- | ------------------------------------------- |
| Короткая заметка, ввод и автосохранение после исправления фокуса | 50 мс                     | 54 и 51 мс              | Продолжение ввода без клика, конфликтов нет |
| Повторные переключения пустого Excalidraw                        | 25,1 мс                   | Нет                     | Длительного зависания не видно              |
| Рисунок из 1000 фигур и повторные переключения                   | 66,7 мс                   | 64 мс                   | Длительного зависания не видно              |
| Открытие и два ввода в заметке из 1000 абзацев                   | 100,1 мс                  | Есть задачи более 50 мс | Оба ввода сохранены, фокус сохраняется      |

RAF и long tasks измеряют работу JavaScript в WebView. Они не измеряют отдельно
оконный message loop, задержку доставки клавиш или задержку физического экрана.
Результаты не покрывают пользовательский рисунок с вложениями и большое
хранилище одновременно.

В панели Excalidraw подсказки Undo/Redo содержат `⌘Z` и `⇧⌘Z`, хотя приложение
работает на Windows. В `sketch-editor.tsx` эти строки заданы напрямую; рядом уже
есть определение `isMac`, которое можно использовать для корректных подсказок.

## Файлы, корзина и тесты

- Нативные IPC сценарии подтвердили создание/чтение/запись Unicode, повторную
  запись, переименование файлов и папок, защиту коллизий, сохранение после
  повторной активации, отклонение устаревшей ревизии и выходов за границу vault.
- Сценарий быстрого ввода/стирания с настоящими сохранениями и событиями прошёл.
  В ручных проверках ввода ложное окно внешнего конфликта не появилось.
- Системная корзина успешно приняла два собственных одноразовых файла:
  обычный путь и вложенный путь длиной 341 UTF-16 code unit. Восстановление
  из системной корзины вручную не проверялось. Это результат на данной машине,
  не гарантия для UNC, сетевых дисков или других настроек Windows.
- `paths::confine` отклоняет стандартные имена устройств и опасные компоненты,
  но допускает COM¹/²/³ и LPT¹/²/³. Microsoft также относит эти варианты к
  [зарезервированным именам](https://learn.microsoft.com/windows/desktop/FileIO/naming-a-file).
  Проверена валидация пути, а не создание файла с таким именем.

Нативный contract harness: **11 из 14 сценариев прошли**. Три оставшихся
результата объясняются ожиданиями тестов:

1. Тест восстановления ожидает, что `delete_item` заполняет `.amby/trash`.
   Текущая реализация отправляет файл в системную корзину; `.amby/trash`
   используется отдельным `archive_item`.
2. Тест отказа удаления блокирует `.amby/trash`, ожидая отказ `delete_item`.
   Эта директория не участвует в текущем системном удалении.
3. Тест ошибки диагностического журнала ожидает только `IoError`.
   Windows возвращает **PermissionDenied** при попытке открыть директорию
   как файл. Ошибка корректно возвращается вызывающему коду и статусу;
   тест уже прошёл проверки отказа flush и ограничения времени, затем упал
   на слишком узком ожидании строки.

Эти три результата не являются доказательством потери заметок. Нужно согласовать
тесты и документацию с разделением «Архив / системная корзина», а ожидание
санитизированной ошибки сделать переносимым.

Обычный Rust test target не компилируется: в
`database/mutations_test.rs:1177` используется `std::os::unix::fs::PermissionsExt`,
а на строке 1223 — `Permissions::from_mode`. Для продолжения аудита только в
игнорируемой тестовой копии этот один Unix-тест ограничен `#[cfg(unix)]`.
После этого: **365 Rust тестов прошли, 4 ignored**. Это не означает, что
обычный `npm run rust:test` в рабочем репозитории исправлен.

В CI уже есть матрица Rust Windows/macOS/Linux и Windows bundle job.
Проблема не в отсутствии Windows job: текущий непереносимый тест блокирует
его прохождение. Нативные сценарии взаимодействия с редакторами не входят
в обычный `verify`.

## Что ещё проверить перед Windows выпуском

### Дополнение: тихое автообновление при запуске

После изменения автообновления проверены короткая проверка сервера, отсутствие
подтверждений, общий Promise для повторных вызовов, ошибки сети/загрузки/подписи,
перезапуск и освобождение ресурсов. Компонентные проверки подтверждают, что
рабочая область не монтируется во время установки и перезапуска, а изменение
настройки после старта применяется при следующем запуске. Проверки проходят и
под React StrictMode. Ручная проверка обновлений сохраняет свой интерфейс.

- Целевые тесты обновления, запуска и локализации: **22 прошли**.
- Повторный `npm run verify`: **870 тестов в 136 файлах прошли**; TypeScript
  и ESLint прошли с тем же существующим warning. Проверка остановилась на тех
  же девяти файлах Prettier, перечисленных выше. Первый параллельный прогон
  превысил таймаут одного существующего теста; после завершения компиляции
  повторный прогон прошёл без изменения теста.
- `npm run build`: успешно. `npm run tauri build -- --no-bundle`: успешно,
  собран Windows release executable с тихим режимом установщика в конфигурации.
- В браузерном режиме проверены открытие рабочей области и новая подсказка
  автообновления в настройках. Tauri dev пересобран и запущен; автоматическая
  установка в dev отключена. Ручная проверка нативного интерфейса в этой сессии
  не завершена: инструмент управления окном дважды вернул
  `failed to activate captured window`.
- Переход между двумя подписанными установленными версиями, MSI/NSIS и
  перезапуск после настоящей установки пока не проверены. Сборка без bundling
  и тесты с подменой IPC не заменяют этот сценарий.

Версия осталась 0.1.5; ключ, HTTPS endpoint и разрешения не менялись. Логи
этой проверки: `.release-evidence/updater-verify.log` и
`.release-evidence/updater-native-build.log`.

### Оставшиеся сценарии

1. Подключить защиту совместимости Markdown и проверить переходы Live/Source
   на корпусе неподдерживаемых конструкций.
2. Исправить переносимость Rust-теста и актуализировать нативные контракты,
   чтобы Windows gate действительно проходил.
3. Профилировать и разгрузить главный поток на хранилищах 1000/10 000 заметок;
   проверить те же сценарии в release-сборке и на пользовательском рисунке.
4. Проверить MSI/NSIS, запуск без toolchain, обновление и закрытие с несохранёнными
   изменениями в установленном приложении.
5. Отдельно пройти DPI 125/150/200%, перенос окна между мониторами, IME,
   UNC/OneDrive, antivirus/file locks, sleep/resume и восстановление из системной
   корзины. Эти сценарии данным аудитом не покрыты.

На macOS сопоставимые замеры не выполнялись. Разные движки
[WebView2 и WKWebView](https://v2.tauri.app/reference/webview-versions/)
объясняют необходимость отдельной проверки интерфейса, но сами по себе
не доказывают причину конкретного Windows дефекта.
