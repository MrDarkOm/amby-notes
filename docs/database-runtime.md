# Runtime, SQLite and IPC of Amby databases

Status: proposed contract
Document version: 1
Date: 2026-09-04

This document continues the
[system architecture](database-system.md),
[user flows](database-user-flows.md) and
[durable format](database-format.md). It defines the rebuildable
SQLite projection, the Tauri IPC boundary, the order of mutations and the frontend state.

## 1. The responsibility boundary

The runtime consists of three layers:

```text
React / Zustand
      │ typed DatabasePort
      ▼
Tauri commands / browser adapter
      │ validated domain requests
      ▼
database domain service
      ├── durable files: Markdown frontmatter (note values), <DB>.json + .ambd/* (schema/views)
      └── .amby/notes.db                          rebuildable projection
```

Main rules:

- the frontend does not read or write database files directly;
- user data is considered saved only after a durable write;
- SQLite is never the only copy of the schema, values, views or
  templates;
- a mutation response separates the result of the durable write from the state of the index;
- disabling the Databases module does not change durable files;
- the property kernel stays available to the app regardless of the module;
- all IPC types are generated by Specta; `src/lib/bindings.ts` is not edited by hand.

The database projection lives in the existing `.amby/notes.db`. A separate SQLite file
is not used: a single transaction with the `notes` table is needed for membership,
relations, search and deletion. Modularity is provided by the code boundary,
a setting and separate tables with the `db_` prefix, not by a second file.

## 2. Backend modules

`lib.rs` only registers commands. The proposed structure:

```text
src-tauri/src/
├── commands/database.rs
└── database/
    ├── mod.rs
    ├── model.rs          # durable and IPC domain types
    ├── discovery.rs      # finding containers and the owning database
    ├── format.rs         # parse/validate/preserve unknown fields
    ├── projection.rs     # full rebuild and incremental projection
    ├── query.rs          # AST validation and SQL compilation
    ├── mutations.rs      # single-file and journaled operations
    ├── yaml_sync.rs      # three-way field sync
    └── recovery.rs       # inspect/resume/rollback
```

Before the editable slice the current `VaultContext` gets a narrow `IndexAccess`:

- a single serialized writer connection;
- a small pool of read connections in WAL mode;
- immutable `vaultRoot` and `vaultGeneration` for the duration of the operation;
- cancelling a long query when the vault changes or a tab closes.

Filesystem I/O and JSON parsing are not performed under the SQLite writer lock. A mutation
holds locks only on the specific durable resources, then briefly
publishes the projection transaction. Locks are taken in a deterministic order
by canonical vault-relative path, so that a batch does not create a deadlock.

## 3. Runtime versions

`index_metadata` gets independent keys:

| Key                          | Purpose                                              |
| ---------------------------- | ---------------------------------------------------- |
| `database_schema_version`    | Version of the SQLite DDL of the database projection |
| `database_projection_epoch`  | A new ULID after a full rebuild                      |
| `database_projection_seq`    | Number of the incremental transaction                |
| `database_projection_status` | `healthy`, `degraded` or `rebuildRequired`           |

The cursor and the UI snapshot use the `{ epoch, seq }` pair. After a rebuild old
cursors are guaranteed to become invalid, even if the counter
started again from zero.

A SQLite migration is a cache migration. It is performed repeatably through
schema introspection and a single DDL transaction. If the existing index cannot be
safely updated, the backend closes the connections, moves the damaged
SQLite file to `.amby/recovery/index/` and builds a new one in full. The durable database
files do not change in the process.

## 4. Normalized SQLite projection v1

Logical fields are listed below. The exact DDL is fixed next to the implementation and
checked by a schema snapshot test.

### 4.1 Databases and schema

```text
db_databases
  database_id PK
  container_path UNIQUE
  attached_note_id NULL FK notes(id) ON DELETE SET NULL
  name
  icon
  cover_json NULL
  locked BOOL
  format_version
  manifest_revision
  projection_state        valid | staleReadOnly | unsupported | broken

db_properties
  database_id FK db_databases ON DELETE CASCADE
  property_id
  position
  name
  property_type
  page_visibility
  config_json
  yaml_key NULL
  yaml_direction NULL
  PK (database_id, property_id)

db_options
  database_id
  property_id
  option_id
  position
  name
  color
  status_group NULL
  PK (database_id, property_id, option_id)
```

`config_json` stores only an already validated projection of the typed config. It is not
executed and is not passed into SQL as a fragment. Unknown durable fields
are preserved by the format layer, but are not required to land in SQLite.

### 4.2 Membership and hierarchy

```text
db_members
  database_id FK db_databases ON DELETE CASCADE
  note_id UNIQUE FK notes(id) ON DELETE CASCADE
  parent_note_id NULL FK notes(id) ON DELETE SET NULL
  relative_path
  category_path
  depth
  title_sort_key BLOB
  PK (database_id, note_id)
```

`UNIQUE(note_id)` fixes the single-owning-database rule. The owner is determined by
the nearest parent `ambd.json`. `parent_note_id` contains only a real
parent row; ordinary intermediate folders are reflected in `category_path`.

A damaged or missing manifest does not make the runtime silently hand
rows to a more distant outer database. Such a subtree gets a diagnostic and stays
in the previous safe projection until an explicit fix or a confirmed
removal of the manifest.

### 4.3 Typed values

```text
db_values
  database_id
  note_id
  property_id
  value_type
  canonical_json
  text_value NULL
  text_sort_key BLOB NULL
  decimal_value NULL
  decimal_sort_key BLOB NULL
  bool_value NULL
  date_start NULL
  date_end NULL
  date_start_key INTEGER NULL
  date_end_key INTEGER NULL
  date_precision NULL        date | instant
  option_id NULL
  source_revision
  PK (database_id, note_id, property_id)
```

Separate tables are used for multi-value types:

```text
db_value_options(database_id, note_id, property_id, option_id, position)
db_value_files(database_id, note_id, property_id, asset_id, position,
               relative_path, name, mime_type, size_bytes)
db_relation_edges(source_database_id, source_note_id, property_id,
                  target_note_id, position, target_state)
```

`target_state` is `resolved`, `outsideDatabase` or `missing`. The foreign key on
`target_note_id` intentionally does not forbid an unresolved relation; when the target appears
the projection updates the state without changing the record shard.

`canonical_json` is needed for an exact IPC round-trip and for diagnostics. Typed columns
are needed for filtering and indexes. They are always built from the canonical value and are not
themselves a source of data.

### 4.4 Exact Number comparison

The decimal string stays the exact value. The runtime additionally builds a
canonical binary `decimal_sort_key`, comparable by SQLite bytewise with the same
result as arbitrary-precision decimal comparison. The algorithm must:

- normalize sign, zero, exponent and trailing zeros;
- keep the correct order of negative and positive numbers;
- have golden tests on very large values and different scale;
- reject values beyond the documented limits before writing.

`Sum`, `Average`, `Min` and `Max` are computed as exact-decimal aggregates on the backend and
returned as a decimal string. SQLite `REAL` is not used as an authoritative
value or a sort key.

### 4.5 Text and dates

`text_sort_key` is computed by the backend from a Unicode-normalized case-folded string and
is versioned together with the projection schema. This removes the dependence on ASCII-only
`NOCASE` and on differences in the system locale.

Date-only is indexed as a calendar day. Date-time is first validated with
an offset, then indexed as a UTC epoch; the original string and the IANA timezone stay
in `canonical_json`. Comparing date-only and date-time inside one property
is forbidden by the schema/config and is not guessed by the query compiler.

### 4.6 Views, templates and diagnostics

```text
db_views
  database_id
  view_id
  position
  name
  layout
  revision
  query_json
  layout_json
  projection_state
  PK (database_id, view_id)

db_templates
  database_id
  template_id
  position
  name
  revision
  body
  values_json
  projection_state
  PK (database_id, template_id)

db_yaml_conflicts
  database_id
  note_id
  property_id
  base_json
  shard_json
  yaml_json
  note_revision
  record_revision
  PK (database_id, note_id, property_id)

db_diagnostics
  diagnostic_id PK
  scope_kind
  scope_key
  code
  severity
  details_json
  first_seen_at
  last_seen_at
```

View filter/sort/group stays a validated AST in `query_json`. A separate
normalization of each condition is not needed: the SQL compiler builds the plan at query time,
and the indexes sit on the typed value tables.

### 4.7 Search

```text
db_values_fts
  database_id UNINDEXED
  note_id UNINDEXED
  property_id UNINDEXED
  searchable_text
```

FTS includes Text, URL and the display names of Select/Status/Multi-select. Relation
is searched through the title of the target, but does not duplicate it in the durable value. Global Search
merges `notes_fts` and `db_values_fts`, removes duplicates by `note_id` and explicitly
indicates the source of the match.

## 5. Indexes

The minimal set:

- `db_databases(container_path)`;
- `db_members(database_id, parent_note_id, note_id)`;
- `db_members(database_id, title_sort_key, note_id)`;
- `db_values(database_id, property_id, text_sort_key, note_id)`;
- `db_values(database_id, property_id, decimal_sort_key, note_id)`;
- `db_values(database_id, property_id, date_start_key, note_id)`;
- `db_values(database_id, property_id, bool_value, note_id)`;
- `db_values(database_id, property_id, option_id, note_id)`;
- `db_value_options(database_id, property_id, option_id, note_id)`;
- `db_relation_edges(property_id, target_note_id, source_note_id)`.

An additional index is added only after `EXPLAIN QUERY PLAN` and a benchmark,
not for every potential combination. The cache size must not grow
uncontrollably because of duplicate JSON indexes.

## 6. Full rebuild

A full rebuild goes like this:

1. Create an immutable snapshot of the path list and fingerprints.
2. Find containers, notes and shards without entering the service directories as if
   they were ordinary notes.
3. Read and validate the durable files outside the SQLite transaction.
4. Compute ownership, hierarchy, typed columns, relations and diagnostics.
5. If the vault changed or the snapshot is stale, cancel the publication and retry.
6. In a single transaction replace only the `db_*` projection, update epoch/seq and
   FTS.
7. Emit one event about the new projection generation.

WAL readers keep seeing the previous whole projection until commit. A read error
in one database does not turn into deleting all of its data:

- if a previous projection exists, the database stays `staleReadOnly`;
- on a clean rebuild a broken-container diagnostic is created by vault-relative
  path;
- automatic repair of a durable file is forbidden.

## 7. Incremental projection and the watcher

The watcher classifies changes:

| Path                                 | What is rebuilt                                  |
| ------------------------------------ | ------------------------------------------------ |
| `ambd.json`                          | schema, ownership of the affected subtree, views |
| `.ambd/records/<id>.json`            | one row, relations, YAML conflict                |
| `.ambd/views/<id>.json`              | one view                                         |
| `.ambd/templates/<id>.json`          | one template                                     |
| row `.md`, bundle rename/move/delete | note fields, membership, YAML binding            |
| nested container create/move/delete  | ownership of the whole affected subtree          |

Events are coalesced per container with a short debounce. Before an incremental commit
the backend checks the fingerprints again. Own writes are marked by the existing
`WatcherState`, but the command itself updates the projection; the watcher event stays
a safety net and does not create a second mutation.

After `update_database_relation_value` the command updates the projection by
`result.affectedNotes`: the `databaseId`/`noteId` pairs are taken from the successfully executed
write plan, including the former targets from which the inverse link was removed. The new
`targetNoteIds` alone must not be used as the invalidation list. Pages are
grouped by database and deduplicated; a self-relation is updated once.
The runtime publishes the last successful `epoch`/`seq`. An error in any group is returned
in `warnings`, the other groups are still processed; durable files are not rolled back
or rewritten because of a projection error. A full rebuild remains the
way to restore derived state. Changing Relation values now requires a
raw-byte revision of the source, rechecks notes/manifests before publishing and
performs a conditional rollback with a check for external edits. `operationId` and the durable
Relation journal keep the completed result for an idempotent replay.
On vault activation pending operations are rolled back before the index is loaded; an error
in the recovery checks blocks activation, preserving the journal/backups. The protocol
is described in the [Relations contract](database-format.md#relations).

Creating a two-way Relation prepares both manifests before writing and uses
a separate schema journal. The request checks the source/target manifest revisions;
the result returns stable forward/inverse IDs and `manifestRevisions`.
A self-pair is published with a single manifest. Completion precedes watcher
confirmation; the command then rebuilds the projection, and a cache failure returns
a warning without rolling back the durable schema. Vault activation checks pending value and schema
journals before restore starts and before SQLite is opened. Configuring an existing
Relation and converting to/from Relation use version 2 of the same schema journal:
the source and related raw manifest revisions, up to three merged manifests,
a stable operation ID and a replay of the original result. Version 1 of creation
keeps being read. A topology change still requires empty values on both
sides; the old inverse property is kept with the reciprocal pointer disabled.

The partial-update warning must be taken into account even with a global
`database_projection_status = healthy`: a successful group can leave this
status while the cache of another group has not been updated. A separate degraded state and a full
transitive recalculation of multi-level Rollups remain P0 tasks; this path
confirms the direct Rollups of the affected pages.

While the Databases module is disabled the watcher continues the regular note index but does not
parse database shards. The old `db_*` projection is not used for queries.
Re-enabling always starts with validation and a full database rebuild.

## 8. Query contract

```ts
interface DatabaseQueryRequest {
  expectedGeneration: number
  databaseId: string
  source:
    | { kind: "savedView"; viewId: string; expectedRevision?: string }
    | { kind: "inline"; spec: DatabaseQuerySpec }
  overrides?: DatabaseQueryOverrides
  page: { limit: number; cursor: string | null }
}

interface DatabaseQueryResult {
  database: DatabaseHeader
  projection: { epoch: string; seq: number }
  rows: DatabaseRow[]
  nextCursor: string | null
  groups: DatabaseGroup[]
  aggregates: DatabaseAggregate[]
  diagnostics: DatabaseDiagnostic[]
}
```

`DatabaseRow` contains system fields, typed property values, `parentNoteId`,
`depth`, a breadcrumb and the row revision. It does not contain an absolute path. Media URLs
are created through the existing asset boundary.

Query rules:

- page limit: a backend constant, at most 200 in v1;
- the cursor uses keyset pagination, not `OFFSET`;
- the opaque cursor contains the projection epoch/seq, the hash of the normalized query,
  the sort keys and the last `(databaseId, noteId)`;
- a cursor from another projection/query returns `staleCursor`, not an empty page;
- every sort has an explicit `nullsFirst`/`nullsLast` and a stable ID tie-breaker;
- nested mode sorts siblings; a filtered child is returned with a
  breadcrumb even if the parent itself did not match;
- the backend returns only the fields the current layout needs;
- board counts and footer aggregates are computed over the full filtered set, not over the
  loaded page.

### 8.1 Security compiler

The frontend passes only versioned `FilterNode`, `SortRule`, `GroupRule` and
`FieldRef`. The backend:

1. limits the AST size/depth;
2. checks field IDs against the current schema;
3. checks the operator and operand against the type;
4. picks the SQL fragment from a closed enum;
5. passes all user data as parameters;
6. adds an execution budget and supports cancellation.

Raw SQL, SQL identifiers, collations and expressions from the renderer are not accepted.
Property IDs are also used as bind values and are not inserted into SQL.

## 9. IPC surface v1

Commands are grouped by purpose but use shared typed requests.

Reading:

- `get_database_module_state`;
- `list_databases`;
- `get_database`;
- `query_database`;
- `get_database_record`;
- `search_database_records`;
- `list_database_recovery`;
- `preview_database_operation`.

Fast mutations:

- `apply_database_value_batch`;
- `apply_database_schema_mutation`;
- `apply_database_view_mutation`;
- `apply_database_template_mutation`;
- `resolve_database_yaml_conflict`.

Structural operations:

- `create_database`;
- `execute_database_operation`;
- `recover_database_operation`;
- `rebuild_database_projection`.

Structural actions — attach/remove/delete database, add/move/lift rows, CSV
import and destructive schema changes — call preview first. Preview
returns an opaque `planId`, the exact affected resources, conflicts, warnings and
expected revisions. `execute_database_operation(planId)` rechecks all
revisions; a stale plan is not executed partially.

Small changes use tagged enums instead of a universal JSON Patch.
This keeps the strict Specta types and lets the backend check the semantics:

```ts
interface DatabaseMutationEnvelope<T> {
  operationId: string
  expectedGeneration: number
  databaseId: string
  originWindow: string
  expectedRevisions: ResourceRevision[]
  mutation: T
}
```

`operationId` is generated by the frontend once and repeated only for a safe retry
of the same request. The backend remembers completed IDs in a short idempotency log;
the same ID with a different payload is rejected.

## 10. Mutation protocol

### 10.1 Single-resource write

1. Check module state, vault generation, lock and permissions.
2. Resolve resource IDs into canonical guarded paths.
3. Read the raw bytes and check the expected revision.
4. Perform full typed validation and the YAML three-way merge.
5. Create a history snapshot if content already exists.
6. Perform an atomic write through the established helper.
7. Update SQLite in a short transaction.
8. Return the outcome and emit an invalidation event.

### 10.2 Multi-resource write

Relation values use `.amby/recovery/database_relations`, and creating and
changing the Relation schema uses `.amby/recovery/database_relation_schemas` from the format
contract. A durable commit is considered complete after the final journal marker;
pending operations block conflicting Relation mutations until recovery.
An ordinary value batch keeps the separate earlier `.ambd/recovery` protocol.
The common protocol for CSV and filesystem moves remains a target contract.

### 10.3 Durable success, index failure

If step 6 completed and the SQLite update failed:

- the command returns success, because the source of truth is already written;
- `indexState` becomes `rebuildRequired`;
- the warning contains only a stable code, without requiring the mutation to be repeated;
- the UI optimistically applies the confirmed value and offers a rebuild;
- a retry with the same `operationId` returns the original success and does not write the file
  a second time.

## 11. Mutation outcome

```ts
interface DatabaseMutationOutcome {
  operationId: string
  databaseId: string
  changedNoteIds: string[]
  changedResources: ResourceRevision[]
  pathChanges: PathChange[]
  projection: { state: IndexState; epoch: string; seq: number }
  warnings: DatabaseWarning[]

```

The absence of `pathChanges` distinguishes a cell edit from a rename/move. The UI must not
guess paths from Title again.

## 12. Typed errors

Database commands return `Result<T, DatabaseError>`, not a string:

```ts
type DatabaseError =
  | { kind: "moduleDisabled" }
  | { kind: "vaultGenerationConflict"; actualGeneration: number }
  | { kind: "revisionConflict"; resource: ResourceRef; actualRevision: string }
  | { kind: "staleCursor" }
  | { kind: "stalePlan"; changedResources: ResourceRef[] }
  | { kind: "notFound"; resource: ResourceRef }
  | { kind: "duplicateTitle"; conflictingNoteId: string }
  | { kind: "databaseLocked" }
  | { kind: "readOnly"; reason: ReadOnlyReason }
  | { kind: "validation"; code: string; field?: FieldRef }
  | { kind: "yamlConflict"; noteId: string; propertyId: string }
  | { kind: "recoveryRequired"; operationId: string }
  | { kind: "indexUnavailable"; canRebuild: boolean }
  | { kind: "failed"; code: string; message: string }
```

What is implemented now. A database IPC error is `moduleDisabled`, `vaultNotOpen`,
`vaultGenerationConflict` or `failed { code, reason, message }`. `code` names the
command that failed (`databaseRenameFailed`, `projectionReadFailed`) and is needed
for support and the log. `reason` is a stable, human-meaningful cause
(`FailureReason`, a Specta enum): `revision_conflict`, `locked`, `read_only`,
`not_found`, `name_taken`, `invalid_name`, `values_not_empty`, `has_dependents`,
`formula_invalid`, `last_view`, `invalid_config`, `relation_invalid`, `invalid_value`,
`too_large`, `rolled_back`, `recovery_required`, `stale_cursor`, `yaml_conflict`, `io`,
`failed` (the cause is unknown). The cause is determined once by
`database/failure.rs::classify` from the phrase returned by the write layer
(`Result<_, String>`), while query errors carry it themselves (`QueryFailure::reason`). A new
failure phrase that a person can do something about gets a variant, a pattern in
`classify`, a text in `databaseErrors.reason.*` and a line in `failure_test.rs`.
`message` is a phrase for the developer: the interface does not show it
(see [docs/notices.md](notices.md), section 10), it is good only for logs. The interface
picks the text by `reason` (`src/lib/database-errors.ts`); an unknown reason gets a generic
text with the command code. Logic that needs to know "is this a conflict" (retrying a view write
after someone else's edit) reads `reason`, not the text.

Paths in errors are vault-relative. Low-level OS details go to the diagnostics
log and do not become a user-visible path or SQL text. The frontend adapter
converts the union into `DatabaseOperationError`, keeping `kind` for the UI; retry
is allowed only for explicitly retryable cases.

## 13. Backend events

```ts
interface DatabaseChangedEvent {
  vaultGeneration: number
  databaseId: string
  operationId: string | null
  originWindow: string | null
  epoch: string
  seq: number
  kind: "schema" | "values" | "views" | "membership" | "rebuild"
  changedNoteIds: string[]
}
```

Events:

- `database:changed` — invalidates the corresponding query pages;
- `database:index-state` — changes the banner/availability;
- `database:conflict` — reports a new YAML/external edit conflict.

An event is an invalidation hint, not the only source of state. All windows
compare `{ epoch, seq }` and then re-read the data. A same-origin event is also
safe to process again: revisions and the operation ID make the update
idempotent.

## 14. Frontend boundary

The main `StoragePort` gets a composite `databases: DatabasePort`. It is always
typed and implemented by both adapters; the `disabled` state is
a result of the capability, not a missing method.

```text
src/lib/storage/database-port.ts
src/lib/storage/database-types.ts
src/lib/storage/desktop-database-adapter.ts
src/lib/storage/web-database-adapter.ts
```

The browser adapter follows the same contract. In the first stage it may use
a limited localStorage representation for fixtures, but a production-sized browser
mode must move to IndexedDB. Components do not branch on Tauri/browser.

`useDatabaseStore` keeps only runtime state:

- the module state and the current projection generation;
- schema/views/templates by ID and revision;
- query cache pages by the normalized query key;
- pending operations by `operationId`;
- conflicts and diagnostics;
- local selection/edit/peek state.

Durable database values are not copied wholesale into the global workspace state.
The query cache is LRU-bounded and is cleared when the vault changes. The Table, Board,
List and Gallery components get one shared `DatabaseRowModel`; a layout does not create its own
version of the data.

## 15. Optimistic editing

- A cell edit appears in the cache immediately with a pending marker.
- The queue is serialized by `{ noteId, propertyId }`, but different rows can be
  saved in parallel up to the backend writer boundary.
- The next edit is built on the revision of the confirmed or pending result.
- Success replaces the revision and removes the marker.
- A validation error returns the previous value and leaves the input available for
  correction.
- A revision/YAML conflict is not silently rolled back: the cell shows both versions.
- Closing a view, disabling the module and unmounting flush the queues first.
- Batch/paste goes through full preflight validation before the first optimistic apply.

A Title edit is not an ordinary cell mutation: it calls a filesystem rename
preview/execute and applies the returned `pathChanges` to the whole workspace.

## 16. Lock and module state

The backend checks the lock for every mutation, even if the UI has already hidden the control.

| Action                        | Locked | Module disabled      |
| ----------------------------- | ------ | -------------------- |
| Read/edit Markdown            | yes    | yes                  |
| Read the database projection  | yes    | no                   |
| Change database values        | yes    | no                   |
| Temporary filter/search       | yes    | no                   |
| Change schema/view/membership | no     | no                   |
| Recovery operations           | yes    | separate entry point |

Disabling the module:

1. the frontend flushes pending value writes;
2. unsubscribes from database events and clears the query cache;
3. the backend stops database projection work;
4. the `db_*` tables may stay on disk as an unused cache;
5. re-enabling validates the durable files and does a full database rebuild.

## 17. Performance contract

Reference benchmark: 10,000 rows, 20 properties, 4 views, relations and 10%
multi-value fields. Until absolute p95 values are approved, structural guarantees are mandatory
after the baseline:

- the first screen does not load the whole database into a Rust response or React;
- a regular query uses keyset pagination and does no N+1 reads;
- a cell edit does not rebuild the whole container;
- a view change does not rebuild values;
- a full rebuild parses files before the SQLite write transaction starts;
- a query can be canceled;
- the result size is limited on the backend;
- the benchmark records the query plan for title, option, date, number, and relation.

After the baseline, p95 budgets for macOS, Windows, and Linux are fixed by a separate
decision; they become regression tests, not a promise without measurements.

## 18. Required tests

### SQLite and projection

- a full rebuild after deleting `notes.db`, `-wal`, `-shm` gives the same result;
- a nested container correctly takes over ownership;
- a malformed shard does not erase the last healthy projection;
- an index failure after a durable write returns success + `rebuildRequired`;
- exact decimal sort/aggregate does not use floating point;
- Unicode title/text sort is the same on all supported OSes;
- an unresolved relation survives deletion and restoration of the target;
- an FTS rebuild does not create duplicate matches.

### Query

- every operator is checked for type, null, and empty;
- the query AST never concatenates user text into SQL;
- equal values have a stable ID tie-breaker;
- a cursor is rejected after a mutation/rebuild and with a different query hash;
- aggregates and board counts do not depend on page size;
- nested/flat return the correct breadcrumb and parent IDs;
- cancellation releases the read connection.

### IPC and concurrency

- generated bindings match the Rust types;
- an old vault generation does not write to a new vault;
- two windows cannot overwrite the same revision;
- repeating the same `operationId` is idempotent;
- the same `operationId` with a different payload is rejected;
- a stale preview does not perform a filesystem mutation;
- a disabled module rejects database calls without changing files;
- the lock is checked by the backend for all schema/view/membership mutations.

### Contract adapters

A single shared set of TypeScript contract tests runs against the desktop harness and
the web adapter: CRUD values, query, conflicts, pagination, module toggle, and recovery
have the same observable semantics.

## 19. Runtime implementation order

1. Extract a pure Rust model/validation for the durable format and fixtures.
2. Add the `db_*` DDL, full rebuild, and schema snapshot tests.
3. Introduce `DatabasePort`, read-only list/get/query, and generated IPC bindings.
4. Add the incremental watcher projection and generation events.
5. Implement single-value CAS mutations and the optimistic frontend queue.
6. Add views/templates/schema mutations.
7. Add journaled membership, relations, batch, and CSV operations.
8. Add YAML sync/conflict resolution.
9. Run the benchmark, fix p95, and extend the query planner based on data.

Each step remains a separate small PR. The first implementation slice does not
start the Table UI until rebuild, typed query, and revision conflict are proven by
automated tests.
