# Mutation and notification inventory

In `src-tauri/src` there are 238 occurrences of `#[tauri::command`, including reads and commands outside the scope of the task. The inventory includes 116 entry points related to the listed data, settings and derived projections; some of them write data only under certain conditions. Found 23 subscription sites for `listen`, 13 groups of background and indirect writes, and 191 direct calls in the UI and services, resolved through TypeScript to ports and storage. This number does not include indirect callbacks and is not equal to the number of user actions.

## Verification boundaries

TypeScript resolved the direct calls to the corresponding modules; callbacks and dynamic calls are not always resolvable automatically, and the specific unresolved places are marked in the tables. Scenarios with two windows, an event landing in the middle of a long batch, and restoring an archived database row were not reproduced through the real UI. These are limits of the verification, not proof that there are no bugs.

### Clarification of background writes on open

`vault_context.rs:176–250` performs preparation before `load_vault` and the full rebuild of projections. Five groups can be distinguished in it: checking and recovery of Relation and its schemas; recovery of unfinished property group operations and checking of old-version edits; cleanup of expired drafts; recovery of unfinished database batch operations; recovery of workshop operations. These paths do not register every write in `WatcherState` from the activation code and do not broadcast an event for each path: their result is taken into account by the subsequent load of the index and tree, and quarantine messages end up in the load warnings. This is a description of the open order, not proof of consistency of other already open windows.

Besides overwriting, sync can move files (`sync/vault_fs.rs:421`), move them to the archive (`:467`), and remove empty folders (`:475`). Regular paths are seen by the system watcher; the `amby_written` enumeration is filled when `.amby` is successfully published through `VaultStaged::publish` (`:278`), not in these methods. Therefore renaming or deleting a file inside `.amby`, if the engine allows such a scenario, does not by itself produce `sync-amby-written`. The engine explicitly considers `Act::Trash` for property groups and counts the loss of values before checking the threshold (`sync/core/src/engine/apply.rs:864`); a deletion below the threshold does not get a separate `amby_written`. `sync-remote-deleted` passes the list of deleted paths, but the handler `sync-notices-host.tsx:181` only marks open documents, without re-reading the groups.

### Additional results and application

`MutationOutcome` contains `FsMutationResult` (primary ID/path, `pathChanges`, `deletedPaths`, `deletedIds`, an optional `treePatch`), the index state, and warnings. The internal `also_touched` is not serialized (`model.rs:129`). `WriteNoteOutcome` contains the path and revision, but not a list of other files. `LayerResult` contains the note path, the layer path, and a list of moves. The differences between database results and their consumers are given in the mapping table of the second report.

Calls of property commands under other names are clarified in `orchestration/use-property-actions.ts:291–465`: `createProperty`, `renameProperty`, `changePropertyType`, `setPropertyAppearance`/`setPropertyIcon`/`setPropertySettings`, `setPropertyValue`, `setPropertyList`, `reorderProperties`, `deletePropertyByName`. The old methods `upsertCustomProperty`, `deleteCustomProperty`, `reorderCustomProperties` explicitly refuse in the desktop adapter (`desktop-adapter.ts:980–1006`); they must not be treated as working IPC writes.

For the workshop, `creative-panel.tsx:210` calls `onCreativeChanged` after creation, refreshes the workshop catalog, and opens the result; `project-settings-dialog.tsx:168` calls `onChanged` and the project refresh; `project-desk.tsx:287–362` increments the data counter after entry changes. These local actions do not broadcast a notification to all windows.

Tests `cargo test --manifest-path sync/Cargo.toml -p amby-sync-core --test engine_props_groups_guard`: 10 passed; they check merging and loss thresholds, but not delivery of the notification to the interface.
