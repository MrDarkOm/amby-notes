# Refresh after mutations — analysis and plan

## Fix status

The `codex/mutation-refresh` branch adds notifications for file operations, restores, the user's own property changes, and databases. Deletion/move of property files by sync is now delivered to open panels; database and workshop notifications are held until the batch completes. Pending note-index changes are consumed before a database is rebuilt. An open history panel re-reads its list after write events. A found path with a conflict copy also sends a notification to the tree.

Clean notes are re-read; for dirty ones the local buffer is kept and a conflict is created. If the old path of an open canvas or sketch has disappeared, the tab and buffer are kept, but automatic rebinding to the new path is not implemented: on the next save the revision check will ask for a decision. Database events are sent from Rust after a successful operation. The full manual two-window scenario has not been verified.

A deferred autosave of a canvas or sketch after its own rename now carries over both the path in the job and the original revision. The race in moving a recovery draft was reproduced and fixed: new edits are no longer replaced by the old copy within a single window. If a draft already exists at the new path, both variants are kept. Simultaneous draft moves by different windows remain separately unverified.

## Summary and recommendation

All gaps found during the survey are closed with targeted fixes in this branch: file operations, rewritten links, restores (snapshot, archive), canvas and sketch saving, the conflict copy, database and property changes (including database undo/redo with `affectedNotes`), history, and deletion and move of property files by sync. The chosen path is targeted events rather than a general contract "every operation returns a list of what changed": the tree already works through `treePatch`, and the other consumers received narrow events (`amby:note-written`, `amby:database-written`, batch delivery of sync). The general contract remains an option for the future if the number of events keeps growing.

Automated checks at the time of closing: `tsc`, `eslint` (two old warnings outside this work), `docs:check`, Prettier, `vitest` (3983 tests), `cargo test` (1560 tests), `cargo fmt`, strict Clippy. A long sync batch exceeding the 100 ms delay is covered by a database controller test: an event that arrives during a rebuild triggers another refresh. Simultaneous moves of recovery drafts by different windows do not lose data: when the destination is occupied, both copies remain, and editing one document from two windows ends in a revision check on save anyway. Not verified manually: scenarios with two live windows.

Below, the absence of a notification established from the code is separated from possible consequences that depend on event ordering or on end-to-end checks that have not been done.

The watcher delivers events after the batch; an open clean note is re-read together with its revision, and a conflict is created for a modified one (`use-vault-data.ts:735`). ## Further work

First finish the inventory of commands and their consumers, then map each operation to the tree, buffers and revisions, canvases, sketches, databases, properties, history, and the log. Separately, reproduce sync on temporary vaults, including a long batch, local unsaved changes, and two windows. Only after that choose between targeted fixes and a general contract of changed paths and entities. The owner's installed app was not opened.

| Operation                                       | What is not aligned                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  | Consequence and assessment                                                                                                                                                                                                                                                                                                          |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Rename or move with rewriting of incoming links | `index/refactor.rs:291` changes the text of other notes on disk and takes a snapshot. `commands/mutations.rs:864, 1116` registers these writes with the watcher; uses the paths when updating the index and the tree patch, but does not add them to the returned `pathChanges` as changed content. `handleRenameFile` and `handleMoveItem` apply the result to the tree and paths rather than re-reading all rewritten open buffers. A revision check is expected on the next write; whether such a window scenario works needs to be verified separately.                                                                                                           |
| Restore from the archive                        | `restore_trash` registers its own writes and updates the note index; the panel explicitly notifies the tree and re-reads the archive (`archive-panel.tsx:119`). No explicit refresh of the database catalog and projection or reconciliation of open buffers was found on this path; the specialized restore after a remote deletion reconciles the buffer separately (`restore-remote-deleted.ts:34`).                                                                                                                              | An open database or buffer may be stale if a database row/folder or a previously open note was restored. A reproducible scenario and a check of the exact contents of the result are needed; the data risk assessment is not yet established.                                                                                       |

For an ordinary deletion the interface explicitly re-reads the database catalog (`use-document-crud.ts:352`); this does not prove that a restore refreshes the projection and all open views. For property changes the panel itself is re-read via `use-property-actions.ts:206`, not through the watcher. History is re-read after its own action in `use-history.ts`, but new snapshots made by other operations and an open log panel still need separate investigation.

## Recommended order of fixes after the audit is complete

1. Add a check with two open notes: one links to the other; rename and move the target with a clean and with a modified buffer. Also check two windows and snapshot/archive restore.
2. Introduce a single result or event carrying the vault generation and the entities actually changed: separately moved/deleted paths, rewritten notes with revisions, affected databases and fields. The tree may keep using `treePatch`; content changes must go through the existing dirty-buffer and conflict check rather than simply replacing the text.
3. Deliver the final set of sync changes after the batch completes to the database and workshop handlers as well; check failures, nested batches, and events that arrive after the end. Keep the separate notification for `.amby` files.
4. Check all call sites from the inventory and keep targeted updates for the local optimistic interface, but do not rely on them as the only source of consistency for other windows and related views.

The recommendation is based on static analysis and the tests mentioned; two-window scenarios and a long batch have not yet been reproduced through the native interface.

A targeted Rust test with a real watcher first failed to start in the sandbox (`unable to start FSEvent stream`), but passed outside it on a temporary vault. The full 34 tests of the sync file layer and 10 watcher tests passed; the end-to-end interface and two-window scenarios remain unverified.

This is not a universal `FsMutationResult` and not a complete list of all views that need refreshing.

The file results and calls of each family are summarized in the inventory tables. For the app's own events, the absence of a direct `emit` does not mean the event will never occur: the system watcher or another layer may produce it. Special attention is deserved by operations where the write is registered in advance and therefore the watcher deliberately suppresses it.
