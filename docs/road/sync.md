### Как запустить

```bash
git push origin HEAD:gates/run
```

Если ветка уже есть, нужен `--force`. Это именно `push` в ветку, а не кнопка и не расписание: такие запуски работают только для файла на `main`, а `sync/` туда попадает при выпуске. Одновременно идёт один запуск (группа `concurrency: sync-gates`; второй встаёт в очередь, а не отменяет первый). Все действия закреплены на полные SHA (проверены `git ls-remote`), права `contents: read`.

### Длинная симуляция

- `sync/simrun`, 20 заданий × 4 процесса (по числу ядер раннера) × 2 режима (`quick`, `folders`) × 400 зёрен = **64 000 сценариев**, зёрна не пересекаются: процесс g берёт зёрна `1 + 400·g .. 400·(g+1)`.
- Упавшие зёрна выводятся в итоге вместе с командой `cargo run --release --manifest-path sync/Cargo.toml -p amby-sync-simrun -- <зерно> 1 <режим>`; полные журналы с трассой — в артефактах `sim-logs-<k>`. Сбой самого транспорта тестового клиента (`INFRA`) выводится отдельно и тоже делает итог красным.
- **Сломанные движки.** Задание `self-check` гоняет `self_check` (все 12 намеренно сломанных мини-движков должны быть пойманы, правильный пройти) с четырёх начальных зёрен: 1, 100001, 200001, 300001 (`AMBY_SIM_SEED`); локально с зерна 300001 все 23 теста прошли (109 с в `release`).

Это безопасно: на пробе около одного соединения на сценарий, упирается всё в процессор (вывод ключа), а не в порты. `simrun` не менялся.

### Зерно 23390: ошибка классификатора

После аварий и переименований две живые записи временно ссылались на
`Ideas/Deep/AMBYSIM-6.md`. Когда файл исчез, `classify` складывал отсутствующие записи в
таблицу по пути; одна запись вытесняла другую. Для вытесненного идентификатора класс
вообще отсутствовал. Решение принимало отсутствие класса за `Same`, не находило файл и
пропускало запись без удержания курсора. Последующие проходы уже не видели пропущенную
серверную версию 3 и повторно пытались отправить правку с базой 2: сервер неизменно
возвращал конфликт, после пяти попыток движок отвечал `Busy`.

В отдельном коммите сначала добавлены два красных теста `gates_regressions.rs`:
исходный неизменённый сценарий `23390` в обоих режимах. Оба падали по исходной причине.
Исправление завершает классификацию по **всем живым записям**, сохраняя уже найденные
классы и назначая `Deleted` только отсутствующим. Это не меняет формат состояния,
правила слияния или пороги защит. После исправления оба теста зелёные.

Дополнительно локально проверены зёрна `23301..23400` в обоих режимах: 200 успешных
сценариев, без сбоев и повторов транспорта. Это не заменяет новый полный прогон ворот.

### Д75: изменения без увеличения объёма в смешанном коммите

Направленные проверки обнаружили ещё один дефект: `Out.blob.is_some()` означает,
что у записи есть тело, но не означает увеличение занятого места. Переименование
несёт прежнее тело, уменьшение — новое тело меньшего размера. После `507` прежнее
разбиение относило оба случая к росту и задерживало их вместе с новой загрузкой.

В отдельном коммите добавлены красные тесты `quota_rename_regression.rs`. Исправление
сравнивает зашифрованный размер новой версии с размером живой базы, как серверное
правило П56-в: только положительное увеличение относится к росту. Часть без увеличения объёма
отправляется первой; незавершённая запись сохраняется для ожидающей части.
Результат `NoRoom` переносит именно ожидающие изменения, чтобы уже отправленное
переименование не попадало в список `QuotaFull`.

Оба теста после исправления зелёные. Ошибочное ожидание старой версии в тесте
уменьшения исправлено отдельным коммитом `70cc540` с явного согласия владельца
26 октября; остальные проверки этого замороженного теста сохранены.

Отдельный красный тест `quota_split_safety.rs` воспроизвёл перезапись незавершённой
части: два элемента могут ссылаться на одно тело, поэтому уменьшение одного элемента
не всегда уменьшает общий объём. Сервер вправе отказать и части, которую прогноз
считал нерастущей. Раньше результат её повторного `commit` игнорировался, и следующая
часть заменяла запись о незавершённой отправке. Теперь отказ возвращается вызывающему
коду; ожидающий коммит не перезаписывается. Этот тест после исправления зелёный.

### Д13: запись папки, которая раньше была пустой

Мутант `classify.rs:179` оказался не равнозначным. Папка, синхронизированная пустой,

### Как проверена сила новых тестов

Мутации из артефактов накладывались последовательно на исходный код по точным diff,

функциях убраны только лишние `clone()` для типов `Copy` и применён Rustfmt.

Проверены границы квоты, повтор `413`/`507`/`UNKNOWN_BLOB`, сохранение посторонних
незавершённых загрузок, смена содержимого после обрыва, точное заполнение квоты,
источник равного ограничения, независимые ошибки нескольких записей и диапазон

### Неизменённые ограничения

При повторе уже сохранённого коммита `507` по Д76/Д7 по-прежнему удерживает его целиком;
последующие пакеты не заменяют эту запись. Расширение разбиения на такой повтор —
отдельное изменение контракта, в этой правке оно не делалось. Новое разбиение относится
к первому достоверно отказанному смешанному пакету и защищает сохранённую запись при
повторном отказе части.

Два прерванных GitHub задания не считаются успешными. После изменения движка нужен
новый **полный** прогон ворот; частичный перезапуск старого кода его не заменяет.
Push/запуск ворот — по разрешению владельца; снятие ограничения настоящих хранилищ —
только после его подтверждения новых полных результатов и подготовки резервной копии.

### Ошибка движка (остановка №4)

`apply_plan` делает три раунда переименований и ломает цикл (`break_cycle`) только в раунде без продвижения. Если принимающее устройство получает «обмен имён» двух файлов (a↔b) вместе с независимым переименованием третьего (c→d) в одном проходе, раунд 0 даёт продвижение (c→d), цикл ломается только в раунде 1, и трёх раундов не хватает: файл остаётся под служебным именем `b.md.amby-swap-0`, а следующий же шаг прохода (`push`) отправляет это состояние на сервер. Итог: имена перепутаны на всех устройствах, включая то, где пользователь сделал обмен. Содержимое не теряется. Чистый обмен и цикл из трёх работают (на них есть тесты, зелёные).

- Красный тест: `sim/tests/survivors_apply_decide.rs::sv_a_swap_of_two_names_with_an_independent_rename_is_finished` (`#[ignore]`; запуск `cargo test --release -p amby-sync-sim --test survivors_apply_decide -- --ignored`).
- Воспроизведение и подробности: `side-session-notes/…/apply-swap-bug.md`.
- Мутанты `apply.rs:170:36` и `170:49` (`&&` → `||` в условии разрыва цикла) **лечат** этот случай, поэтому тест, зелёный на настоящем движке, их не убьёт. Они остаются «не решены» до исправления движка; после исправления красный тест станет зелёным и закроет и их.
- Родственное наблюдение, не ошибка: цикл из четырёх и более файлов или два независимых цикла за один проход оставляют часть переименований на следующий проход (они закончатся в нём, имена не теряются).

### Исправление Codex (25 октября)

После разрешения владельца ошибка воспроизведена готовым тестом: на устройстве 1 остались
`S/a.md=AAA` и `S/b.md.amby-swap-0=BBB`. Из теста снят только `#[ignore]`, проверки не менялись.
В `apply_plan` разрыв обнаруженного цикла больше не зависит от продвижения независимых
переименований: он проверяется после каждого из первых двух раундов. Лимит Д49 в три раунда
сохранён; `break_cycle` по-прежнему переносит только участника найденного цикла.
Тест и все соседние сценарии `survivors_apply_decide` прошли: 39/39.
Это исправление не заменяет окончательный прогон ворот.

### Что происходит

Принимающее устройство (d1) получает с сервера «обмен имён» двух файлов (a↔b) вместе с независимым
переименованием третьего файла (c→d) в том же проходе. `apply_plan` делает 3 раунда переименований
(`for round in 0..3`) и ломает цикл (`break_cycle`) только если в раунде НЕТ прогресса и round < 2.
Независимое переименование c→d даёт «прогресс» в раунде 0, цикл ломается лишь в раунде 1, и на третий
раунд не остаётся места: файл остаётся под служебным именем `b.md.amby-swap-0`, а следующий же шаг
прохода (`push`) отправляет это состояние на сервер как обычное. В итоге имена перепутаны на ВСЕХ
устройствах, включая то, где пользователь сделал обмен.

### Воспроизведение (устройства d0, d1; на обоих S/a.md=AAA, S/b.md=BBB, S/c.md=CCC)

d0: a→tmp, pass; b→a, pass; tmp→b + c→d, pass. d1: один pass.
Ожидалось на d1 (как на d0): S/a.md=BBB, S/b.md=AAA, S/d.md=CCC.
Получилось: S/a.md=AAA, S/b.md.amby-swap-0=BBB, S/d.md=CCC; после settle то же самое на d0 и на сервере.
Чистый обмен без третьего переименования работает правильно (a↔b за 3 раунда). Цикл из трёх (a→b→c→a) тоже.
