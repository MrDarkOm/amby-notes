# Engineering conventions

## Required checks

Run `npm run verify` before requesting review. It performs TypeScript checking,
ESLint, Vitest, and `cargo check`. Run `npm run rust:test` after Rust changes.
The CI workflow also runs strict Clippy and checks that generated IPC bindings
match `src/lib/bindings.ts`.

The repository currently has pre-existing Prettier and Rustfmt drift. CI reports
it in a non-blocking job until a dedicated formatting-only change establishes a
clean baseline. Do not add new drift: format touched frontend files with
Prettier and touched Rust files with Rustfmt.

## Generated bindings

`src/lib/bindings.ts` is generated by the Rust test `specta_export::export_bindings`.
Never edit it manually. Whenever a Tauri command changes, run `npm run rust:test`
and commit the resulting generated binding update in the same change.

## Migrations

- Treat Markdown and vault attachments as the source of truth; SQLite is a
  rebuildable index.
- Give every persistent-data migration a monotonic version and make it either
  idempotent or able to detect that it has already completed.
- Make a backup or recovery point before any migration that writes vault files.
- Record the migration version and outcome, and document rollback or recovery
  steps alongside the migration.
- Never silently migrate `.obsidian` data or unknown user files.

## Feature flags

- Put experimental features behind an explicit, persisted flag with a stable
  name such as `experimental.e2eeSync`.
- Default flags to off until their data-loss, compatibility, and rollback paths
  are validated.
- A flagged feature must not alter on-disk formats until the user explicitly
  enables it and acknowledges any migration.
- Remove a flag only after the feature is stable and its migration/rollback
  behavior is documented.
